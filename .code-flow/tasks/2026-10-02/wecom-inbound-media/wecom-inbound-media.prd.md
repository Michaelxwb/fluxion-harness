## 2. 背景与目标

### 2.1 问题陈述 [必填]

| 维度 | 内容 |
|------|------|
| **问题描述** | 企微侧与 Agent 对话的用户发送图片或文件后，机器人**完全没有任何反应**：消息在渠道适配层被静默丢弃（`channels/wecom/adapter.py:381` 对 `msgtype != "text"` 直接 `return None`），既无回复、也无日志、也无审计。用户无法判断是"不支持"还是"机器人坏了"。**即使把消息收下来也不够**：Agent 侧同样缺通道——全仓唯一的文件读取工具是 `read_skill_resource`，且被 skill 包边界锁死（skill 包内、≤256KB），Agent 既读不到用户发来的东西，也交不出自己产出的东西。 |
| **当前替代方案** | 无。用户只能放弃附件、改打文字，而截图/文档里的信息用文字复述既费时又易失真。仓库的契约层（`MessageInput.attachments`）与端口层都没有承接能力：`attachments` 是留白字段（全仓零写入方，且 `type` 只允许 `text`），`WeComSdkPort` 只暴露 `send_text`/`reply_text`/`send_stream`。这是设计文档明写的 V1 取舍（`08-runtime-execution.backend.design.md:515`：「附件引用（V1 不解析）」），不是实现缺陷。 |
| **触发原因** | 2026-10-02 实机使用中发现：在企微里给 bot 发图并附言「识别一下图片中的内容」，bot 毫无反应。排查确认是静默丢弃，且 Agent 侧亦无消费附件的工具，遂立项把**入站附件 + Agent 附件工具面**一并补齐。 |

---

### 2.2 目标与价值 [必填]

| 维度 | 内容 |
|------|------|
| **核心目标** | 让企微入站的**图片与文件**能被真实接收、落盘、并在对话中被 Agent **真正用起来**（图片可被模型看到、文档内容可被读取）；任何"收不了"的情况都必须给出明确反馈并留审计痕迹，**不再有静默丢弃**。 |
| **预期价值** | ① 用户可用截图/文档直接表达诉求，不再被迫用文字复述；② 消除"机器人像坏了"的误判；③ 沉淀一套**与入口无关**的附件底座与工具面——企微、Console 上传、skill 产出将来共用同一条通路。 |

**成功指标**

> 本需求无历史基线数据，不编造量化数字；以下为可判定的定性目标。

| 指标 | 当前值 | 目标值 | 衡量方式 |
|------|--------|--------|----------|
| 非文本入站消息被静默丢弃的比例 | 100%（全部丢弃且无痕迹） | 0%（要么成功接收并落盘，要么给出明确反馈 + 审计） | 渠道入站审计记录：入站非文本消息数 vs（接收成功数 + 明确拒绝数） |
| 图片类消息的模型可见性 | 0%（模型拿不到任何图像内容） | 100%（图片作为多模态内容块进入模型上下文） | 实机用例：发送含可识别文字的截图，模型回答须体现图中内容 |
| 文档类消息的内容可达性 | 0% | 100%（Agent 能通过工具取出文档中的文本并据此作答） | 实机用例：发送一份内容已知的 pdf/docx，提问须能答对其中事实 |
| 文本消息路径回归 | 现有 E2E 全绿 | 不变 | 既有 im-gateway 与 agent-runtime 测试套件 |

## 4. 功能需求

### 4.1 功能清单 [必填]

| 功能ID | 功能名称 | 功能描述 | 优先级 | 来源用户故事 |
|--------|---------|---------|--------|-------------|
| FEAT-01 | 非文本入站消息识别与承接 | 识别企微回调中的图片/文件类消息，携带媒体引用进入入站管道，不再直接丢弃 | P0 | US-01 |
| FEAT-02 | 媒体下载与解密 | 经渠道 SDK 下载媒体内容，并在消息携带密钥时解密 | P0 | US-01 |
| FEAT-03 | 附件落 artifact | 将下载到的附件按租户/会话隔离落盘，产出可被引用的产物记录 | P0 | US-01, US-02, US-03 |
| FEAT-04 | 契约承载附件 | 让入站消息契约真正承载附件引用（标识、类型、大小、文件名、产物位置） | P0 | US-02, US-03 |
| FEAT-05 | 图片直发模型 | 把图片作为**多模态内容块**送入模型上下文（需放宽模型消息的内容类型与请求体组装） | P0 | US-02 |
| FEAT-06 | 附件读取工具 | 新增供 Agent 调用的产读工具：按产物标识取内容；文档类（pdf/docx/txt）在其中抽取文本 | P0 | US-02, US-03 |
| FEAT-07 | 接收反馈与审计 | 对拒绝与失败给出明确回复，并对接收/拒绝/失败写入审计 | P0 | US-04, US-07 |
| FEAT-08 | 类型与大小门控 | 可配置的单文件大小上限、单消息附件数上限与允许类型清单 | P1 | US-04 |
| FEAT-09 | 产物写出工具 | Agent 可将结果写为产物并交付到当前会话 | P1 | US-05 |
| FEAT-10 | 当前时间可用 | 让 Agent 能获得可信的当前时间基准，供定时与相对时间判断使用 | P1 | US-06 |

> P0=核心必做，P1=重要

#### FEAT-01: 非文本入站消息识别与承接

- **描述**: 渠道适配层不再对非文本消息一律 `return None`，而是按类型分流：可接收的（图片/文件）进入附件处理管道，不可接收的交给 FEAT-07 反馈。
- **验收标准**:
  - [ ] 企微回调中的图片消息能被解析出消息 ID、发送者、会话 ID 与媒体引用，并进入入站管道
  - [ ] 企微回调中的文件消息同样能被解析并进入入站管道
  - [ ] 未被识别的消息类型不再被"无声"处理：至少产生一条审计记录
  - [ ] 文本消息的现有行为逐字不变（既有用例全绿）

#### FEAT-02: 媒体下载与解密

- **描述**: 复用渠道 SDK 的下载能力取得媒体内容；消息携带解密密钥时按其解密。
- **验收标准**:
  - [ ] 能依据消息中的媒体引用下载到完整内容
  - [ ] 携带密钥的媒体能正确解密（解密后内容可被识别为原始格式，如 PNG/JPEG/PDF 魔数）
  - [ ] 下载失败（超时、URL 失效、网络错误）被明确区分并向上传递，不静默吞掉
  - [ ] 下载具有超时与字节上限，不会无界占用

#### FEAT-03: 附件落 artifact

- **描述**: 下载到的附件按既定产物口径落盘，路径按租户隔离，产出可供后续引用的产物记录。
- **验收标准**:
  - [ ] 附件落盘后能通过产物标识取回，且内容与下载内容逐字节一致
  - [ ] 不同租户的附件互不可见（跨租户读取必须失败）
  - [ ] 落盘位置遵循既有的产物根配置，不写入仓库工作区
  - [ ] 原始文件名（含非 ASCII）作为元信息保留且不丢失

#### FEAT-04: 契约承载附件

- **描述**: 入站消息契约从"留白字段"变为真实承载：附件以结构化引用随消息传递，类型字段不再只允许文本。
- **验收标准**:
  - [ ] 入站契约能表达"本条消息包含 N 个附件"，每个附件带标识、类型、大小与产物位置
  - [ ] 契约变更后，既有只发文本的调用方无需改动即可继续工作（向后兼容）
  - [ ] 契约层的序列化/反序列化有测试覆盖（含多附件与零附件）

#### FEAT-05: 图片直发模型

- **描述**: 模型消息的内容类型从"只能是字符串"放宽为可承载多模态内容块，图片以图像块形式进入上下文；请求体组装相应透传。
- **验收标准**:
  - [ ] 含图片的会话中，发给模型的请求体确实携带图像内容块（可在请求层断言，不依赖模型回答）
  - [ ] 纯文本会话的请求体与现状**逐字节一致**（不引入多余字段）
  - [ ] 实机验证：发送一张含已知文字的截图并提问，模型的回答须体现图中内容
  - [ ] 图片引用不可达/产物缺失时，降级为文本说明而非请求失败

#### FEAT-06: 附件读取工具

- **描述**: 新增供 Agent 调用的产物读取工具，按产物标识取得内容；对文档类（pdf/docx/txt 等）在工具内抽取文本返回。这是**类型无关**的读取入口，不限于企微来源。
- **验收标准**:
  - [ ] Agent 能通过工具按产物标识读取附件内容
  - [ ] pdf 与 docx 能抽取到文本，且抽取内容与文档实际内容一致（用内容已知的样本断言）
  - [ ] 纯文本类文件直接返回其文本内容
  - [ ] 二进制/不可解析类型返回明确错误，不返回乱码
  - [ ] 工具受大小上限保护，超大文件不会拖垮运行
  - [ ] 跨租户/越权的产物标识被拒绝

#### FEAT-07: 接收反馈与审计

- **描述**: 对"收不了"的消息给出用户可见的明确回复，并写入审计；这是本需求消除"静默丢弃"的落点。
- **验收标准**:
  - [ ] 类型不受支持时，用户收到一句明确说明（而非无响应）
  - [ ] 超过大小上限时，用户收到的说明中包含上限数值
  - [ ] 下载或解密失败时，用户收到明确失败说明，且措辞不泄露内部路径/密钥等敏感信息
  - [ ] 上述三种情形各有一条审计记录（可回答"这条消息为何没被接收"）
  - [ ] 成功接收同样有审计记录，可与入站消息一一对应

#### FEAT-08: 类型与大小门控

- **描述**: 门控参数可配置，默认值给出合理口径，供 FEAT-07 判定。**P0 阶段以文档化的默认常量生效**（保证 FEAT-07 的上限提示有值可用），P1 再做成可配置。
- **验收标准**:
  - [ ] 单文件大小上限、单消息附件数上限、允许类型清单均可配置
  - [ ] 配置缺省时使用文档化的默认值，而非"无限制"
  - [ ] 边界值行为明确：恰好等于上限应被接收，超过 1 字节应被拒绝

#### FEAT-09: 产物写出工具

- **描述**: 让 Agent 能把结果写为产物并交付到当前会话（出站方向只交付产物引用，端到端的文件发送不在本期，见 §6）。
- **验收标准**:
  - [ ] Agent 可写出一个产物并拿到其标识
  - [ ] 写出的产物可被 FEAT-06 的读取工具读回（闭环）
  - [ ] 写出同样受大小上限与租户隔离约束
  - [ ] 未配置交付路由时给出明确错误，不静默丢弃

#### FEAT-10: 当前时间可用

- **描述**: 给 Agent 一个可信的时间基准，供定时与相对时间（"明天早上 9 点"）判断使用。
- **验收标准**:
  - [ ] Agent 在会话中能获得当前日期时间（含时区口径，与既有时间规范一致）
  - [ ] 该时间与系统时间一致（可用测试注入固定时钟断言）
  - [ ] 不因该能力改变纯文本会话的既有请求体

### 4.2 边缘情况 [可选]

| 场景 | 预期行为 |
|------|----------|
| 一条消息带多个附件 | 全部尝试接收；部分失败时，成功的仍落盘，失败的逐个反馈 |
| 附件名为空或含路径穿越字符（`../`） | 不按用户提供的名字直接落盘；使用安全的产物标识，原始名仅作为元信息 |
| 同一消息被企微重投（重复回调） | 依既有消息幂等键去重，不产生重复产物 |
| 下载成功但解密失败 | 视为接收失败：不落半成品，回明确反馈 + 审计 |
| 图片格式不被当前模型支持 | 降级为文本说明 + 可读工具兜底，不让整个请求失败 |
| 文档加密/受密码保护 | 抽取失败给明确错误，由 Agent 转述给用户，而不是返回空内容 |
| 附件在后续轮次被引用但已被清理 | 明确告知附件不可用，不产生悬空引用 |

## 5. 非功能需求 [可选]

| 指标ID | 类型 | 要求 |
|--------|------|------|
| NFR-SEC-01 | 安全 | 附件按租户隔离，跨租户读取必须失败；解密密钥不得写入日志或审计明文 |
| NFR-PERF-01 | 性能 | 下载与文档抽取均具备超时与字节上限，不得让消息处理链路无界阻塞 |
| NFR-REL-01 | 可靠性 | 接收链路的任何失败路径都必须落到"用户可见反馈 + 审计"，不允许静默失败 |
| NFR-COMPAT-01 | 兼容性 | 纯文本消息的处理路径与既有行为一致（含发给模型的请求体）；既有 im-gateway 与 agent-runtime 测试套件保持全绿 |

> 无 NFR 时整节可省略。design 模板的 3.5 质量实现方案 / 2.5.3 非功能指标将引用这些 NFR ID。

## 6. 范围与边界 [必填]

| 类别 | 内容 |
|------|------|
| **范围（In Scope）** | ① 企微入站**图片与文件**的识别与承接（FEAT-01）；② 媒体下载与解密（FEAT-02）；③ 附件落 artifact 并按租户隔离（FEAT-03）；④ 入站契约真实承载附件（FEAT-04）；⑤ 图片作为多模态内容块直发模型（FEAT-05）；⑥ 类型无关的附件读取工具，含 pdf/docx/txt 文本抽取（FEAT-06）；⑦ 拒绝/失败的明确反馈与全程审计（FEAT-07）；⑧ 可配置的类型与大小门控（FEAT-08）；⑨ 产物写出工具（FEAT-09）；⑩ 当前时间可用（FEAT-10） |
| **非范围（Out of Scope）** | ① **出站方向的端到端文件发送**——把产物真正作为企微文件发给用户（FEAT-09 只写产物并交付引用）；② 企微以外的其它 IM 渠道适配；③ 语音/视频类消息的专门处理（若其回调结构与图片/文件同构，则顺带纳入同一管道；否则明确拒绝并反馈）；④ 附件的保留期与回收策略（复用既有产物清理口径，不新定义）；⑤ 文档的**结构化理解**（如表格还原、版面分析）——本期只做文本抽取 |
| **前置假设** | ① 企微 aibot 回调对图片/文件会携带可直接下载的媒体引用与解密密钥——**当前唯一依据是 SDK（`aibot`）的方法签名与 docstring，尚未以真实回调验证**，须在设计前用真机探针取样确认；② **当前配置的模型支持多模态图像输入**（用户确认），故图片无需另配 vision 模型；③ 既有产物存储（`muad_artifact_store` / `NfsArtifactStore`）的租户隔离能力可复用；④ 既有 im-gateway 测试套件可作为文本路径的回归基线；⑤ 文档抽取可在 Agent 侧引入解析依赖（不引入到 im-gateway） |

### 7.1 项目依赖

| 依赖方 | 依赖内容 | 最晚交付时间 | 风险等级 |
|--------|---------|--------------|---------|

### 7.2 风险识别

| 风险ID | 描述 | 影响 | 缓解方案 |
|--------|------|------|---------|
| R-01 | 回调中媒体字段的真实结构未经验证（现有认知全部来自 SDK docstring 与推断） | 设计与实现可能打偏，返工 | 设计阶段先做真机探针，抓一条真实的图片与文件回调样本落档，再定契约 |
| R-02 | 大文件下载或文档抽取拖慢消息处理链路 | 对话响应变慢甚至超时 | 设字节上限 + 超时（NFR-PERF-01）；超限走 FEAT-07 反馈 |
| R-03 | 解密失败（密钥缺失、算法不符） | 附件不可用且难以排查 | 失败必反馈 + 审计（NFR-REL-01）；不落半成品 |
| R-04 | 放宽模型消息内容类型时**误伤纯文本路径** | 既有对话行为回归 | 用「纯文本请求体逐字节不变」作为硬验收（FEAT-05 / NFR-COMPAT-01） |
| R-05 | 文档解析依赖引入供应链与体积成本 | 镜像变大、漏洞面增加 | 依赖选型在设计阶段评估；解析放在工具内、按需加载 |
| R-06 | 附件落盘造成磁盘持续增长 | 存储成本与运维负担 | 复用既有产物清理口径；本期不新定义保留策略（见 §6 非范围） |
| R-07 | 用户对"已接收"的期望被高估 | 体验落差 | 反馈与上下文措辞明确区分"已收到"与"已理解"；不可解析时如实说明 |
| R-08 | 本次范围横跨渠道入站与 Agent 工具面两侧，单批交付体积偏大 | 评审与验收周期拉长 | 按 P0（底座 + 图片直发 + 读取工具 + 反馈审计）先交付，P1（写产物 + 时间 + 门控配置化）紧随；P0 独立可验收 |
