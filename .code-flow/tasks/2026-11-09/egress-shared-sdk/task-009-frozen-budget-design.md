# TASK-009 冻结执行预算补充设计

状态：设计和验收准备，尚未实现或验证。本文补充现有总体设计，不改变 TASK-009、TASK-003 或后续任务的状态。

## 当前缺口

- `BudgetController` 的 execution 桶使用 `segment_id`，只存在于进程内；新进程或新执行段会从零开始，不能满足恢复累计。
- `SharedRedisMeter` 的公共规则键以 rule ID 建立，尚无执行或脚本作用域的冻结预算；当前 admit 不支持公共规则和冻结预算一起扣减。
- `TrustedInvocation` 是宿主内部值对象，不本身证明身份有效；持久身份、调用边界及执行段 fencing 仍需 Runtime/Worker 接线。
- Runtime 的 `_workspace_execution_id` 为目录名安全化并截断 `run_id` 和 `call_id`，不同原始 ID 可能映射到同一值；不能直接将它当作全局唯一计数身份。Runtime 当前缺少 run 上下文时还会生成随机 ID；Worker 当前以 task ID 构造脚本预算身份。两者在恢复与多脚本场景下的身份持久化契约仍需验证。
- B-04 目前只准备了公共规则变更部分，冻结预算断言故意保留未完成标记；两个进程使用计数内核不等于真实 Skill 请求路径已经接入。

## 权威来源和作用域

Run/Task 建立时冻结的预算及稳定 execution ID 是执行预算权威；每次脚本调用建立稳定 invocation ID。恢复同一次调用保留这两个 ID，新执行段只改变 segment/fence。明确新调用使用新 invocation ID，仍共享所属 execution 的总预算。ID 来自宿主可信执行上下文，不接受脚本自行声明的 ID。

计数身份使用无损或抗碰撞的完整作用域标识，不复用为文件路径设计的截断名称；是否可由持久化的完整 Run ID 与 tool call ID 派生，必须先证明恢复重放时 call ID 稳定且唯一，否则应由权威存储分配并记录 invocation ID。Task ID 可作为执行身份，但不能仅据此断言多次脚本调用的 invocation 身份已经独立。

公共规则与执行快照分离：公共规则采用保护域当前 revision；已创建执行保留自己的冻结预算。修改公共规则不能清空执行预算，更新配置只影响随后新建执行的快照。冻结快照由宿主从权威持久数据读取，SDK 不将来路不明的请求参数当作配置。

## 登记与缺失处理

按 protection domain、execution ID 建立执行登记，包含规范化预算快照摘要、初始化状态及稳定桶集合；invocation 登记绑定所属 execution 和其冻结后的 Skill 预算摘要。桶名使用稳定作用域、规则身份的无歧义编码或摘要，不包含 segment、公共策略 revision 或 attempt ID；所有键与公共规则位于相同 Cluster slot。

初始化必须由宿主在权威存储中区分「新执行首次登记」与「恢复已有执行」：首次登记以原子操作写入登记和零计数；重复登记只接受相同身份和摘要。恢复时必须要求已有登记和所有必需桶完整，缺失、摘要不符或状态不确定时失败关闭，不允许从零补建。初始化完成与权威状态之间的崩溃窗口、重试及并发创建要有明确状态机和真实 PG/Redis 测试，不能仅凭客户端传入的 `is_new` 建立安全保证。

无共享规则且冻结预算为空时直接旁路，不访问 limiter Redis。仅配置冻结预算时仍需进入共享原子计量；公共规则为空不能作为整体旁路的依据。

## 单次准入

1. 宿主检查执行租约/fencing 和 invocation 归属，匹配冻结预算与当前公共接口规则，生成新物理发送的 attempt ID。
2. 客户端将所有匹配的公共规则、执行规则和脚本规则及其 Redis 键传给同一次 Lua；命中集合与身份绑定进 attempt 指纹。公共 revision 必须与权威当前版本一致；冻结预算摘要必须与登记一致。
3. Lua 在写入前验证每个键类型、登记、作用域、参数和状态，并检查全部累计、滑窗、并发限制。任一不满足时不更新任何桶；全部满足才原子更新并写入 attempt 决策。同 attempt 仅用于 Redis 协议重试，不允许复用许可再次发送。
4. 执行或脚本累计额度耗尽返回可定位作用域的确定性错误；窗口与并发拒绝分别报告。已准入次数不回退。发送前还需消费许可并检查执行段有效性；Redis 不确定时不发送。

生命周期由可恢复状态决定，不采用请求明细的保留期清理计数。执行终态后的重放窗口、清理与 fencing 归属后续生命周期实现；Redis 异步复制丢写的限制和外部 epoch 保护仍按 TASK-003 处理。

## B-04 真实边界测试计划

在真实 Redis Cluster 和两个独立宿主进程中：

1. 建立执行 E、脚本调用 I，冻结其执行累计和脚本累计；进程 A 消耗部分额度。发布公共规则新 revision 降额，进程 B 用同一 E/I 恢复、新 segment 申请；旧公共 revision 被拒，新 revision 沿用公共桶和冻结桶。
2. 调整新执行的预算配置，证明已登记 E/I 的阈值及已用次数不变；新执行采用新快照。用新的 invocation 验证脚本额度独立，而执行额度仍共享。
3. 构造公共规则不足和冻结预算不足两种拒绝，分别验证其他命中桶均不增加；用同一 attempt 协议重试验证只扣一次，重新消费同一许可被拒。
4. 删除登记或必需计数键后模拟恢复，验证不重新初始化且不发出请求；摘要不一致同样拒绝。执行段变更本身不得重置累计。
5. 公共规则新增较长窗口时验证历史不完整期间保守阻断；有规则状态下验证 Redis 不可用 fail closed，无任何规则时验证不访问 Redis。

上述是待实现断言，不是测试结果。B-04 的跨进程场景可证明共享计量行为；PG 恢复、真实执行器、fencing 和 Skill/MCP 发送路径仍须对应后续任务的真实边界测试，不能拿本测试代替。
