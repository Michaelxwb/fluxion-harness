## 2. 背景与目标

### 2.1 问题陈述

| 维度 | 内容 |
|------|------|
| **问题描述** | 上游 MSSW 平台新增「智能客服」，需要复用我方 Agent 的对话能力。但 MSSW 的身份体系与我方完全不同：它用 RS256 签名的 `soc-token` Cookie、身份字段是明文的 `job_number`（工号），而我方 WebChat 用的是自签 `CHAT Cookie`。直接用现有 WebChat 接口会失败在第一步——认不出用户是谁 |
| **当前替代方案** | 我方已有完整的 WebChat 会话能力（202 受理、SSE 事件流、取消、历史分页、附件上传下载、会话管理），但没有一条通道能从外部身份体系接入 |
| **触发原因** | MSSW 侧需求方提出接入诉求，明确「上游只有 BFF 一层，由 BFF 转发到我们」 |

### 2.2 目标与价值

| 维度 | 内容 |
|------|------|
| **核心目标** | 为现有 WebChat 会话能力**换一个身份入口**：让 MSSW BFF 用 `soc-token` 调用，网关验签后映射为平台用户，其余能力全部复用 |
| **预期价值** | 不新建一套聊天服务，只新增 JWT 验签器与一层路由；BFF 侧按我方现有契约适配即可接入 |

**成功指标**

| 指标 | 当前值 | 目标值 | 衡量方式 |
|------|--------|--------|----------|
| BFF 可完成端到端对话 | 不可用 | 权限探测 → 建会话 → 发消息（202）→ SSE 订阅 → 查历史 全链路可用 | 验收用例 |
| 现有通道回归 | WEBCHAT / WECOM 正常 | 零行为变化 | 现有测试全绿 |

## 3. 用户与场景

### 3.1 目标用户

| 维度 | 内容 |
|------|------|
| **用户画像** | MSSW 平台上的终端用户（有工号的内部员工），通过 MSSW 前端使用「智能客服」Tab；中间由 MSSW BFF 转发请求 |
| **使用场景** | 用户在 MSSW 前端打开智能客服 → 与 Agent 多轮对话（流式）→ 中途可停止 → 可回看历史 → 可上传/下载附件 |

> 我方不直接面向终端用户，**直接调用方是 MSSW BFF**。这是本需求的特殊之处：对接契约的"用户"是 BFF，终端用户只通过 BFF 间接使用。

### 3.2 用户故事

| 编号 | 用户故事 | 优先级 |
|------|---------|--------|
| US-01 | 作为 MSSW BFF，我希望带 `soc-token` 调权限接口就能知道该用户能否看到「智能客服」入口，以便决定 Tab 是否可见 | P0 |
| US-02 | 作为 MSSW BFF，我希望用同一个 `soc-token` 建会话并发送消息，且发送后立即拿到受理结果（202），以便前端能马上进入等待态 | P0 |
| US-03 | 作为 MSSW BFF，我希望订阅某个 Run 的事件流做流式渲染，断线后能从上次位置续上，用户点「停止」时能中断 | P0 |
| US-04 | 作为 MSSW BFF，我希望按游标读取历史消息，用户回看时能翻页 | P0 |
| US-05 | 作为 MSSW BFF，我希望用户能上传和下载附件 | P1 |
| US-06 | 作为平台管理员，我希望在 Console 里把 MSSW 工号对应到我方用户，未映射的工号无法使用智能客服 | P0 |
| US-07 | 作为运维，我希望 MSSW 通道未配置或已停用时请求返回明确错误码，而不是 500 | P1 |

## 4. 功能需求

### 4.1 功能清单

| 功能ID | 功能名称 | 功能描述 | 优先级 | 来源用户故事 |
|--------|---------|---------|--------|-------------|
| FEAT-01 | JWT 验签与身份映射 | 校验 `soc-token` 的 RS256 签名与 `aud`/`iss`，取出 `job_number`，映射为平台用户 | P0 | US-01 |
| FEAT-02 | 权限探测接口 | `GET /permissions`：返回入口可见性与 `entry_id`/`agent_id`，判定复用现有入口查询 | P0 | US-01 |
| FEAT-03 | 建会话与发消息 | `POST /conversations`、`POST /messages`：复用现有 202 受理语义，幂等以我方 `Idempotency-Key` 为准 | P0 | US-02 |
| FEAT-04 | 事件流订阅与取消 | SSE 订阅（支持断线续传游标）、`POST /cancel` 中断 Run | P0 | US-03 |
| FEAT-05 | 历史分页 | 按我方 `page` + `page_size` + `through_seq` 读取历史消息与产物 | P0 | US-04 |
| FEAT-06 | 附件上传下载 | 复用现有附件能力，含格式清单与压缩包读取约束 | P1 | US-05 |
| FEAT-07 | 通道配置与工号映射管理 | Console 侧维护 MSSW 入口账号与「工号 ↔ 平台用户」映射 | P0 | US-06 |
| FEAT-08 | 通道错误码与未配置处理 | 四个稳定错误码；选配未开 → 404，而非 500/501 | P1 | US-07 |

#### FEAT-01: JWT 验签与身份映射

- **描述**: 在网关侧校验 MSSW `soc-token`（RS256 + PKCS#1 公钥），比对 `aud`/`iss` 密文，取出明文 `job_number`，经 Console 解析为平台用户与入口授权
- **验收标准**:
  - [ ] 合法 token（含 `exp: -1`）验签通过，能解析出 `job_number`
  - [ ] 签名错误、格式错误、`alg=none`、缺 `job_number` 均 401，且 fail-closed（不降级放行）
  - [ ] `aud`/`iss` 比对走「加密期望值比对」，不实现 AES 解密
  - [ ] 不依赖 `exp` 判断有效性（上游恒为 -1）
  - [ ] 工号未建映射 → 无法取得平台用户身份

#### FEAT-02: 权限探测接口

- **描述**: 新增 `GET /permissions`，供 BFF 决定「智能客服」Tab 是否可见
- **验收标准**:
  - [ ] 已映射且入口可用 → 200，返回 `{"visible": true, "entry_id": ..., "agent_id": ...}`
  - [ ] 已映射但无授权 → 200 `{"visible": false}`
  - [ ] 工号未映射 → 200 `{"visible": false}`
  - [ ] token 无效 → 401
  - [ ] 入口未配置或已停用 → 404 `MSSW_CHANNEL_NOT_CONFIGURED`

#### FEAT-03: 建会话与发消息

- **描述**: `POST /conversations` 与会话内的 `POST /messages`，复用现有 WebChat 的 202 受理语义
- **验收标准**:
  - [ ] 消息受理返回 202 与 `run_id`，不等正文生成
  - [ ] `Idempotency-Key` 重复提交返回同一 `run_id`，不产生第二个会话/Run
  - [ ] 幂等指纹只含我方值（`tenant_id`/`agent_id`/`platform_user_id`/`entry_id`/`external_thread_id`），**不含正文**
  - [ ] 会话归属按 `conversation_id` + `tenant_id` + `platform_user_id` 三键校验

#### FEAT-04: 事件流订阅与取消

- **描述**: 订阅 Run 的 SSE 事件流与取消能力
- **验收标准**:
  - [ ] 可按 `after_seq` 从指定位置续订，断线重连不重复不漏
  - [ ] 订阅前必须做归属校验（按 `platform_user_id`），**不能只凭 `run_id`**
  - [ ] 游标过期返回 409 `CURSOR_EXPIRED`，BFF 可转历史接口补全（两者同一套 canonical seq 水位）
  - [ ] `POST /cancel` 幂等，重复取消不报错

#### FEAT-05: 历史分页

- **描述**: 按游标读取历史消息与产物
- **验收标准**:
  - [ ] 直接复用我方 `page` + `page_size` + `through_seq` 参数形态，**不做游标转换**
  - [ ] `through_seq` 与事件流 `after_seq` 处于同一套水位空间

#### FEAT-06: 附件上传下载

- **描述**: 复用现有附件能力
- **验收标准**:
  - [ ] 上传注册只需 `user_id`/`agent_id`/`entry_id`，不传 `external_user_id`
  - [ ] 允许的媒体类型沿用统一格式清单，未登记类型显式拒绝
  - [ ] 产物下载可用

#### FEAT-07: 通道配置与工号映射管理

- **描述**: Console 侧维护 MSSW 入口账号与工号映射
- **验收标准**:
  - [ ] 可创建 MSSW 通道入口账号（单入口，`bot_id` 由配置指定）
  - [ ] 建用户时 `user_code` 填工号，并为该用户建立 MSSW 通道身份映射
  - [ ] 运行时解析只查已建映射，**不做首次访问自动建档**
  - [ ] 移除映射后该工号立即无法使用（后续请求 401/403）

#### FEAT-08: 通道错误码与未配置处理

- **描述**: 提供稳定、可区分的错误码
- **验收标准**:
  - [ ] 四个错误码稳定：`MSSW_JWT_INVALID`(401)、`MSSW_USER_NOT_MAPPED`(403)、`MSSW_CHANNEL_NOT_CONFIGURED`(404)、`CURSOR_EXPIRED`(409)
  - [ ] 选配未配置返回 404，不用 501/500

### 4.2 边缘情况

| 场景 | 预期行为 |
|------|----------|
| token 已登出（MSSW 侧已吊销）但签名仍有效 | 我方无法感知（`exp` 恒为 -1、吊销在 MSSW Redis）。由 BFF 转发前判定有效性，形成我方连接寿命 + BFF 责任边界 |
| 同一用户重复提交相同消息 | 幂等命中，返回原 `run_id` |
| 已映射工号被移除映射 | 后续请求不再能解析出平台用户 |
| 入口被停用 | 需入口的接口返回 404 `MSSW_CHANNEL_NOT_CONFIGURED` |
| 事件流游标过旧（超出保留窗口） | 409 `CURSOR_EXPIRED`，BFF 转历史接口 |
| 请求体里出现 `conv` 等上游字段名 | 不做别名兼容，按我方字段名（`conversation_id`） |

## 5. 非功能需求

| 指标ID | 类型 | 要求 |
|--------|------|------|
| NFR-SEC-01 | 安全 | JWT 验签 fail-closed：任何校验失败都必须拒绝，不得降级放行；不实现 AES 解密，只比对加密期望值 |
| NFR-SEC-02 | 安全 | 所有需要身份的接口必须做归属校验（按 `platform_user_id`），不得仅凭 `run_id`/`conversation_id` 的单键授权 |
| NFR-SEC-03 | 安全 | 密钥按静态单密钥配置读取，**不实现轮换、不做多密钥并存/版本槽位**（上游已定） |
| NFR-COMPAT-01 | 兼容性 | WEBCHAT / WECOM 两条现有通道零行为变化 |
| NFR-MAINT-01 | 可维护性 | 通道差异只活在适配器层，核心域零渠道专有字样（见 RULE-im-002） |

## 6. 范围与边界

| 类别 | 内容 |
|------|------|
| **范围（In Scope）** | JWT 验签与身份映射；`/permissions` 探测；建会话与发消息（202）；SSE 事件流（含续订）与取消；历史分页；附件上传下载；Console 侧入口与工号映射管理；四个错误码 |
| **非范围（Out of Scope）** | token 有效性与吊销判定（责任在 BFF）；本地签发时间窗；token 校验接口；密钥轮换；AES 解密；第二套认证域（不复用 CHAT Cookie）；客户维度隔离；用户自动建档；改动 WEBCHAT / WECOM 行为；MSSW 前端界面 |
| **前置假设** | ① BFF 是后端服务转发，非浏览器跨站，`soc-token` 可正常送达；② 上游只有 BFF 一层，BFF 会在转发前校验 token 有效性；③ 管理员会预先完成工号映射；④ 生产密钥（`issue`/`audience`/`salt`/公钥）后续提供 |

## 7. 依赖与风险

### 7.1 项目依赖

| 依赖方 | 依赖内容 | 最晚交付时间 | 风险等级 |
|--------|----------|--------------|---------|
| MSSW 需求方 | 生产环境 `issue`/`audience`/`salt`/公钥（M5） | 生产联调前 | 中（**只阻塞生产联调**，开发环境值已实测确定） |
| MSSW BFF | 转发前校验 token 有效性；按我方契约适配 | 联调前 | 中（属对接约定，需落成对方实现） |
| 平台管理员 | 完成工号 ↔ 平台用户映射 | 上线前 | 低 |
| 依赖包 | 新增 `PyJWT`（`cryptography` 已在依赖树中） | 开发期 | 低 |

### 7.2 风险识别

| 风险ID | 描述 | 影响 | 缓解方案 |
|--------|------|------|---------|
| RISK-01 | Runtime 的 `_load_run_in` 只按 `id + tenant_id` 查、不带 user_id，同租户内拿到 `run_id` 即可越权读 | 安全漏洞 | 网关必须按 `platform_user_id` 复核归属；SSE 建连同样必须校验 |
| RISK-02 | 历史 token 重放：`exp` 恒为 -1，吊销在 MSSW 侧 | 已登出用户可用旧 token 继续访问 | 责任前移给 BFF；我方不设时间窗（无效且会误杀） |
| RISK-03 | `CURSOR_EXPIRED` 无补全数据（`check_cursor` 只抛错） | "按历史补全"需自行编排 | R6 自行实现"过期 → 转历史接口"；两者同一套水位，无需换算 |
| RISK-04 | 生产密钥未取得 | 无法生产联调 | 需求方"后续会给"；开发环境值已实测确定，不阻塞开发 |
| RISK-05 | 密钥固定不轮换 | 公钥泄露无法靠轮换止损 | 上游选择；实现为单密钥静态配置，泄露时换密钥 + 重新部署 |
