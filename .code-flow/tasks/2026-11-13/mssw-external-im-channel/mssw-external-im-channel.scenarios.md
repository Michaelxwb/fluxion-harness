# MSSW 外部 IM 入口 验收场景

> **修订版本**：v1.2；状态为待实现/待人工执行，本文不代表验收已通过。

> 这是给**人工测试者**使用的验收清单，不是 E2E 代码或测试注册表。
> 每个场景保留 S-/E-/B- 编号，供 design 和 Task 的 `Scenarios` 字段引用。
> 步骤用用户能执行的界面动作、CLI 命令或 API 请求描述；期望写用户可观察的结果。
> 本次接入方是业务平台 BFF，因此部分场景以 API 请求为主；Console 管理面场景以页面操作为主。

## 公共前置

- Console、Gateway、Runtime 已启动。
- Console 的 Secret 已配置 `mssw` 因子（公钥、issuer、audience、salt）。
- 已创建 MSSWWEB 入口（`entry_id` 已知），并已把测试用户的 MSSW `user_id` 绑定到平台用户。
- 已准备一条**真实签发**的 MSSW `soc-token`（测试账号，未过期/或被允许的 `exp=-1`）。
- 测试工具：curl 或业务平台 BFF 代理；SSE 用 `curl -N` 或浏览器 DevTools。

## S-01 管理员创建 MSSWWEB 入口

- **负责**：待 plan 分配
- **前置**：管理员已登录 Console；Agent 已存在；Secret 已配置 `mssw`。
- **步骤**：
  1. 打开 Agent 详情 → 通道。
  2. 点击“新建通道”，类型选择 `MSSWWEB`。
  3. 填写名称与入口标识 `bot_id`（与 WebChat 一致）；确认页面没有 Secret 输入框。
  4. 观察页面是否出现“平台 mssw 已配置”的提示。
  5. 保存。
- **期望**：
  - 保存成功，通道列表出现该 MSSWWEB 入口。
  - 表单有入口标识 `bot_id`，没有 Secret 输入框。
  - 页面不显示公钥、salt、issuer/audience。
  - 入口状态为启用，Agent 正确。

## S-02 管理员创建用户级外部身份并授权入口

- **负责**：待 plan 分配
- **前置**：已有 MSSWWEB 入口；用户已存在；平台 `identity_keys` 已知（如 `["expert_id","tenant_id"]`）。
- **步骤**：
  1. 打开用户详情 → 外部身份。
  2. 点击“新建外部身份”，输入身份 JSON：
     - 单字段示例：`{"user_id": "6620c18c73c760c6b6ca527f"}`；
     - 多字段示例：`{"expert_id": "E123", "tenant_id": "1001"}`。
  3. 提交，得到用户级外部身份。
  4. 在该身份下“添加入口”，选择一个 MSSWWEB 入口并授权。
  5. 刷新身份/授权列表。
- **期望**：
  - 身份创建成功，列表显示身份 JSON 与平台 `identity_keys`。
  - 多字段必须全部匹配；key 集合与平台不一致时提示 `IDENTITY_KEYS_MISMATCH`，不落库。
  - 同一身份可授权多个入口，但只有一个 `platform_user`。
  - 把同一身份 JSON 绑到另一个平台用户时提示 `IDENTITY_ALREADY_BOUND`，不产生第二条。
  - 解绑某个入口只移除 grant，身份仍在；其他入口不受影响。

## S-03 完整对话（BFF 代理）

- **负责**：待 plan 分配
- **前置**：S-02 已完成；BFF 可携带 `soc-token` 调用。
- **步骤**：
  1. 调 `GET /api/v1/msswwweb/identity`，携带 `soc-token`。
  2. 调 `GET /api/v1/msswwweb/entries`，拿到入口。
  3. 调 `POST /api/v1/msswwweb/entries/{entry_id}/conversations` 创建会话。
  4. 调 `POST /api/v1/msswwweb/entries/{entry_id}/messages` 发送一条文本，带 `Idempotency-Key`。
  5. 用返回的 `run_id` 打开 `GET /api/v1/msswwweb/runs/{run_id}/events`。
  6. 调 `GET /api/v1/msswwweb/conversations/{id}/messages` 查看历史。
- **期望**：
  - `/identity` 返回 `allowed=true`，grants 含该入口。
  - 创建会话返回 201 与 `conversation_id`。
  - 发消息返回 202，带 `run_id`。
  - SSE 有增量帧，最终有终态；连接正常结束。
  - 历史消息包含刚才的用户消息与助手回答，刷新后仍在。
  - 响应均为 `no-store`，不出现 token/因子。

## S-04 停止生成

- **负责**：待 plan 分配

- **步骤**：
  1. 发一条会触发长回答的消息。
  2. SSE 开始输出后，调 `POST /api/v1/msswwweb/runs/{run_id}/cancel`。

  - SSE 在合理时间内结束，不继续输出。
  - 历史里该 Run 终态为取消，不出现伪完成。
  - 可以继续在该会话发下一条消息。

## S-05 最近会话与红点未读

- **负责**：待 plan 分配
- **前置**：用户至少有一个会话，且有一轮 Run 已完成但未读。
- **步骤**：
  1. 调 `GET /api/v1/msswwweb/conversations?agent_id=...`。
  2. 找到有未读通知的会话，观察 `has_unread` 与来源 `entry_id`/`channel`。
  3. 取该会话详情，记录同次返回的 `last_seq=C` 与 `notification_through_seq=N`，显示其当前状态/确认提示。
  4. 用 `through_seq=C` 获取历史并展示；随后调会话 read，body 为 `{"through_seq":N}`。
  5. 再查一次会话列表。
- **期望**：
  - 列表按最近活动倒序；同用户+Agent 跨入口聚合；第一条是最新会话。
  - 有未读终态通知的会话 `has_unread=true`。
  - mark-read 只标水位内通知；新通知保留未读；重复调用不报错。
  - 再查列表已读会话 `has_unread=false`，其他会话不受影响。

## S-06 上传图片/文件与 Agent 产物下载

- **负责**：待 plan 分配
- **前置**：S-03 可复现；准备一张图片与一个允许的文档。
- **步骤**：
  1. 调 `POST /api/v1/msswwweb/entries/{entry_id}/attachments` 上传文件（multipart，字段 `file`）。
  2. 拿到 `upload_id`，在发消息时带上 `upload_ids`。
  3. 让 Agent 生成一个文件（如“整理成 Excel”）。
  4. 在 SSE/历史中观察附件卡，点击/调用下载。
- **期望**：
  - 上传成功，返回 `upload_id`、大小、校验和。
  - 消息发送成功，Agent 能读到文件。
  - Agent 产物在历史里显示为附件卡。
  - 下载返回正确字节与文件名；`checksum`/`conversation_id` 不匹配时 404。

## S-07 删除会话

- **负责**：待 plan 分配
- **前置**：S-03 已完成，至少有一个会话；可另选一个有活跃 Run 的会话。
- **步骤**：
  1. 调 `DELETE /api/v1/msswwweb/conversations/{id}`。
  2. 再查会话列表、详情、消息。
  3. 重复调用删除。
  4. 对活跃 Run 的会话重复步骤 1。
- **期望**：
  - 删除成功，列表不再出现该会话；详情/消息返回 404。
  - 重复删除仍返回成功（幂等）。
  - 有活跃 Run 时，同一请求内取消并软删，删除响应不等待 Run 终态。
  - 该会话的通知不再出现在列表/未读里；其他会话不受影响。

## S-08 解绑入口后重绑，历史与产物保留

- **负责**：待 plan 分配
- **前置**：S-03/S-06 已完成；用户有历史会话与至少一个 Agent 产物；已知外部身份与入口。
- **步骤**：
  1. 管理员在 Console 移除该身份对某个入口的 grant（不删身份）。
  2. 用同一 `soc-token` 调 `/identity` 与旧会话详情。
  3. 管理员把同一入口重新授权给该身份。
  4. 再调 `/identity`、用户+Agent 会话列表、旧会话消息。
  5. 下载之前的产物。
  6. 新建一个会话并发送一条消息。
- **期望**：
  - 移除 grant 后该入口 `allowed=false`；外部身份与其他入口授权仍在。
  - 历史会话/产物没有删除；同一 user+Agent 仍按数据共享规则可访问（有可用入口/直接 ID）。
  - 重新授权后该入口 `allowed=true`；历史会话/产物可查看/下载。
  - 可以新建会话并正常对话。
  - 重绑到**不同**平台用户时，旧历史归原平台用户，新用户看不到（预期，不伪造迁移）。

## S-09 管理员编辑用户级外部身份

- **负责**：待 plan 分配
- **前置**：S-02 已完成；平台 `identity_keys` 已确定；用户有历史会话。
- **步骤**：
  1. 打开用户详情 → 外部身份，找到该身份，点击“编辑”。
  2. 保持 key 集合不变，修改其中一个 value（如多字段 `expert_id` 或 `tenant_id`）。
  3. 保存，刷新列表与 grants。
  4. 用新身份值对应的 JWT 调 `/identity`；用旧值对应的 JWT 调 `/identity`。
  5. 查看历史会话/产物。
  6. 再次编辑，尝试增加/删除 key。
- **期望**：
  - 编辑成功，列表显示新的身份 JSON；`platform_user` 与入口 grants 不变。
  - 新身份值可命中；旧身份值不再命中。
  - 历史会话、产物仍可查看/下载（仍归原平台用户）。
  - 修改 key 集合时提示 `IDENTITY_KEYS_MISMATCH`，不落库；平台 schema 固定。
  - 编辑成另一个用户已占用的身份 JSON 时提示 `IDENTITY_ALREADY_BOUND`，不覆盖。

  - resume 后产生预期副作用（如记忆保存）。

  - 重复/过期确认按稳定错误处理。

## S-11 同用户同 Agent 跨入口共享

- **负责**：待 plan 分配
- **前置**：U1 在 WebChat 和 MSSWWEB 都创建过同一 Agent 的会话；两个入口可用。
- **步骤**：
  1. 在 MSSWWEB 调用用户+Agent 会话列表。
  2. 通过同一用户+Agent 的列表接口（WebChat 侧）查看同一批会话。
  3. 在实际 WebChat 页面选择 MSSW 创建的会话，读取历史/发送新消息并上传文件；刷新该会话 URL 再重复。
  4. MSSW 反向打开 WebChat 创建的会话并续聊；观察列表中的创建来源。
  5. 切换到另一个 Agent，再切回；同时快速切换两个会话。
- **期望**：
  - 两个入口看到同一批会话，item 带 `entry_id`/`channel` 来源。
  - 同用户同 Agent 可继续对方创建的会话；entry/channel 不影响访问。
  - 不同 Agent 的会话不混入（按 `agent_id` 分开）。
  - 不因创建来源与当前入口不同而拒绝、跳回空会话或偷偷切入口；来源可不显示，但 API 的创建来源不被新消息覆盖。
  - 发消息/上传使用当前有权入口；晚到的列表/历史不会覆盖另一个 Agent/会话的页面。

## E-01 缺失/无效 `soc-token`

- **负责**：待 plan 分配
- **前置**：服务正常；准备一条签名被篡改的 token。
- **步骤**：
  1. 不携带 `soc-token` 调 `/api/v1/msswwweb/identity`。
  2. 携带篡改 token 调用。

- **期望**：

  - 响应/日志中不出现 token 原文、salt、公钥。

## E-02 未绑定用户

- **负责**：待 plan 分配
- **前置**：准备两种测试账号：A 的 JWT 身份没有用户级外部身份；B 已绑定用户级身份但没有入口 grant。
- **步骤**：
  1. 分别用 A、B 调 `/identity`、入口列表，尝试创建会话/发消息。
  2. 对 B 使用已知的、属于 B 且仍有 Agent 授权的旧会话 ID 读取历史并取消/删除。
- **期望**：
  - A 返回 allowed=false、UNBOUND，没有平台用户 ID；不能访问资源或清理别人的数据。
  - B 返回其原用户 ID、allowed=false、NO_ENTRY_GRANT；入口列表为空，不能在未授权入口新建/发送。
  - B 的旧数据仍归自己；Agent 授权有效时可按共享规则读取，用户有效时可清理；没有凭空删除用户身份或历史。

## E-03 Secret 未配置/损坏

- **负责**：待 plan 分配
- **前置**：先用有效 token 成功访问资源并打开 SSE，确认不是首次请求；随后按维护流程移除 Secret/键或改为非法 JSON。
- **步骤**：
  1. 重启 Console（模拟部署）。
  2. 观察 Console 是否正常启动、其他接口是否正常。
  3. 先用之前可用的 token 直接调资源并重开 SSE，再调 `/identity`。
  4. 打开 WebChat 页面并完成一次对话。
- **期望**：
  - Console 正常启动；`/readyz` 正常。
  - MSSWWEB 返回 503，错误码明确是“平台不可用”。
  - WebChat 正常，不受影响。
  - 日志只记录“平台未配置/损坏”，不打印因子。
  - 管理面平台状态显示 `configured=false`。
  - 预先访问过的资源也不可继续放行；平台不可用不要求用户退出业务平台登录。

## E-04 同用户跨入口共享 / 不同用户隔离

- **负责**：待 plan 分配
- **前置**：用户 U1 同时拥有 WebChat 与 MSSWWEB 的会话/Run/产物；另一个用户 U2 有同类资源。
- **步骤**：
  1. 用 U1 的 MSSWWEB token 读取 U1 在 WebChat 创建的 `conversation_id` 详情/消息。
  2. 用 U1 的 MSSWWEB token 继续/取消 U1 的 WebChat Run。
  3. 用 U1 的 MSSWWEB token 订阅 U1 的 WebChat SSE、下载 U1 的产物。
  4. 用 U1 的 token 访问 U2 的会话/Run/产物 ID。
  5. 反向用 U1 的 WebChat token 访问 U1 在 MSSWWEB 创建的同类资源。
- **期望**：
  - U1 同用户同 Agent 的跨入口资源可见/可操作；entry/channel 只显示来源。
  - U2 的资源一律 404/403，不泄露存在性。
  - 不产生跨用户副作用；同用户操作正常。
  - 通知：WebChat 可以看到 U1 的 MSSW 通知（用户级共享），看不到 U2 的。


## E-05 Agent 授权撤销

- **负责**：待 plan 分配
- **前置**：用户有外部身份与入口授权，且有 Agent 授权。
- **步骤**：
  1. 分别在 WebChat 和 MSSW 成功访问目标 Agent，保持登录，并准备另一个仍有权的 Agent。
  2. 管理员撤销目标 Agent 授权；成功响应后，不刷新身份也不重新登录，立即用两个入口请求旧会话/消息、发送、SSE、resume。
  3. 再查 `/identity` 与入口列表，并访问另一个有权 Agent。
  4. 删除/取消/已读旧数据。
- **期望**：
  - `/identity` 显示该入口 `allowed=false`，reason 为无授权/Agent 不可用。
  - `/entries` 不再返回该入口。
  - 读/发/SSE/resume 返回 403/404；删除/取消/已读仍可用。
  - 恢复授权后，下一次请求即恢复可见。
  - 两种认证方式都立即反映撤权；另一个 Agent 正常，WebChat 不要求重新登录。

## E-06 重复发送与重试

- **负责**：待 plan 分配
- **前置**：S-03 可复现。
- **步骤**：
  1. 用同一个 `Idempotency-Key` 和 `message_id` 连续发送两次。
  2. 第一次成功后，模拟网络超时重试一次。
- **期望**：
  - 只产生一个 Run/一条用户消息。
  - 第二次返回与第一次一致的受理结果，不重复执行。
  - 不同消息使用不同 key，互不影响。

## E-07 长流期间 Agent 撤权/用户停用

- **负责**：待 plan 分配
- **前置**：SSE 正在输出。
- **步骤**：
  1. 打开一个长回答的 SSE。
  2. 管理员撤销该用户对目标 Agent 的授权（或停用用户）。
  3. 等待下一个复核周期。
  4. 另开一条流，只解绑一个入口 grant，不改 Agent 授权。
- **期望**：
  - Agent 撤权/用户停用后，SSE 在复核边界内结束，不继续输出。
  - 后续读/发/SSE/resume 被拒绝；仅 Agent 撤权且用户仍有效时，删除/取消/已读可用于清理。用户停用后不保留这些例外。
  - 仅解绑入口 grant 且 Agent 授权仍在时，已开流不因 entry 变化而中断（entry 不是授权边界）。
  - 连接状态明确，不把 SSE 结束显示成 Run 完成；已受理执行是否停止取决于现有取消操作，不把撤权当作副作用回滚承诺。

## E-08 BFF 断线重连

- **负责**：待 plan 分配
- **前置**：准备能产生多片正文快照的测试会话，以及一个正常增量流；BFF 能保存应用状态与恢复游标。
- **步骤**：
  1. 完整显示普通事件，保存最后完整应用的 seq；开始接收同一 seq 的多片快照。
  2. 故意在快照只收到部分片时断开，保留上一完整 seq，不使用半组的 id。
  3. 带上一完整 seq 的 `Last-Event-ID` 或 `after_seq` 重连，收齐快照后原子替换正文。
  4. 重复一次帧重放；另测未收到终态时网络直接结束，以及游标过期/超前后的历史恢复。
- **期望**：
  - 从断点继续，不重复、不丢正文。
  - 游标过期/超前时返回明确错误，不静默夹取。
  - BFF 不缓冲时首帧/心跳及时到达。
  - 半组快照不覆盖完整正文、不推进游标；重复片不重复追加，旧 generation 不覆盖新答案。
  - 普通 EOF 不显示完成；历史恢复后的正文不会与重放片段重复拼接。

## E-10 Redis 缓存 revision 失效/不可用

## E-12 撤权与旧请求并发

- **负责**：后端/测试，Task 阶段明确执行人
- **目标**：管理端已确认撤权后，早先延迟的请求不能重新获得旧权限。
- **前置**：测试环境可通过代理延迟响应；同一用户持有两个有效凭证。
- **步骤**：
  1. 暂时延迟一次身份解析响应，使它在撤权前开始、撤权后才返回。
  2. 在管理页面解除入口绑定或撤销 Agent 授权，等到状态已确认。
  3. 释放延迟响应，用两个凭证直接请求原受保护资源，期间不刷新登录。
- **期望**：旧响应不能恢复授权；后续请求与管理页面一致；不出现一会儿拒绝、一会儿恢复的情况。

## E-13 同步中断与重启恢复

- **负责**：后端/运维/测试，Task 阶段明确执行人
- **目标**：变更遇故障不会假报成功或恢复旧权限。
- **前置**：隔离环境支持在授权变更同步期间中断 Redis/Console，且有已登录的 WebChat、MSSW 客户端。
- **步骤**：
  1. 提交撤权，在测试环境分别中断“业务提交前”和“业务已提交后”的同步流程。
  2. 查看管理端结果并请求受保护资源；对超时请求刷新实际资源与同步状态。
  3. 恢复依赖/重启服务，等待管理端状态明确后重试原目标动作。
- **期望**：未提交的变更不称为成功；已提交但未同步明确提示待恢复；不确定期间不放行旧权限。恢复后与实际授权一致，重复操作不产生重复授权/审计，其他用户只在声明的短暂同步窗口受影响。

## E-14 配置变化与普通重启的区别

- **负责**：运维/后端/测试，Task 阶段明确执行人
- **目标**：确认服务重启不会掩盖旧配置缓存问题。
- **前置**：已有成功访问资源的旧 token；平台有多个 Console 副本；Redis 保持运行。
- **步骤**：
  1. 不改配置重启 Console/Gateway，使用同一 token 访问资源。
  2. 按维护流程修改有效期策略或验签配置，只启动一部分新 Console；尝试激活并请求资源。
  3. 全部副本配置一致后开放平台；再用原来不符合新策略的 token 直接访问资源。
- **期望**：同配置重启继续有效；配置不一致时不开放该平台，不影响正常 WebChat；新策略开放后，旧缓存不能继续放行不符合策略的 token，不靠等待 TTL 或用户刷新身份。

## B-05 通知序号与消息序号不同

- **负责**：后端/前端/BFF 联调，Task 阶段明确执行人
- **目标**：标读不误清并发到达的新通知。
- **前置**：同用户多个会话各有通知，使通知序号与目标会话消息序号明显不同。
- **步骤**：
  1. 取目标会话详情，记录 C=`last_seq`、N=`notification_through_seq`。
  2. 取 C 范围历史并展示；让另一轮执行在详情返回后完成，产生新通知。
  3. 提交 read，body 使用 N；查询会话列表，并重复同一 read。
  4. 分别让 Run 等待确认、Task 返回结果，再走详情/历史/展示/标读流程；最后提交一个超出当前通知水位的值。
- **期望**：N 内通知已读，新到通知仍有红点；重复标读不误清新通知；三类提醒都能通过实际页面状态被看见再标读；超前水位被明确拒绝；列表的 has_unread 或 SSE id 不被当成通知水位。

## B-06 未知来源与迁移尾差

- **负责**：运维/后端/前端，Task 阶段明确执行人
- **目标**：旧数据来源如实保留，共享访问与新写入正确。
- **前置**：迁移样本含可核实来源、无法核实来源、初次回填后由旧服务新建的会话。
- **步骤**：
  1. 按发布流程停旧写入、核对并回填尾差，启动新版本。
  2. 在共享列表和 URL 中打开上述会话；从当前有权入口续聊。
  3. 创建新会话，再由另一个入口续聊，观察历史、通知与产物。
- **期望**：可核实来源正确；未知来源不被冒充为 WebChat，仍可在授权范围内读取和续聊；旧会话来源不被续聊改写；新会话有真实来源，通知/产物可正常访问；迁移后新写入缺来源会明确阻止发布。

## 场景编写约定

- 一个场景只验证一个用户可理解的目标。
- 步骤编号从 1 开始，按真实操作顺序编写。
- 期望写“用户看到什么/数据变成什么”，不写内部函数名或测试断言。
- 场景不生成 manifest、不登记执行结果、不阻断 `task finish` 或 `task archive`。
- 需要机器执行的快速回归放在 Task 的 `### Tests`；E2E 和全量回归留在 CI。
