# ASYNC Skill 后台执行与结果投递 验收场景

> **文档版本**: v1.1（2026-11-18，对齐 v0.5 设计：复用任务中心/执行详情，后台详情走查询参数）
> 给**人工测试者**使用；不是 E2E 代码或测试注册表。
> 场景编号供 design 与 Task 的 `Scenarios` 字段引用。
> 步骤用用户能执行的动作描述，期望写用户可观察的结果。

**公共前置**

- 已有一个 ASYNC（长耗时）技能，可在 WebChat 会话里被调用；另有一个**必定失败**的变体（例如调用不存在的接口，或脚本里主动抛异常）。
- WebChat 前端可用、账号可登录；企微通道已配置一个测试机器人（S-04 需要）。
- Worker 与 Runtime 均为本设计版本。
- **产物依赖**：S-02/S-06 的「产物」步骤依赖统一文件产物投递能力（Worker 输出登记 + `OUTPUT`）。若该能力尚未合入，只验结果文本与任务记录，产物步骤标记为依赖项，不把缺失当成本需求失败。

## S-01 提交后台任务后会话不被长期占用

- **负责**：TASK-001
- **前置**：公共前置；准备一个执行 30 秒以上的 ASYNC 技能。
- **步骤**：
  1. 在 WebChat 里让 Agent 调用该长耗时技能。
  2. 看到「已提交 / 后台执行中」类回执后，**等本轮助手回复结束**，再发一条普通消息（例如「现在几点了」）。
  3. 等 30 秒以上，切到任务中心 →「后台任务」分组，找到该任务。
- **期望**：
  - 第 2 步的新消息被正常受理并得到回复，不出现「当前会话有任务执行中」一类拒绝；后台任务不再造成长时间等待。
  - 会话时间线里不出现长时间「等待工具结果」的挂起状态。
  - 任务中心「后台任务」分组能看到该任务；任务完成后结果可取。
  - 若 WebChat 产生未读通知，它只提示有结果，不代表聊天里被塞进了任务结果消息。

**实际结果**：待执行

## S-02 成功结果在任务中心可取，并进入下一轮上下文

- **负责**：TASK-002
- **前置**：公共前置；产物步骤需要统一 Artifact 已合入。
- **步骤**：
  1. 让 Agent 调用一个会成功的 ASYNC 技能（例如导出一份周报）。
  2. 等任务完成后，切到 WebChat 的「任务」页 → **后台任务**分组，找到该任务并打开详情。
  3. 查看结果文本与产物，下载产物。
  4. 回到原来的会话，追问「刚才那个任务的结果是什么」。
- **期望**：
  - 任务出现在「后台任务」分组（不是「定时任务」分组），状态是已完成。
  - 详情里能看到结果文本；有产物时能列出并下载成功（依赖统一 Artifact）。
  - 聊天对话框里**没有**被塞进一条任务结果消息。
  - 追问时 Agent 能直接引用该结果，不需要重新执行任务。
  - 刷新任务详情后，列表/结果不重复、不漂移。

**实际结果**：待执行

## S-03 失败原因原样可见（任务中心与模型都能读到）

- **负责**：TASK-002
- **前置**：准备一个必定失败的 ASYNC 技能（如调用不存在的接口，或脚本中抛异常）。
- **步骤**：
  1. 让 Agent 调用该技能。
  2. 等任务失败后，在任务中心「后台任务」分组打开该任务详情。
  3. 查看失败正文；随后回到会话追问「刚才那个任务为什么失败，具体是哪个接口」。
- **期望**：
  - 失败正文里能看到**原始的接口错误或 traceback 原文**（接口地址、状态码/报错信息、异常堆栈中的关键行），而不是「external side effect cannot be confirmed」「attempts exhausted」这类通用文案。
  - 任务状态显示为失败（不是「已完成」）。
  - 追问时 Agent 能引用同一份原文指出失败位置，不需要重新执行。
  - 若正文被脱敏或截断，能看到明确的截断提示，而不是静默少一截。

**实际结果**：待执行

## S-04 企微会话收到同一份结果正文

- **负责**：TASK-003
- **前置**：企微测试机器人已绑定且能收消息。
- **步骤**：
  1. 在企微会话里让 Agent 调用一个 ASYNC 技能（先成功一次、再失败一次）。
  2. 等待推送到达。
- **期望**：
  - 成功时收到任务完成正文（结果摘要或附件提示）。
  - 失败时收到的正文包含原始错误原文，与网页侧结论一致。
  - 同一个任务不会收到两条重复结果。
  - 后台任务完成不会额外触发一条「Run 完成」重复结果。

## S-05 任务中心两个分组互不混淆

- **负责**：TASK-003
- **前置**：至少有一个定时任务和一个立即提交的后台任务。
- **步骤**：
  1. 切到 WebChat 的「任务」页。
  2. 分别在「定时任务」与「后台任务」两个分组里查看列表。
  3. 各打开一条详情，切换回另一个分组，再用深链打开某条后台任务详情（地址形如 `/chat/tasks?view=background&taskId=<任务标识>`）。
  4. 用深链打开某条定时任务详情（地址形如 `/chat/tasks/<定时任务标识>`），刷新页面。
- **期望**：
  - 两个分组的列表互不混排：定时任务只出现在定时分组，立即提交的后台任务只出现在后台分组。
  - 两个分组的详情都能显示各自的结果文本与产物；定时任务原有的操作（启停、执行历史）不受影响。
  - 刷新页面或重新进入后，分组、深链目标与列表内容一致；`taskId` 查询不会覆盖 `/chat/tasks/<定时任务标识>`。
  - 没有新增「投递管理」页面或入口。

**实际结果**：待执行

## S-06 批量任务能定位到具体失败项

- **负责**：TASK-003
- **前置**：准备一个批量导出任务（例如 5 个客户 A~E），其中 1~2 个客户的接口会失败；聚合方式为「全部成功才算成功」。
- **步骤**：
  1. 在会话里让 Agent 提交该批量任务。
  2. 等待任务结束，在任务中心「后台任务」分组打开该任务详情。
  3. 查看子任务表，找到失败的那几行，点开其中一行看完整错误。
  4. 查看产物列表：成功项的产物是否都在（依赖统一 Artifact）。
- **期望**：
  - 父任务显示为失败，并给出「5 项中 2 项失败」之类的计数。
  - 子任务表能看出**具体是哪几项失败**：行标签是可辨认的客户/条目，不是一串哈希。
  - 失败行有错误摘要；点开失败子任务能看到完整错误原文（哪个接口、什么报错）。
  - 成功项的产物在产物列表里可下载；产物总数与截断提示一致。

**实际结果**：待执行

## S-07 部分失败（尽力而为模式）不被误判为全部成功

- **负责**：TASK-003
- **前置**：批量任务的聚合方式为「尽力而为」（部分失败仍算完成）。
- **步骤**：
  1. 提交一个 5 项、其中 1 项会失败的批量任务。
  2. 任务结束后查看列表与详情。
- **期望**：
  - 父任务状态是「已完成」，但列表与详情都明确显示「5 项中 1 项失败」的计数。
  - 子任务表里那 1 项显示为失败且能看到错误摘要。
  - 计数与子任务表一致，不出现「徽标说有失败、表里找不到」或反之。

**实际结果**：待执行

## E-01 提交未获受理时明确失败

- **步骤**：

  - 不把「提交未确认」伪装成「已完成」。

## E-02 结果投递失败可重试且不丢事实

- **负责**：TASK-003
- **前置**：可模拟投递目标不可达（如停掉网关或断开企微通道）。
- **步骤**：
  1. 在投递不可用期间让任务完成。
  2. 恢复通道后观察投递。
  3. 在任务中心查看该任务。
- **期望**：
  - 投递按既有重试策略重试，最终送达或落到明确的失败终态并在任务详情可见。
  - 任务本身的结果不因投递失败而丢失，任务中心仍可读。
  - 恢复后同一任务不会出现两条结果。

**实际结果**：待执行

## E-03 撤销 Agent 授权后后台任务不可见

- **负责**：TASK-003
- **前置**：用户拥有两个 Agent，其中一个有已完成后台任务；可撤销该 Agent 授权。
- **步骤**：
  1. 撤销该 Agent 的授权。
  2. 重新进入任务中心，尝试通过旧深链打开该后台任务详情与产物。
  3. 切换回仍有授权的 Agent 查看列表。
- **期望**：
  - 被撤销 Agent 的后台任务不再出现在列表中。
  - 旧深链与产物下载显示「不存在/无权访问」，不泄露结果、错误原文或文件名。
  - 仍有授权的 Agent 任务正常可见。

**实际结果**：待执行

## E-04 长错误/大结果不会让任务一直显示运行中

- **负责**：TASK-002
- **前置**：准备一个 stderr 很长、或结果 JSON 很大的失败/成功变体。
- **步骤**：
  1. 触发该任务，等待结束。
  2. 在任务中心查看状态、失败正文/结果与产物。
  3. 回到会话追问结果。
- **期望**：
  - 任务进入明确的完成/失败终态，不会长期停在「运行中」。
  - 任务中心能看到脱敏后的错误原文或结果；截断处有提示。
  - 模型下一轮能看到有界的结果/错误，不需要重新执行。
  - 不出现「结果违反协议」「external side effect cannot be confirmed」把原始错误覆盖掉。

**实际结果**：待执行

## B-01 超长错误正文按上限截断

- **负责**：TASK-002
- **前置**：让失败技能的 stderr 显著超过上限（例如循环打印堆栈）。
- **步骤**：
  1. 触发执行并等待失败。
  2. 查看任务中心详情、会话下一轮上下文、外部通道正文（如有）。
  3. 检索服务日志中的截断记录。
- **期望**：
  - 任务中心保留较完整的脱敏原文；外部/模型侧按各自上限截断，仍是原始内容的前缀，不出现通用替换文案。
  - 截断处有明确提示；服务日志能检索到截断发生的事实（不记录正文）。
  - 任务状态与结果不被截断影响。

**实际结果**：待执行

## B-02 迟到结果仍进入会话事实

- **负责**：TASK-002
- **前置**：任务执行时间长于会话轮次的自然收尾（如 Run 已结束）。
- **步骤**：
  1. 提交长任务后不再发消息，等待 Run 收尾。
  2. 任务完成后再回到该会话追问。
  3. 在任务中心查看该任务。
- **期望**：
  - 结果仍出现在任务中心，且 Agent 追问时能读到。
  - Run 不会因为迟到结果被复活或重新执行。
  - 不会因为 Run 已结束而丢弃结果；同一结果不会重复出现。

**实际结果**：待执行

## B-03 停止当前会话不取消已提交的后台任务

- **负责**：TASK-001
- **前置**：已提交一个长耗时后台任务。
- **步骤**：
  1. 提交任务后停止当前会话（如点击停止）。
  2. 等待后台任务结束。
  3. 查看任务中心与投递结果。
- **期望**：
  - 当前会话停止；已提交的后台任务继续执行（本期边界）。
  - 任务中心仍能看到该任务与最终结果；投递按既有策略进行。
  - 不出现「停止后任务被静默取消但状态仍显示运行中」的矛盾。

## 场景编写约定

- 一个场景只验证一个用户可理解的目标。
- 步骤从 1 开始，按真实操作顺序。
- 期望写「用户看到什么 / 数据变成什么」，不写内部函数名。
- 产物步骤必须标注统一 Artifact 依赖，不把依赖缺失当成本需求失败。
- 场景不生成 manifest、不登记结果、不阻断 `task finish` 或 `task archive`。
- 机器执行的快速回归放 Task 的 `### Tests`；E2E 与全量回归留在 CI。
