# 执行失败收尾与定时任务执行模型 人工验收场景

> **文档版本**: v0.5
> **创建日期**: 2026-11-18
> **需求**: `run-failure-reporting.prd.md` v0.6
> **设计**: `run-failure-reporting.design.md` v0.5

**使用约定**:

- 场景是人工验收资产，不是自动化清单；不记录 selector、内部 API 路径或实现细节。
- 每个场景写清目标、前置、人工步骤、可观察结果和负责人。
- 真实边界：真实构建产物、真实 PostgreSQL/Redis、真实 Runtime/Worker；外部平台使用现有测试探针或可复现的失败注入。
- 未满足环境时记录缺失项与 owner，不把环境缺失伪装成产品失败。
- 自动化回归覆盖在 `design.md` 第 8 章；本文件只描述用户/排障人员可观察的结果。

## S-01 工具层全 OK、内容层失败、轮次耗尽

**目标**: 平台不再把“工具层全 OK”写成“没有失败/仅预算耗尽”，而是分别交代终止原因、工具结果和业务失败证据。

**前置**:
- 一个会返回内容层失败的 Skill（或可注入的等价探针）：调用本身成功，但执行结果 `status=FAILED`/非零退出，或结构化业务错误；
- 允许 Agent 继续排查，直到轮次预算耗尽。

**步骤**:
1. 在 WebChat 触发该 Skill。
2. 等待 Run 终止。
3. 查看收尾消息。
4. 打开运行详情/审计导出。

**预期**:
- 收尾消息包含：终止原因（轮次预算 20/20）、工具用量、业务失败证据（工具名、status/退出码、平台返回摘要）、证据采集状态、完成情况。
- 不出现“没有任何工具调用记录/没有收到失败信息/仅预算耗尽”这类与事实不符的结论。
- 审计包能读到同一条业务失败，不要求用户贴报错。

**负责人**: 后端 + 前端

## S-02 确定性 Skill 失败首次停止

**目标**: 鉴权/凭据/明确业务失败第一次即停止，不再烧 16 轮。

**前置**:
- 一个返回 `PLATFORM_AUTH_REJECTED` 或等价确定性错误的 Skill/探针；
- 配置允许的第 1 次调用。

**步骤**:
1. 在 WebChat 触发该 Skill。
2. 观察 Run 是否在第一次失败后停止。
3. 查看收尾消息和运行详情。

**预期**:
- 不再继续手工排查；Run 以失败收尾。
- 收尾消息指出失败工具、错误码、平台原文摘要。
- 审计中该工具 `business_status=FAILED`、`failure_layer=CONTENT`，不再只有 transport `OK`。

**负责人**: 后端

## S-03 瞬时失败有界重试

**目标**: 5xx/429/网络等瞬时失败按冻结策略有界重试，不被误判为“第一次即停”。

**前置**:
- 可注入 5xx/429/网络错误的探针；
- 探针在失败 stderr 中输出 `code/retryable` 结构化信封；
- 冻结的 `max_identical_failures` 策略。

**步骤**:
1. 触发一个会瞬时失败、随后可恢复的 Skill/探针。
2. 观察重试次数与最终结果。
3. 重复一次持续瞬时失败的场景。
4. 另起一次非零退出但未提供 `retryable` 的 Skill，观察是否按确定性停止。

**预期**:
- 明确标记 `retryable=true` 的失败按冻结策略重试，第一次不会立即终止。
- 持续失败达到阈值后停止，收尾消息说明“重试达到上限/最后失败证据”。
- 未提供 `retryable` 的非零退出按确定性处理，事实中标注 retryability unknown。
- 不会把成功恢复后的历史失败误报为本次停止原因。

**负责人**: 后端

## S-04 工具预算耗尽与 Deadline

**目标**: 工具预算/硬超时也有确定性收尾，不出现空正文或把未执行调用算成失败。

**前置**:
- 可配置较小的工具预算或 deadline；
- 一个会发起多次工具调用的任务。

**步骤**:
1. 触发任务直到工具预算耗尽。
2. 查看收尾消息。
3. 另起一次到 deadline 的任务，查看收尾消息。
4. 另起一次模型错误/空回复的任务，查看收尾消息。
5. 查看运行详情中的 pending 调用。

**预期**:
- 各出口都有明确的终止原因与用量，不出现空白收尾。
- model 错误/空回复使用现有错误码 + 平台事实，不伪造工具失败。
- 未执行工具调用只显示为 pending/未执行，不计入失败数。
- 不要求用户贴报错。

**负责人**: 后端

## S-05 用户取消

**目标**: 取消是“用户停止”，不编造业务失败，也不把取消算作工具失败。

**前置**:
- 一个可长时间运行的任务。

**步骤**:
1. 触发任务。
2. 在运行中点击停止并确认。
3. 查看收尾消息和运行详情。

**预期**:
- 收尾明确说明已停止/取消。
- 不出现“工具执行失败”或外部平台错误等伪造原因。
- 已提交的后台任务按既有语义独立处理，不被取消文案误伤。

**负责人**: 后端 + 前端

## S-06 长回合压缩后收尾

**目标**: 单回合内多次压缩（含消息条数兜底）后，收尾仍能看到失败证据，不会被裁成“只有 Skill 列表”。

**前置**:
- 一个会产生大量工具结果/长回合的任务；
- 配置可触发 2-3 次压缩的消息预算。

**步骤**:
1. 触发任务，制造早期失败和后续长历史。
2. 等待轮次/预算终止。
3. 查看收尾消息。
4. 在审计包中查看压缩事件与失败证据。

**预期**:
- 收尾消息仍包含早期失败证据/事实块；事实来自审计/终止快照，不依赖压缩后的模型上下文。
- 失败收尾不追加 USER 指令、不调用收尾模型，不会出现“只剩系统提示+收尾指令”的请求。
- 正常模型回合的工具消息按完整调用组保留，不出现孤儿 tool 结果。
- 压缩失败时回退原历史，Run 不因压缩失败而失败。

**负责人**: 后端

## S-07 恢复后的收尾

**目标**: Run 经过等待/恢复后，收尾事实仍可重建，不依赖进程内存。

**前置**:
- 一个会产生等待/恢复的 Run（工具等待或人工确认）；
- 恢复前已有工具结果/失败证据。

**步骤**:
1. 触发 Run 进入等待。
2. 恢复 Run，并让它因失败/预算终止。
3. 查看收尾消息与审计包。

**预期**:
- 收尾事实与首次执行一致：终止原因、用量、最后失败证据可读。
- 不出现重复事件、重复失败计数或丢失历史失败。
- 无法确认交付物时明确写“完成情况无法确认”。

**负责人**: 后端

## S-08 模型此前编造或空回复

**目标**: 模型在失败前说“报告已生成”或输出为空时，平台事实仍然正确收口。

**前置**:
- 可注入模型编造/空回复的测试探针；
- 一个已失败的任务。

**步骤**:
1. 触发任务，让模型在失败前输出“报告已生成”或空回复。
2. 让 Run 因业务失败/预算终止。
3. 查看用户收到的收尾消息。

**预期**:
- 失败收尾由平台直出，不再调用模型；模型此前的矛盾内容不会进入收尾结论。
- 事实块至少包含终止原因、用量、失败证据/证据状态、完成状态。
- 不出现空气泡；用户不会被要求去贴平台已经掌握的错误。

**负责人**: 后端

## S-09 成功执行但输出含疑似失败

**目标**: 平台不把 stdout/stderr 里的 4xx/5xx 文本当成失败判决，同时不丢失这条证据。

**前置**:
- 一个执行成功但输出包含 500/401 等疑似失败文本的探针（例如诊断命令读取含 500 的日志，或 exit 0 的 skill 打印上游错误）；
- 一个真实的 confirmed 失败对照。

**步骤**:
1. 触发该探针，确认工具执行成功。
2. 查看收尾消息/运行详情。
3. 导出审计包，查看 `failures.csv`、`calls.csv` 与 `report.json` 的 `failure_evidence`。
4. 与一个 confirmed 内容层失败的 Run 对照。

**预期**:
- 不把 Run 判失败，也不写成“确认无失败”；证据状态为 `UNKNOWN` 或 `NOT_OBSERVED`。
- 收尾写“执行成功，但输出出现疑似失败信号；完成情况无法确认”或等价表达。
- `failures.csv` 不列该调用；`calls.csv`/`report.json` 能看到脱敏后的 `evidence_preview`。
- confirmed 失败仍正常进入 `failures.csv`/`failure_evidence`。
- 输出被截断时显示 `output_truncated`，并说明证据可能不完整。

**负责人**: 后端

## S-10 诊断命令非零退出不触发止损

**目标**: `workspace_shell`/`skill_draft_shell` 的非零退出只作结果证据，不把正常诊断命令当成内容层失败。

**前置**:
- 一个可用 `workspace_shell` 的 Run；
- 诊断命令会正常退出 1（如 `grep` 无匹配、`test` 条件不成立）。

**步骤**:
1. 触发 `workspace_shell` 执行一个退出 1 的诊断命令。
2. 观察 Run 是否继续，而不是立即失败。
3. 查看收尾消息/审计中的 `exit_code`、`business_status`、`failure_layer`。
4. 随后触发一次真实的 `target=skill` 内容层失败，确认仍能正常止损。

**预期**:
- 诊断命令退出 1 不会触发 `no_progress`/Run 失败；模型可以继续调整命令。
- 审计记录 `exit_code=1`，但 `business_status=NOT_APPLICABLE`、`failure_layer=NONE`。
- 真实 `target=skill` 内容层失败仍按契约进入失败跟踪和收尾。
- 收尾不会把诊断命令的非零退出误报为 decisive failure。

**负责人**: 后端

## E-01 审计导出可复盘内容层失败

**目标**: 排障人员从链路分析包直接读到内容层失败，不依赖 grep 日志。

**前置**:
- 已产生一次含内容层失败的 Run；
- 导出包开启 timeline 截断。

**步骤**:
1. 从 Console 导出该 Run 的链路分析包。
2. 打开 `report.md`、`failures.csv`、`calls.csv`。
3. 对照 `report.json` 的 `failure_evidence` 与 timeline。

**预期**:
- `report.md` 给出终止原因、用量、最后失败、完成状态。
- `failures.csv` 能区分工具层/内容层失败，只列 confirmed 失败。
- `calls.csv` 能看到工具业务状态/退出码/截断标记/证据预览，不再全是 transport `OK`。
- `execution_diagnosis` 能发现 `status=OK + business_status=FAILED` 的内容层失败。
- timeline 截断时，首个失败、最后失败、所有 confirmed 失败调用与收尾事实仍保留。
- “数据完整”和“导出截断”分开表达，不产生矛盾文案。

**负责人**: 后端 + 前端

## E-02 没有交付物依据

**目标**: 平台不根据工具日志猜测“完成/未完成”。

**前置**:
- 一个没有显式输出契约/交付物声明的普通 Run；
- 该 Run 因失败或预算终止。

**步骤**:
1. 触发 Run 并让它终止。
2. 查看收尾消息与审计包。

**预期**:
- 收尾明确写“完成情况无法确认”或等价表达。
- 不出现“报告已生成”“全部完成”等无依据结论。
- 有显式输出契约时，才列出未完成交付物。

**负责人**: 后端

## S-11 用户不选模式：agent 推断并给出业务卡片

**目标**: 用户只描述业务意图，不需要理解 SKILL/AGENTIC；agent 推断 payload 并展示计划。

**前置**:
- 本地回归 Skill 或 `daily-duty-report-mssp` 已可用；
- 平台设置可读。

**步骤**:
1. 用户说：“每天 9 点给客户 22921947 出昨天的值守日报。”
2. 查看 agent 生成的卡片。
3. 检查卡片上的执行方式、参数、时间、预算来源。

**预期**:
- 卡片不使用“SKILL/AGENTIC”让用户选；用业务语言说明“直接调用 Skill、不消耗模型”。
- 展示 `company_id=22921947`、`date=previous_day`、`Asia/Shanghai`、`09:00`。
- 如果信息不足，agent 问业务问题（“客户固定还是每次判断？”），不暴露 mode 下拉。

**负责人**: 后端 + 前端

## S-12 真实试跑：创建前看到真实输出

**目标**: 创建定时任务前先真实执行一次，用户看到真实报告/文件。

**前置**:
- S-11 的计划已生成；
- 投递路由可用。

**步骤**:
1. 在卡片上点击“试跑”。
2. 等待真实执行完成。
3. 查看会话/任务记录中的真实输出与文件。

**预期**:
- 试跑走真实 Skill/Agent、真实产物、真实投递，不是渲染预览。
- 成功后才允许创建 Job；失败时不创建，展示失败事实与修复建议。
- 试跑产物与正式运行的产物走同一套 Artifact/Delivery 链路。

**负责人**: 后端 + 前端

## S-13 从成功对话提升为定时任务

**目标**: 复用一次已成功的对话调用，不重新猜意图。

**前置**:
- 用户已在对话中成功执行 `daily-duty-report-mssp`；
- 该 Run 有 `execute(target=skill)` 的真实调用。

**步骤**:
1. 用户说：“把这个做成每天 9 点。”
2. Agent 读取该成功调用的 skill/input/argv。
3. 把日期绑定为 `{{previous_day}}`，生成 Job 计划。
4. 试跑 → 确认 → 创建。

**预期**:
- 复用真实 `skill_key`/`input`/`argv`/platform，不重新猜。
- 卡片展示“基于 2026-11-18 那次成功执行”。
- 试跑成功后才创建；失败不创建。

**负责人**: 后端 + 前端

## S-14 开放性任务走 AGENT_TURN

**目标**: 需要判断/查询的任务使用完整 prompt 模式，而不是被裁剪的 AGENTIC。

**前置**:
- 任务：“每天 9 点汇总昨天的定时任务执行，按失败原因分类。”
- `list_tasks`/`get_task` 等平台只读工具可注册。

**步骤**:
1. 创建任务，查看卡片：payload=AGENT_TURN、工具策略、时间窗口。
2. 触发执行，查看 prompt 中的时间/窗口/无人值守契约。
3. 查看工具调用与结果。

**预期**:
- 卡片说明“每次触发由 Agent 判断并调用工具”。
- prompt 含 `previous_day`/`window`，不向用户问日期。
- 工具面完整：任务查询、`current_time`、必要的 Skill/MCP。
- 结果可按 `record_result(no_change)` 静默；有附件时照常交付，用户可见文本必须直白。

**负责人**: 后端

## S-15 意图不确定：问业务问题而不是选模式

**目标**: 低置信度时不让用户选 mode，而是问业务问题或先试跑。

**前置**:
- 一个模糊请求：“每天给我看看客户情况。”

**步骤**:
1. 提交模糊请求。
2. 查看 agent 的澄清问题。
3. 提供业务信息后查看卡片。

**预期**:
- 问题形如“客户是固定的，还是每次判断？”或“要看哪个平台/哪些指标？”
- 不出现“请选择 SKILL/AGENTIC”。
- 仍不确定时，agent 提议先试跑一次，再根据真实结果生成计划。

**负责人**: 后端 + 前端

## S-16 SKILL_PLAN 的 argv/input/时间窗口

**目标**: 固定 Skill 任务不消耗模型，参数由平台冻结。

**前置**:
- 本地回归 Skill 或 `daily-duty-report-mssp`；
- `argv_template`/`input` 可编译。

**步骤**:
1. 创建 SKILL_PLAN 任务。
2. 触发执行，查看脚本收到的 argv 与 stdin。
3. 人为重试一次，查看 argv/input 是否一致。

**预期**:
- argv 按模板渲染并冻结；stdin 只含业务 input（不含 mode/skill_id/context）。
- 重试复用同一 argv/input；日期窗口不变。
- 不出现 `required: --company-id`。

**负责人**: 后端

## S-17 静默结果与文件产物

**目标**: 无变化时不刷屏；有文件时仍交付。

**前置**:
- 一个可能无变化的 AGENT_TURN 任务；
- 平台文件工具可用。

**步骤**:
1. 触发一次“无变化”的执行。
2. 触发一次有文件产物的执行。
3. 查看会话/任务记录/通知。

**预期**:
- 无变化时 `record_result(no_change)`，平台抑制文本消息；任务中心记录“本次无变化”。
- 有文件时文件按 delivery 策略交付，不受文本静默影响；Web 任务中心可见，企微 push 按配置发送。
- 用户可见文本必须是直白语言；不出现 `NO_REPLY`、内部错误码或 token。
- 上次 meaningful result 不因静默被覆盖。

**负责人**: 后端

## S-18 预算与工具策略来自平台设置

**目标**: 模型不再自拟预算；工具策略可收紧但不越权。

**前置**:
- 平台设置中 `agent.max_turns`/`agent.max_tool_calls`/`agent.deadline_ms` 可改；
- 一个 AGENT_TURN 任务。

**步骤**:
1. 修改平台设置。
2. 新建/更新任务，查看卡片预算与来源。
3. 触发执行，查看快照。
4. 收窄 `tools_allow` 后再次触发。

**预期**:
