# 平台登录态逐平台返回 验收场景

在真实构建产物、真实服务和真实浏览器会话中执行。列 session 使用增强后的现有 `session-manager list-platforms`，不增加查询命令。主要观察用户第一次收到的回复；只看 CLI 或工具原文有字段不算通过。场景是人工验收资产，不生成 E2E 代码，不阻断 task finish / task archive。

## S-01 查询两个正常平台

- **负责**：待 TASK 拆分
- **目标**：一次问询即可知道查询范围内的平台都可用。
- **前置**：当前用户可见 MSSP、MSSW，两个平台凭据均正常。
- **步骤**：
  1. 打开新会话，发送“可以列一下 MSSP、MSSW 的平台 session 吗”。
  2. 查看第一次回复和本次工具结果。
- **期望**：
  - 两个平台分别列出，均说明登录态可用；有有效期时可展示有效期。
  - `list-platforms` 继续返回平台 `key`、`name`、`authentication` 和 `version: 2`；`available` 表示实际检查结果。
  - 查询未被当作业务执行失败，不需要再次追问。
  - 不显示 Cookie、CSRF 或凭据值。

## S-02 查询一个正常、一个认证失败的平台

- **负责**：待 TASK 拆分
- **目标**：复现“列一下平台 session”后还需追问“都失败了吗”的原问题，并确认修复。
- **前置**：MSSP 正常；MSSW 有凭据但被平台拒绝认证。
- **步骤**：
  1. 在新会话发送“可以列一下 MSSP、MSSW 的平台 session 吗”。
  2. 只查看第一次回复，确认是否能判断每个平台的情况。
  3. 在另一新会话改为“列一下 MSSW、MSSP 的平台 session”，再次查看第一次回复。
- **期望**：
  - 两种次序都说明 MSSP 可用、MSSW 获取失败及实际原因。
  - MSSW 先失败时，MSSP 仍得到检查；成功结果不会被失败结果覆盖。
  - `list-platforms` 完成检查后返回报告并成功退出（单个平台失败不改变命令成功）；回复不只有 `platform session unavailable` 或运行终止摘要。
  - 不需要追问“都失败了吗”，不展示任何敏感值。
  - 普通 AUTO 执行下，`list-platforms` 直接返回每个平台实际 `available` 与失败原因；命令执行前即失败的原调用另按 B-05 验证。

## S-03 Skill 只依赖正常平台

- **负责**：待 TASK 拆分
- **目标**：无关平台的故障不影响当前 Skill，且模型不因旧说明先做全平台登录。
- **前置**：MSSP 正常、MSSW 认证失败；一个只声明依赖 MSSP、原本可正常执行的 Skill。
- **步骤**：
  1. 让 Agent 执行该 Skill。
  2. 查看本次工具调用（确认没有先跑 `list-platforms`）、业务结果和现有执行记录。
- **期望**：
  - Skill 按原流程取得 MSSP 登录态并完成业务。
  - 不要求 MSSW 就绪，也不因它失败而阻断或新增检查。
  - `execute` 说明要求“列 session 用 list-platforms；Skill 直接用 get-state，不要先 list”；模型没有为了执行 Skill 而触发全平台登录。

## S-04 Skill 依赖的平台有一个获取失败

- **负责**：待 TASK 拆分
- **目标**：保持 Skill 原有失败停止行为，同时一次告知各依赖平台的情况。
- **前置**：Skill 声明依赖 MSSP、MSSW，并按现有规范调用 session-manager；MSSP 正常，MSSW 认证失败。业务操作有可观察结果，例如报表产物或业务平台操作记录。
- **步骤**：
  1. 在新会话中执行该 Skill。
  2. 查看本次失败回复与业务结果。
  3. 对同类后台 Skill，检查任务失败消息及投递回复。
  4. 若预登录成功、脚本内 `get-state` 才失败，按同一期望检查失败回复；该路径可在集成测试中复现。
- **期望**：
  - Skill 沿原有失败处理停止，没有继续依赖缺失登录态的业务请求，未被标记为成功。
  - 本次回复说明 MSSP 可用、MSSW 获取失败及原因，并说明业务未完成。
  - 失败回复里有有界摘要（例如 `platform_sessions: mssp=ok; mssw=PLATFORM_AUTH_REJECTED(http=401) …`）；不要求用户追问。
  - 后台失败告知也保留诊断；提交回执不当作执行结果。
  - 预登录先失败或脚本内 `get-state` 失败都保留报告；不要求脚本必须已经启动。

## E-01 查询的两个平台均认证失败

- **负责**：待 TASK 拆分
- **目标**：全部失败也能列出各自原因。
- **前置**：两个可查询平台均被平台拒绝认证，失败原因可区分。
- **步骤**：
  1. 请求列出这两个平台的 session。
  2. 查看第一次回复。
- **期望**：
  - 明确两个平台分别失败，并给出各自实际原因。
  - `list-platforms` 完成检查后成功退出并返回报告，不只输出首个平台的错误或运行终止信息。

## E-02 可见平台缺少凭据

- **负责**：待 TASK 拆分
- **目标**：缺凭据的平台仍出现在查询结果中。
- **前置**：当前用户能看到两个平台；一个正常，另一个没有可用的用户或共享凭据。
- **步骤**：
  1. 请求列出平台 session。
  2. 查看第一次回复中的平台列表及失败原因。
  3. 另准备一个有凭据但内容错误的平台，确认它实际检查后也失败。
- **期望**：
  - 两个平台都出现，正常平台可用，另一个说明缺少可用凭据。
  - 缺凭据不被静默过滤，也不被描述为平台返回了认证拒绝。
  - 有凭据但内容错误的平台返回 `available: false` 和实际认证失败原因，不能因为“有配置”就返回 `available: true`。

## E-03 既有 get-state 失败出口保持

- **负责**：待 TASK 拆分
- **目标**：旧 Skill 不因新增查询能力而把登录态获取失败当作成功。
- **前置**：可在既有 Skill 测试环境观察命令退出码及状态文件；准备正常与认证失败两种凭据。
- **步骤**：
  1. 用正常凭据执行原来的 `session-manager get-state --skill-name <当前技能名>`，以及 `get-state --platform <key>`。
  2. 改为认证失败的凭据，用相同方式再次执行，观察退出码和错误输出。
  3. 结束本次执行，检查执行期文件的生命周期。
- **期望**：
  - 正常路径仍返回可读取的状态文件及原有字段；文件内容不打印到对话。
  - 原本失败的获取仍非零退出并保留原因，不因别的平台成功而变为成功退出。
  - 失败输出带 `platform_sessions`，可供失败回复/模型读取；不交付不完整的成功状态文件；执行结束后按原机制清理。

## B-01 查询范围与身份边界

- **负责**：待 TASK 拆分
- **目标**：指定查询范围不改变平台授权。
- **前置**：当前用户有一个可查询平台；另有不在受信允许范围的平台 key，或另一个用户的凭据。
- **步骤**：
  1. 只请求列出一个可查询平台。
  2. 在受限执行上下文中尝试查询范围外的平台。
  3. 查看查询结果与拒绝说明。
- **期望**：
  - 第一次只检查指定平台，不要求其他平台就绪。
  - 范围外的平台保持拒绝，不返回他人登录态，也不能通过命令参数切换身份。
  - 显式 `execute platforms` 的预登录失败仍按原规则处理，并在本次回复保留范围诊断。

## B-02 既有会话机制保持

- **负责**：待 TASK 拆分
- **目标**：查询与 Skill 继续使用现有登录态复用和刷新机制。
- **前置**：一个正常平台，可从测试平台的登录记录分辨是否发生重新登录。
- **步骤**：
  1. 查询该平台 session，再执行依赖它的既有 Skill。
  2. 会话仍有效时重复查询。
  3. 按原流程显式刷新或使会话失效，再次获取。
- **期望**：
  - 有效会话按原机制复用和续期，不因查询额外强制刷新。
  - 显式刷新和失效后重新获取仍按原行为工作。
  - `list-platforms` 的成功检查可能写成功会话/续期，这是实际查询语义；失败平台不写 Redis。

## B-03 查询结果可见而非只存在工具原文

- **负责**：待 TASK 拆分
- **目标**：实际入口把完整摘要交到第一次回复中。
- **前置**：存在正常与失败平台，可查看会话的工具结果详情。
- **步骤**：
  1. 在真实会话请求列出平台 session。
  2. 对比第一次回复与工具结果中的平台项。
- **期望**：
  - 回复覆盖本次查询的每个平台及失败原因。
  - 不需要读附件或重跑查询才知道哪些成功；原文有字段但回复缺失不算通过。
  - 模型说明要求读取逐平台结果后回答。

## B-04 查询无法全部完成

- **负责**：待 TASK 拆分
- **目标**：依赖故障、超时或不可检查平台出现时不编造状态。
- **前置**：隔离测试环境能模拟存储不可用、目录服务不可用、查询预算/超时耗尽；也可配置当前身份没有可查询平台；可选一个无会话适配器平台。
- **步骤**：
  1. 让部分平台已有检查结果后，触发无法继续检查的条件，查看本次回复。
  2. 对目录不可取得、目录确实为空、无会话平台三种情况分别查询。
- **期望**：
  - 已完成结果保留，剩余平台 `available: null` 并说明 `reason`（预算/超时/取消/全局故障）。
  - 目录服务故障不描述为所有平台凭据错误；空目录说明没有可查询的平台。
  - 无会话 / REQUEST_SIGNING 平台标 `available: null` + `reason`，不报成认证失败。
  - 取消、预算及基础设施故障沿用现有控制，不自动重试或越过限制。

## B-05 原 list-platforms 调用在预登录阶段失败

- **负责**：待 TASK 拆分
- **目标**：覆盖用户原始调用路径，命令尚未执行也不能丢失其他平台的结果。
- **前置**：准备当时的显式双平台 workspace 调用：`command` 为 `session-manager list-platforms`，`platforms` 包含 MSSP、MSSW；MSSP 正常，MSSW 认证失败。测试人员可从执行记录辨别 shell 命令是否启动。
- **步骤**：
  1. 在真实服务上用相同的显式平台参数执行 `list-platforms`，并查看本次回复。
  2. 将失败平台放在参数列表前面，再次执行并查看回复。
- **期望**：
  - 两种次序都能告知 MSSP 可用、MSSW 获取失败及原因，不只返回运行终止摘要。
  - 若现有预登录使 shell 命令未启动，回复如实说明该事实；不能声称 CLI 已执行或把单个平台失败说成所有平台失败。
  - 报告进入现有工具错误载荷/失败回复，有界摘要可见；不修改原有授权、Skill 失败停止或 Runner 终止规则。

## 场景编写约定

- 一个场景只验证一个用户可理解的目标。
- 步骤按真实操作顺序编号；期望写“看到什么 / 数据变成什么”。
- **第一次回复**是本需求的主观察点；不要只看 CLI stdout 或模型追问后的第二次回答。
- 需要机器执行的快速回归放在 Task 的 `### Tests`；E2E 与全量回归留在 CI。
