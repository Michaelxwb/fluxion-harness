# IM 附件完整性与后台任务产物交付 验收场景

> 这是给**人工测试者**使用的验收清单，不是 E2E 代码或测试注册表。
> 场景在真实 Connector、真实 Gateway、真实 Runtime、真实 PostgreSQL/Redis 上执行；企微相关场景优先使用真实企微，条件不具备时使用真实 WS 探针并记录差异。
> 每个场景只验证一个用户可理解的目标；步骤按真实操作顺序编写。

## S-01 企微文字 + 多个附件一次发送

- **负责**：待 TASK 拆分
- **前置**：
  - 企微机器人已绑定当前用户，Connector 正常运行。
  - 准备 2–3 个内容可区分的文件（例如两个 PDF/图片 + 一个 txt）。
  - 会话历史里已有旧附件，确保能区分“本次附件”和“历史附件”。
- **步骤**：
  1. 在企微输入一句“解析一下我这次发的附件”，随后连续发送 2–3 个文件。
  2. 等待第一次回复。
  3. 查看本次 Run 的输入与附件列表。
- **期望**：
  - 只创建一个 Run，输入同时包含文字和本次发送的全部附件。
  - 第一次回复只基于本次附件；不会读取历史残留文件或工具结果。
  - 用户只收到一条业务回复，不出现“先答错、再答对”的两条回复。
  - 附件顺序与发送顺序一致。
- **实际结果**：待执行

## S-02 后台任务结果按需重发

- **负责**：待 TASK 拆分
- **前置**：
  - 已有一个已完成的后台定时任务，产出 `report.txt` 和 xlsx。
  - 当前会话用户可以访问该任务所属 Agent。
- **步骤**：
  1. 在企微/WebChat/MSSWWEB 输入“把最近一次定时任务的结果发给我”。
  2. 等待回复和附件。
  3. 对照任务执行记录，确认没有重新执行 Skill。
- **期望**：
  - 用户收到任务当时生成的 `report.txt` 和 xlsx，内容与任务产物一致。
  - 回复正文按任务的 `result.text` **原文完整呈现**，不擅自摘要、压缩或改写；只有用户明确要求摘要时才摘要。
  - 不出现 `ATTACHMENT_NOT_FOUND`。
  - 任务执行次数、业务平台调用次数不增加；不是靠重跑 Skill 生成的新文件。
- **实际结果**：待执行

## S-03 工具结果的来源标注与显式访问

- **负责**：待 TASK 拆分
- **前置**：
  - 会话里存在至少一条 `TOOL_RESULT`（例如之前调用 `list_tasks` 的外置结果）。
- **步骤**：
  1. 让 Agent 列出当前可访问的附件。
  2. 查看列表中的来源标注。
  3. 明确要求“把刚才那个工具结果给我看看/发给我”。
- **期望**：
  - `TOOL_RESULT` 显示为“工具结果”或“内部产物”，不显示为“入站”。
  - 用户明确要求时，Agent 能读取该工具结果；需要交付时能按当前会话发送。
  - 用户没有明确要求时，Agent 不主动把内部工具结果当作用户附件或主动外发。
- **实际结果**：待执行

## S-04 WebChat / MSSWWEB 文本 + 多个附件

- **负责**：待 TASK 拆分
- **前置**：
  - WebChat 与 MSSWWEB 均已登录/可访问，可上传附件。
- **步骤**：
  1. 分别在 WebChat 和 MSSWWEB 输入文字，并附加 2 个文件。
  2. 等待上传完成后发送。
  3. 查看两个面的 Run 输入、附件和交付结果。
- **期望**：
  - 两个面都只创建一个 Run，文字和两个附件都在同一个 Run 中。
  - 不出现“先提交文字、后补附件”的第二个 Run。
  - 上传失败时不提交消息，不产生无附件的 Run。
  - 两个面行为一致，不按通道分叉。
- **实际结果**：待执行

## S-06 MSSWWEB 任务结果交付与下载

- **负责**：待 TASK 拆分
- **前置**：
  - MSSWWEB 面已启用，用户有可用入口。
  - 已有一个已完成的后台任务产物。
- **步骤**：
  1. 在 MSSWWEB 输入“把最近一次任务的结果发给我”。
  2. 等待回复和附件卡片。
  3. 点击下载 report 和 xlsx，核对内容与任务执行记录。
- **期望**：
  - 两个文件都出现在 MSSWWEB 当前会话。
  - 回复正文按任务的 `result.text` **原文完整呈现**，不擅自摘要、压缩或改写；只有用户明确要求摘要时才摘要。
  - 下载到的是任务当时的不可变版本，不是 404，也不是最新版顶替。
  - 任务执行次数不增加。
- **实际结果**：待执行

## E-01 多附件中有一个取件失败

- **负责**：待 TASK 拆分
- **前置**：
  - 准备 2 个附件，其中一个在发送后立即失效/损坏（或用测试媒体源返回失败）。
- **步骤**：
  1. 发送文字 + 2 个附件。
  2. 查看第一次回复和 Run 记录。
- **期望**：
  - 系统明确告知哪个附件失败，以及失败原因的用户可读说明。
  - 不创建基于“只剩成功附件”的业务 Run，不输出看似完整的解析结果。
  - 系统提示“本次未处理，请连同说明重新发送整批附件”，不承诺只补失败项。
- **实际结果**：待执行

## E-02 跨用户访问后台任务产物

- **负责**：待 TASK 拆分
- **前置**：
  - 用户 A 有一个后台任务产物；用户 B 没有该任务权限。
- **步骤**：
  1. 用户 B 尝试通过对话或附件 ID 读取/交付用户 A 的产物。
  2. 查看回复和工具结果。
- **期望**：
  - 返回“附件不存在或不可访问”，不显示文件名、大小、ID 存在性等泄露信息。
  - 不产生跨用户交付记录。
- **实际结果**：待执行

## E-03 附件晚于聚合窗口到达

- **负责**：待 TASK 拆分
- **前置**：
  - 可控制文字帧和文件帧的到达间隔，使文件晚于聚合窗口。
- **步骤**：
  1. 发送文字，等待超过最大聚合窗口。
  2. 再发送文件。
  3. 查看两次回复和 Run。
- **期望**：
  - 文字先按纯文本执行；如果用户要求解析“刚发的文档”，Agent 明确说明当前消息没有附件并请用户重发，不读取历史残留文件。
  - 后到的文件按独立消息处理，不追溯合并到前一个 Run。
  - 行为与文档描述一致，不出现“假装收到了附件”。
- **实际结果**：待执行

## E-04 附件下载超过最大等待

- **负责**：待 TASK 拆分
- **前置**：
  - 可让一个附件下载明显慢于最大等待窗口。
- **步骤**：
  1. 发送文字 + 1 个下载很慢的附件。
  2. 等待超过最大聚合窗口。
  3. 查看第一次回复和 Run 记录。
- **期望**：

  - 明确提示“本次附件未全部收到，未处理；请连同说明重新发送整批附件”。
  - 后到的附件不会单独触发一个缺少原说明的 Run。
- **实际结果**：待执行

## B-01 单批附件数量达到上限

- **负责**：待 TASK 拆分
- **前置**：
  - 确认当前单批附件上限。
- **步骤**：
  1. 发送文字，并连续发送达到上限数量的附件。
  2. 再发送第 N+1 个附件。
  3. 查看回复、Run 和附件列表。
- **期望**：
  - 达到上限的批次按明确规则处理，不静默丢弃。
  - 超限时给用户友好提示，例如“一次最多接收 5 个附件，请分批发送；本次未处理”，并说明当前上限。
  - 不产生部分附件被静默忽略的“成功”结果。
- **实际结果**：待执行

## B-02 同一批次消息被平台重投

- **负责**：待 TASK 拆分

  - 仍只创建一个 Run。
  - 不重复下载/重复回复/重复交付。
  - 已受理的批次不会因为成员重投再执行一次。
- **实际结果**：待执行

## B-04 命令消息穿插附件批次

- **负责**：待 TASK 拆分
- **前置**：
  - 聚合窗口内可发送 `/stop`、`/new` 等命令。
- **步骤**：

  - 待处理附件不被静默丢弃；按设计顺序明确处理。

## 场景编写约定

- 一个场景只验证一个用户可理解的目标。
- 步骤编号从 1 开始，按真实操作顺序编写。
- 期望写“用户看到什么/数据变成什么”，不写内部函数名或测试断言。
- 场景不生成 manifest、不登记执行结果、不阻断 `task finish` 或 `task archive`。
- 需要机器执行的快速回归放在 Task 的 `### Tests`；E2E 和全量回归留在 CI。
