# 会话上下文保留验收

> v0.4 · 2026-11-24 · 与 PRD v0.5 / backend design v0.5 对齐

使用本地构建的 WebChat、Console 与一个可执行工具调用的测试 Skill。每个场景开始前确认没有残留的在途 Run，使用独立测试会话与测试租户。执行后记录会话标题、Run ID、助手回复原文，以及 Console Run 事件里的压缩/裁剪统计。

> 预算语义：`history_budget_tokens` 是保守估算 token（1 token ≈ 1 UTF-8 字节 + 协议开销）。需要“预算内”的场景把它调到足够大（例如 65536）；需要“预算外”的场景调到能在几轮工具调用后触达（例如 8192）。所有场景都通过系统设置保存，新 Run 生效。整轮工具结果外置预算与预览头尾不是设置项，不能通过这些场景调参。

## S-01 多轮工具型对话后仍记得第一轮的要求（预算内）

- **负责**：功能验收人。
- **前置**：已登录 WebChat；测试 Skill 可被助手调用；系统设置把历史预算调到足够大；准备一个只在本场景使用的 6 位随机口令。
- **步骤**
  1. 新建会话，第 1 轮发送：「记住口令 A1B2C3。接下来我会让你做几轮工具任务，最后我会问你口令。」
  2. 第 2~5 轮，每轮让助手执行一个需要多次工具调用的任务（例如逐目录列出 Skill 并读取标题）。
  3. 第 6 轮直接问：「口令是什么？」
  4. 打开本轮 Run 事件详情。
- **期望**：助手在第 6 轮准确答出口令；第 2~5 轮不重复询问第 1 轮已经交代过的要求；本轮 Run 正常完成；预算内不应出现 `[历史裁剪]` 标记，也不应出现 `snip`/`micro` 层。

## S-02 说「继续」时助手接着当前工作回答，不被单条旧线索劫持

- **负责**：功能验收人。
- **前置**：同一用户在以往会话里**只留一条** TASK_STATE 线索（这是最容易被自动选中的路径）；当前会话里助手刚完成或正在做一件具体工作。
- **步骤**
  1. 在 WebChat 里等一次工具任务结束后，直接发送「继续」。
  2. 查看本轮回复、Console 的运行记录，以及本 Run 是否出现 `MEMORY_RESUME_RESOLVED`（outcome=SELECTED）。
- **期望**：助手针对当前会话的工作给出可执行的下一步，而不是只回一份模板任务清单，也不是自动跳去那条旧任务；本轮 Run 有正常的模型回复；本 submission 不应自动产生 `SELECTED` 绑定。若助手拿不准，它会结合候选任务向用户确认。

## S-03 用户明确选择候选任务

- **负责**：功能验收人。
- **前置**：上一步中助手列出了候选任务编号（或 Console 会话里有可选择的线索事件）。
- **步骤**
  1. 回复「第 2 个」。
  2. 查看助手回复与后续任务内容；Console 查看 `MEMORY_RESUME_RESOLVED` 的 `resume_ref`。
- **期望**：助手按第 2 个候选任务继续，回复内容与该任务相关；`resume_ref` 只在这次明确选择后才生成；不是把选择当普通闲聊处理。

## E-01 历史预算的非法值被字段级拒绝

- **负责**：管理员 + 功能验收人。
- **前置**：以管理员登录 Console，打开「系统设置 → 上下文压缩」。
- **步骤**
  1. 确认分组里只有「历史预算（tokens）」「启用摘要压缩」「摘要模型」「结果外置阈值」四项，不再出现历史预算条数、历史工具轮次上限、snip、micro、单轮结果预算、预览头尾。
  2. 把「历史预算（tokens）」清空后保存。
  3. 填 0、负数、小数后分别保存。
  4. 填一个超过后端范围上限的值后保存。
  5. 填一个合法正整数后保存，刷新页面。
- **期望**：第 2~4 次保存都被拒绝，错误落在该字段上并说明原因，设置没有变更；第 5 次保存成功，刷新后仍显示所填数值。

## E-02 预算不足时保头保尾，中间被裁且如实说明

- **负责**：功能验收人。
- **前置**：把「历史预算（tokens）」调小到能在几轮工具调用后触达；准备可执行多轮工具任务的测试 Skill。
- **步骤**
  1. 新建会话，第 1 轮提出一个具体需求（例如「把某个目录的文件逐个读一遍并总结」）。
  2. 第 2~4 轮连续进行多轮工具调用，并让第 3 轮留下一个可识别的中间细节（例如「核对第 3 个文件时发现的版本号」）。
  3. 第 5 轮问：「我们最开始让你做的是什么？第 3 个文件的版本号是多少？你还能看到吗？」
  4. 在 Console 打开本轮 Run 的事件详情。
- **期望**：助手仍然知道第 1 轮的目标（头部锚点保留），但明确说明第 3 轮的中间细节已被裁剪、无法找回，并请用户重新提供；不得编造。Run 事件详情里能看到 `[历史裁剪]` 对应的 `dropped_records`、`retained_from_seq` 与裁剪前后估算量；标记只在确实有记录未进入请求时出现。不得出现按条数/组数/回合数触发的旧层。

## E-03 摘要开启且预算截断时 coverage 只覆盖连续材料，尾部仍保留

- **负责**：开发/运维 + 功能验收人。
- **前置**：启用摘要并选择摘要模型；把历史预算调到很小；准备多轮工具任务；确认库里没有旧 `CONTEXT_SUMMARY`。
- **步骤**
  1. 连续进行多轮工具调用，直到装配出现中间缺口。
  2. 查看本轮是否调用了摘要模型、是否新增 `CONTEXT_SUMMARY` 事件，以及 `covers_up_to_seq` 的范围。
  3. 同时核对本轮请求里最近几轮对话仍在（摘要替换没有吞掉尾部），且当前用户消息的 seq 大于 `covers_up_to_seq`。
  4. 再发一轮消息，查看新一份 `CONTEXT_SUMMARY` 的 `covers_up_to_seq` 是否从上一份的末尾之后继续。
  5. 问中间某一轮的内容。
- **期望**：摘要材料是**连续**区间，`covers_up_to_seq` 等于实际材料末条历史事件的 seq，从不跨越未读取的记录，也不覆盖当前用户消息；摘要成功后最近几轮对话仍在请求里；缺口期间请求里仍带裁剪标记，而不是静默丢失；每轮覆盖起点从上一份摘要的末尾接上，多轮之后缺口逐步收敛。

## E-04 重置不兼容数据后设置页与新 Run 正常

- **负责**：开发/运维。
- **前置**：数据库中存在旧 `settings_json`（含 `snip`/`micro`/`history_budget_messages`/`max_history_tool_rounds` 等旧键）、Agent `runtime_config_json.budget.compaction`，以及旧 `CONTEXT_SUMMARY` 事件；已排空在途 Run/Task。
- **步骤**
  1. 清空 `control.platform_setting`（全租户全 revision）与平台设置幂等回执；删除每个 Agent `runtime_config_json` 里的 `budget.compaction` 块；删除全部 `CONTEXT_SUMMARY` 事件。
  2. 打开系统设置，确认压缩分组只有 4 项；其他分组回到 schema 默认（revision 0）。
  3. 保存一次合法压缩配置（建立 revision 1），新建一个 Run。
  4. 回读 Run 的 `policy_json`，确认 `compaction` 只包含 4 个叶子。
  5. 在旧会话继续一轮，确认不会有旧摘要被当作前置历史。
- **期望**：设置读取与保存不因未知键失败；新 Run 正常准入；`policy_json.compaction` 只包含 4 个叶子；旧键、旧摘要不再出现；库里也没有迁移补写的 revision 或审计行。重置的是整份平台设置，不只压缩分组，验收记录必须写明这一点。

## B-01 单条超大工具结果不导致整轮失败

- **负责**：功能验收人。
- **前置**：准备一个会返回超大输出的工具调用（例如一次性读取大文件），以及一个需要多轮工具调用的任务。
- **步骤**
  1. 让助手执行该大结果调用，随后继续下一轮提问。
  2. 查看聊天回复与 Run 状态。
  3. 检查该轮的工具结果是否按单条阈值或整轮派生预算被外置为引用。
- **期望**：后续轮次仍能正常送出并获得回答，不出现上下文超限失败；当前用户消息与最近一次完整工具往返仍在请求里；更早历史被省时，助手说明被省略但仍回答当前问题；Run 状态不是失败。整轮结果外置由 `history_budget_tokens` 派生，不是独立配置项。

## B-02 预算变更只影响后续 Run

- **负责**：管理员 + 功能验收人。
- **前置**：一个正在进行工具任务的会话；Console 可修改「历史预算（tokens）」。
- **步骤**
  1. 在助手执行期间把历史预算改小并保存。
  2. 让当前任务继续到结束。
  3. 在同一会话发起新一轮对话。
- **期望**：正在进行的 Run 行为不受影响（继续用自己冻结的预算）；新一轮才使用新预算，并且更早的历史在新预算下按保头保尾规则被裁剪或被摘要覆盖；Console 运行记录里两次 Run 的预算口径可区分。

## B-03 旧摘要清理是发布门禁

- **负责**：开发/运维。
- **前置**：准备一条旧 `CONTEXT_SUMMARY`（`covers_up_to_seq` 是单点最大 seq，且中间存在未读记录），确认发布清理尚未执行。
- **步骤**
  1. 在未清理的库上执行发布前检查：平台设置旧键、Agent 压缩覆盖、`CONTEXT_SUMMARY` 均应为空。
  2. 确认检查失败，发布不得继续；该状态不进入应用行为验收。
  3. 执行发布清理后重新检查，三者均为空。
  4. 用旧会话发起一轮，检查历史装配不再引用旧摘要。
- **期望**：旧摘要清理是发布门禁，不是代码兼容分支；未清理时不得发布，也不得把旧摘要当作可信 coverage。清理后旧会话不再有旧摘要，早期历史按新规则重新装配/摘要。
