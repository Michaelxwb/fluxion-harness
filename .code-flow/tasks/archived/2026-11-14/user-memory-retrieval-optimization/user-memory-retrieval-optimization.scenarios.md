# 用户长期记忆 v2（准确率优先）验收场景

> **修订版本**：v1.3；状态为待实现/待人工执行，本文不代表验收已通过。v1.3 收敛：实体正向匹配与逐标签冲突、旧 lane 行状态刷新、SET tombstone 恢复、forget_epoch 仅清空递增、评测 query-macro/ΔCI 口径。

> 这是给**人工测试者**使用的验收清单，不是 E2E 代码或测试注册表。
> 每个场景保留 S-/E-/B- 编号，供 design 和 Task 的 `Scenarios` 字段引用。
> 步骤用用户能执行的界面动作、CLI 命令或 API 请求描述；期望写用户可观察的结果。
> 本需求以 Console 管理面为主；Redis/模型故障类场景允许使用测试环境故障注入，缺少环境时记录缺失项与 owner，不伪装通过。

## 公共前置

- Console、Runtime、Worker、PostgreSQL、现有 Redis 集群、模型池已启动。
- 至少准备：
  - 一个 ADMIN 账号；
  - 一个非 ADMIN 账号（用于确认 403/入口不渲染）；
  - 一个已绑定模型的 agent；
  - 两个平台用户（用于跨用户隔离）。
- taxonomy 已按 v1 seed：`report_format`、`language`、`timezone`、`role`、`team`、`owned_system`、`general` 等。
- 测试用户没有历史记忆；如上次执行残留，先清空。
- **v1 治理面仅 ADMIN**：普通用户不应看到用户详情里的记忆 Tab；直接请求记忆接口应 403。
- Redis 故障场景需要测试环境可停止/恢复 Redis，或可注入连接失败；不能操作时标记未执行。
- 模型故障场景需要可临时停用 agent 模型或注入超时；不能操作时标记未执行。
- 评测场景需要已冻结合成数据集、基线和 TASK 声明的评测命令。

## S-01 显式保存偏好，并在后续对话中准确使用

- **负责**：待 plan 分配
- **前置**：ADMIN 已登录；测试用户没有 `report_format` 记忆。
- **步骤**：
  1. 打开用户详情 → 记忆 → 新建记忆。
  2. 类型选择“偏好”，predicate 选择“报告格式”。
  3. scope 选择 `audience=internal`。
  4. 值选择 `PDF`。
  5. 标题填写“内部报告默认 PDF”，摘要填写“用户明确要求内部报告默认使用 PDF”。
  6. 保存。
  7. 用该用户打开一个绑定 agent 的对话，问：“内部报告默认用什么格式？”
  8. 刷新记忆列表。
- **期望**：
  - 保存成功，列表出现该记忆，状态 ACTIVE，版本 1。
  - 对话回答使用 PDF，而不是 Word/Excel。
  - 刷新后记忆仍在；标题/摘要/scope 显示正确。
  - 页面不显示内部 `memory_key` 输入框。

## S-02 单值事实、SET 成员与多值 NOTE 并存

- **负责**：待 plan 分配
- **前置**：测试用户没有 `role` 记忆、`owned_system` 和客户备注。
- **步骤**：
  1. 创建 `role=解决方案架构师` 的事实记忆。
  2. 创建 `owned_system=防火墙` 与 `owned_system=EDR` 两条 SET 成员。
  3. 创建一条 NOTE：“A 客户最近在推零信任”，标签填 `entity:customer:A`、`topic:data-security`、`topic:zero-trust`。
  4. 创建第二条 NOTE：“B 客户关注数据安全”，标签填 `entity:customer:B`、`topic:data-security`。
  5. 刷新列表。
  6. 让 agent 回答“我是什么角色？”、“我负责哪些系统？”和“A 客户最近关注什么？”
- **期望**：
  - `role` 只有一条当前值。
  - `owned_system` 两个成员同时存在，不互相覆盖。
  - 两条 NOTE 同时存在，不互相覆盖，也不出现“冲突”提示。
  - agent 能分别使用角色、系统成员和 A 客户备注；B 客户备注不会被误用于 A。
  - 客户只作为标签/上下文出现，列表没有“客户主体”字段。

## S-03 内部/外部 scope、全局默认与特定覆盖

- **负责**：待 plan 分配
- **前置**：测试用户没有 `report_format` 记忆。
- **步骤**：
  1. 创建 `report_format + scope_state=ABSENT（全局）→ PDF`。
  2. 创建 `report_format + audience=internal → Excel`。
  3. 创建 `report_format + audience=external → Word`。
  4. 在对话中问：“内部报告默认用什么格式？”
  5. 再问：“给客户的报告默认用什么格式？”
  6. 最后问：“报告默认用什么格式？”（不带内部/外部）。
  7. 用一条包含未识别条件（如“合作伙伴报告”）的说法再问一次。
- **期望**：
  - 内部问题回答 Excel；客户问题回答 Word；全局 PDF 不与特定值同时注入。
  - 不带 scope 的问题使用全局 PDF，不会把内部/外部值混在一起。
  - 未识别的“合作伙伴”条件不被当成全局；如果系统无法判断，应明确不知道/要求澄清，而不是猜一个。
  - 管理列表能同时看到三条不同 scope_state/scope 的记忆；`UNKNOWN` 条件不能被保存为全局规则。

## S-06 管理员查看、编辑、启用/禁用、删除、恢复、清空、回收站

- **负责**：待 plan 分配
- **前置**：测试用户至少两条记忆。
- **步骤**：
  1. 在记忆列表按 kind/predicate/关键词筛选。
  2. 编辑一条记忆的摘要和值，保存。
  3. 尝试编辑该记忆的 predicate/scope（应只读）。
  4. 禁用该记忆，观察状态；再启用。
  5. 删除另一条记忆，确认。
  6. 打开回收站，找到已删除记录，恢复它。
  7. 点击“清空全部”，二次确认。
  8. 刷新列表和回收站。
- **期望**：
  - 筛选/分页正常，空结果不报错。
  - 编辑后版本递增；predicate/scope/kind 不可编辑，服务端返回 `MEMORY_IDENTITY_IMMUTABLE`。
  - 禁用后状态 DISABLED，不再注入；启用后恢复注入。
  - 删除后列表不显示，回收站可发现并恢复；恢复后 identity/version 不重置。
  - 清空后列表为空；回收站仍可查历史，可按 `memory_id` + 保留版本逐条恢复；清空确认文案明确“当前值不再注入，可从回收站恢复，历史保留”。
  - 非 ADMIN 访问记忆接口 403，且不渲染治理 Tab。

## S-12 合成评测对照，确认没有变差

- **负责**：待 plan 分配
- **前置**：
  - 已冻结 `user-memory-retrieval-optimization.evaluation.md` 的评测协议、合成数据集与基线实现（当前 `select_injection` 的只读副本）。
  - TASK 已声明评测命令；测试机有 PG/Redis 与模型池访问。
- **步骤**：
  1. 运行冻结数据集的 Smoke 档。
  2. 运行 Standard 档，分别记录基线、v2 的候选召回、门控后召回/精度、预算后注入、Required Recall、Strict Conditional Precision、Forbidden Injection、Stale Injection、Update Correctness。
  3. 分别运行“oracle 结构化输入”和“真实 extractor 输出”两套；不要把标签里的 predicate/scope 直接喂给检索器。
  4. 经验/TASK_STATE lane 单独跑、单独报告，不混入 v2 指标。
  5. 查看逐条结果、分 category 报告、optional 占用和端到端答案/动作质量。
  6. 抽查失败样本，确认不是标签/数据错误。
- **期望**：
  - 安全/冲突/过期/跨 scope 类别的 Forbidden Injection 为 0；这说明该集未观察到，不证明总体为 0。
  - Required Recall：主聚合 query-macro 的 ΔR 点估计 ≥ 0 且 CI 下界 ≥ -1pp；Strict Conditional Precision 的 ΔP 点估计 ≥ +5pp 且 CI 下界 > 0。
  - 报告同时给出 query-macro、user-macro 与 pooled 数值，签收只看 query-macro；置信区间对象是 Δ，不是 v2 绝对值。
  - Stale Injection、跨租户/跨用户泄漏为 0。
  - 报告保留数据版本、算法版本、参数、逐条结果；不能只看聚合数字。
  - Scope parser、extractor、renderer 都在真实链路中计分；不能只测检索器。
  - 未达标时先定位错误类别，不通过修改盲测标签凑结果。

  3. 观察 B 的提示和表单内容。
  4. 刷新 B 后重试。
- **期望**：
  - B 收到版本冲突提示，不静默覆盖 A。
  - B 的输入保留；提示刷新/重新加载。
  - 刷新后 B 看到 A 的新值，重试成功。
  - 历史里保留两次变更，顺序正确。

## E-05 跨用户/跨租户隔离

- **负责**：待 plan 分配
- **前置**：两个用户 A/B，各自有不同记忆。
- **步骤**：
  1. 用 A 的会话问 B 的记忆内容。
  2. 在 Console 打开 B 的用户详情，确认 A 的记忆不可见。
  3. 用 A 的登录态直接请求 B 的 user_id 记忆接口。
  4. 检查对话回答。
- **期望**：
  - A 的对话不出现 B 的记忆。
  - 跨用户接口被拒绝（403/404），不返回 B 内容。
  - 普通用户访问记忆治理接口 403；v1 不承诺“只读可访问”。
  - 日志/页面不泄漏 B 的正文或 key。
  - 同租户内的隔离同样成立。

  2. 创建一条记忆。
  3. 观察页面提示。
  4. 恢复 PG，刷新列表。

  - 恢复后可正常创建；不产生部分写入/半条记录。

## E-07 基于旧版本的候选被拒绝

- **步骤**：

  - 当前值保持新值，不被旧候选覆盖。
  - 候选状态变为失效/不再可接受。
  - 历史记录当前值的变更。

## E-08 清空后旧候选失效

- **负责**：待 plan 分配
- **前置**：已有一条 PENDING 候选。
- **步骤**：
  1. 清空该用户全部记忆。
  2. 打开待确认列表。
  3. 若缓存/页面仍显示候选，尝试接受。
  4. 刷新页面。
- **期望**：

## E-09 AGENT 同内容被用户确认后权威/版本变化

- **负责**：待 plan 分配
- **前置**：测试环境预置一条 AGENT 推断记忆，内容与用户随后确认的内容相同。
- **步骤**：
  1. 用户在对话中明确确认/保存同内容。
  2. 打开该记忆的历史和来源。
  3. 检查 `author`/`authority`/`confirmed_count`/`version`。
  4. 在 `inject_inferred=false` 的配置下开对话，确认它现在可用。
- **期望**：
  - 权威从 AGENT 变为 USER/ADMIN；即使内容相同，也产生可审计的新版本（或明确的权威升级记录）。
  - 不是只合并计数却仍不可注入。
  - `inject_inferred=false` 下，确认后的 USER 内容可正常注入。
  - 同一确认命令重放不重复升版本。

## E-10 SET 成员不能改值，变更走删除+创建

- **负责**：待 plan 分配
- **前置**：测试用户已有 `owned_system=防火墙`。
- **步骤**：
  1. 编辑该 SET 成员，尝试把值改成 `EDR`。
  2. 观察页面/接口结果。
  3. 删除 `防火墙` 成员，再创建 `EDR` 成员。
  4. 再尝试创建第二条 `EDR`。
  5. 用 POST 再次创建同值 `防火墙`。
  6. 打开回收站，恢复原 `防火墙` 记录。
  7. 刷新列表，检查成员、版本和历史。
- **期望**：
  - 编辑 SET 内容被拒绝（`MEMORY_IDENTITY_IMMUTABLE`），页面内容只读。
  - 删除+创建后只有一条 `EDR`，member key 正确；`EDR` 是新身份，不复用 `防火墙` 的 id/version。
  - 重复创建 `EDR` 被 `MEMORY_ALREADY_EXISTS` 拒绝，不出现两个相同成员。
  - 同值 `防火墙` 的 POST 被 `MEMORY_ALREADY_EXISTS` 拒绝：确定性 SET key 命中 tombstone，不能创建另一条同值身份。
  - 从回收站恢复原 `防火墙`：沿用原 id/version，不新建身份；恢复写 history/审计；恢复后 `EDR` 与 `防火墙` 作为两个独立成员并存。

## E-11 NOTE 重试复用 UUID，删除后同内容不能自动复活

- **负责**：待 plan 分配
- **前置**：可在保存 NOTE 后模拟响应丢失/重试；有一个已删除 NOTE 的内容。
- **步骤**：
  1. 保存一条 NOTE，记录返回的 `id`/version。
  2. 用同一 `Idempotency-Key` 重试同一请求。
  3. 观察 id/version/历史。
  4. 删除该 NOTE。
  5. 让后台提炼再次产出相同内容。
  6. 检查候选/当前值/历史。
- **期望**：
  - 重试返回同一 NOTE id/version，不重新分配 UUID，不产生两条。
  - 删除后 tombstone/version 保留；清空才递增 `forget_epoch`。后台同内容被拒绝/记录，不自动复活。
  - 显式人工重新保存/恢复可走授权路径，但必须新建/恢复明确身份，并写审计。
  - 不会用两个不同 UUID 绕过按旧 key 的删除保护。

## E-12 无实体匹配或复合条件冲突时不误召回

- **负责**：待 plan 分配
- **前置**：
  - 测试用户只有一条 B 客户 NOTE（`entity:customer:B`、`topic:data-security`），没有任何 A 客户实体行。
  - 后续步骤再创建 A 客户通用 NOTE（`entity:customer:A`、`topic:data-security`）。
  - 再创建 A 客户+项目 X NOTE（`entity:customer:A`、`entity:project:X`、`topic:data-security`）和 A 客户+项目 Y NOTE（`entity:customer:A`、`entity:project:Y`、`topic:data-security`）。
- **步骤**：
  1. 只有 B 客户 NOTE 时，问“A 客户关注数据安全吗？”。
  2. 查看注入内容。
  3. 创建 A 客户通用 NOTE 后，再问“A 客户关注数据安全吗？”。
  4. 创建 A 客户+项目 X/Y NOTE 后，问“A 客户项目 Y 的安全要求是什么？”。
  5. 再问“A 客户关注数据安全吗？”（不带项目）。
- **期望**：
  - 第 1 步 B 客户 NOTE 不得注入；没有正向实体匹配时，带 entity 标签的候选一律不注入；通用 topic NOTE 仍可能按 topic 出现，这是 v1 的保守边界。
  - 第 3 步 A 客户通用 NOTE 可注入，B 仍被拒绝。
  - 第 4 步 A 客户+项目 X NOTE 因项目 Y 冲突被拒绝，A 客户+项目 Y NOTE 可注入；不能因共同客户 A 而放行 X。
  - 第 5 步不带项目时，A 客户+项目 X/Y NOTE 因候选实体标签多于 query 而不注入；只召回无项目维度的 A 客户通用 NOTE。

## 场景编写约定

- 一个场景只验证一个用户可理解的目标。
- 步骤编号从 1 开始，按真实操作顺序编写。
- 期望写“用户看到什么/数据变成什么”，不写内部函数名或测试断言。
- 场景不生成 manifest、不登记执行结果、不阻断 `task finish` 或 `task archive`。
- 需要机器执行的快速回归放在 Task 的 `### Tests`；E2E 和全量回归留在 CI。
