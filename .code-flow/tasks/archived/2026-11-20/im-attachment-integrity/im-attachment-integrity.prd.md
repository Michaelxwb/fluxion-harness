## 2. 背景与目标

### 2.1 问题陈述 [必填]

| 维度 | 内容 |
|---|---|
| **问题描述** | 2026-11-20 14:51（CST）用户在企微发送“解析一下文档中的内容”和一份 PDF。企微把文字和文件拆成两条独立回调，网关先为文字创建了没有附件的 Run；PDF 又因为同路由串行锁被第一条 Run 阻塞约 24 秒。模型在第一个 Run 里调用 `list_attachments(scope="conversation")`，工具把两条 `TOOL_RESULT` 标成“入站”，模型选了其中一条旧的 `list_tasks` 任务列表并当成用户文档解析。用户先收到错误回复，之后才收到真正读 PDF 的回复。用户也可能一次发送**多个附件**（多张图片或多个文件），每个附件同样各占一条回调。 |
| **第二个问题** | 2026-11-19 20:35 用户要求“把最近的一次执行结果发给我”。`list_attachments(scope="agent", direction="outbound")` 能列出后台定时任务产出的 `report.txt` 和 xlsx，但 `deliver_artifact` 两次返回 `ATTACHMENT_NOT_FOUND`。数据库里这两条产物 `run_id` 和 `conversation_id` 都为空，`task_id`、`user_id`、`agent_id` 有值；现有归属查询只认会话或 Run，没有使用产物自身的 owner 字段。 |
| **第三个问题** | `TOOL_RESULT` 是工具结果外置产物，既不是用户附件也不是 Agent 产出。当前列表把除 `OUTPUT` 外的所有类型都标成“入站”，直接误导模型。 |
| **当前替代方案** | 用户重发附件；模型重新执行一次 Skill 生成当前 Run 的产物再交付。重跑会重复消耗业务平台额度，并可能产生重复业务操作。 |
| **触发原因** | 企微协议没有给文字帧和文件帧提供关联 id；现有入站链路把每条回调当成独立消息，且默认一条消息只有一个附件。附件工具的来源标注和归属判断也没有覆盖任务产物。 |

### 2.2 目标与价值 [必填]

| 维度 | 内容 |
|---|---|
| **核心目标** | 让“用户发来的附件”和“后台任务产物”在入站、枚举、读取、交付四个环节口径一致：该等的附件等到位，该标的来源标对，该能取的产物能取到。 |
| **预期价值** | 消除“文字和附件分家”导致的错误回答；后台任务结果可由用户按需取回，不重复执行业务 Skill；模型不再把工具结果当用户附件。 |

**成功指标**

| 指标 | 当前值 | 目标值 | 衡量方式 |
|---|---|---|---|
| 企微分帧文字+单附件/多附件产生多个 Run 的比例 | 可复现 | 0（窗口内合并） | 入站聚合指标 + 场景验收 |
| 多附件批次只创建一个 Run 的比例 | 未知 | 100% | 入站聚合指标 + 场景验收 |
| 任务产物 owner 访问成功率 | 列表可见但交付失败 | 100%（owner 显式请求） | `read_attachment` / `deliver_artifact` 集成测试 |
| WebChat/MSSWWEB 任务产物下载成功率 | 无会话产物被发布/下载层拒绝 | 100%（owner 显式请求、同会话发布事实存在） | WebChat/MSSWWEB 集成/人工场景 |
| `TOOL_RESULT` 被标成“入站”的次数 | 可复现 | 0 | 附件工具契约测试 |
| 因附件误判导致的错误回答 | 可复现 | 0 | 人工场景 S-01/S-02 |

**明确不承诺**

- 不保证企微客户端一定把文字和文件放进同一个回调；平台只按同路由短窗口聚合。
- 不改变后台任务的执行、调度、投递和产物生成逻辑。
- 不把内部工具结果默认展示给用户；只在用户明确要求且归属校验通过时允许交付。
- 不新增数据库表或迁移。

### 4.2 功能明细

#### FEAT-01: 企微文字+文件短窗口聚合

- **描述**: 入站侧按 route 维护一个有界聚合批次。批次可包含**一段文字 + 1..N 个附件**，也可只有附件；所有附件成功物化后只创建一个 Run。聚合发生在 Connector（单 bot owner，能看到该 bot 的全部帧）。窗口与上限来自系统设置页的 `im` 配置，必须有界；Connector 读取并缓存该租户配置。批次采用“静默窗口 + 最大等待 + 数量上限”：
  - 每来一个新帧就刷新静默计时；
  - 超过最大等待时间必须 flush，不能无限等；
  - 附件数达到平台上限后停止接收新媒体，等待静默/最大等待到期；若到期前又来新媒体，追加 `ATTACHMENT_COUNT_EXCEEDED` 并整批拒绝；
  - 新文字帧到来时先 flush 当前批次，避免把两条独立文字合并。
- **验收标准**:
  - [ ] 文字帧先到、1 个附件在窗口内到达：只创建一个 Run，`MessageInput` 同时含文字和附件。
  - [ ] 文字帧先到、多个附件分批到达（每个附件一条回调）：全部附件都进入同一个 Run，顺序与到达顺序一致。
  - [ ] 附件帧先到、文字帧在窗口内到达：同样只创建一个 Run。
  - [ ] 只有多个附件、没有文字：只创建一个仅含附件的 Run。
  - [ ] 窗口内没有附件：窗口到期后按纯文本执行，不无限等待。
  - [ ] 附件数达到配置上限：停止接收新媒体并等待窗口到期；超限帧追加明确失败并整批拒绝，不静默丢弃，也不产生部分成功的业务 Run。
  - [ ] 超限给用户友好通知：“一次最多接收 N 个附件，请分批发送”，N 来自系统设置页。
  - [ ] 批次中任一附件取件/物化失败：不按“没有附件”的纯文本继续执行业务；给用户逐项失败反馈，并明确提示“本次未处理，请连同说明重新发送整批附件”。
  - [ ] 同一批次的任一消息被平台重投：不创建第二个 Run；批次内所有成员 `message_id` 都参与去重。
  - [ ] 聚合只发生在同一 route，不跨用户/入口/会话合并。
  - [ ] 聚合缓冲有数量、字节和时间上限；超过上限按既有明确失败路径处理，不静默丢。
  - [ ] 聚合发生在路由锁和 Run 创建之前，不能因第一条 Run 的长流阻塞后续附件帧。
  - [ ] 命令消息（如 `/stop`、`/new`）不参与聚合；命令到达时先按既有语义处理，不与附件批次合并。

**默认值（系统设置页可配，按 1000 并发用户取保守值）**

| 配置键 | 默认值 | 范围 | 说明 |
|---|---|---|---|
| `im.inbound_batch_quiet_ms` | 300ms | 100–2000ms | 静默窗口；纯文本延迟主要来自它 |
| `im.inbound_batch_max_wait_ms` | 5000ms | 500–30000ms | 最大等待；只在连续来帧/慢下载时生效 |
| `im.inbound_batch_max_attachments` | 5 | 1–20 | 单批附件上限；沿用现有单条消息上限 |

#### FEAT-02: 附件来源标注与显式访问

- **描述**: 附件枚举返回真实来源；`TOOL_RESULT` 作为“工具结果”可见、可显式读取，但不再被描述为用户附件。`read_attachment` 的显式访问能力保留。
- **验收标准**:
  - [ ] `INBOUND_*` 标“入站”，`OUTPUT` 标“自产”，`TOOL_RESULT` 标“工具结果”，其他内部类型标“内部产物”。
  - [ ] 默认枚举不再把 `TOOL_RESULT` 标成“入站”，也不把它当作“用户刚发的文件”。
  - [ ] `direction=inbound` 只返回 `INBOUND_*`。
  - [ ] `read_attachment` 仍可按 id 读取 owner 的 `TOOL_RESULT`；权限校验不因类型被禁用。
  - [ ] 工具描述明确“工具结果是内部产物，不是用户附件”；模型需要找用户附件时用 inbound 过滤。
  - [ ] 用户明确要求转发内部产物时可直接交付，不需要确认卡片；模型不得在用户未要求时主动把内部工具结果发给用户。

#### FEAT-03: 后台任务产物按 owner 读取/交付

- **描述**: 归属判断除会话/Run 外，还认目标任务产物自身的 `task_id` + `user_id` + `agent_id`（租户已由外层限定，agent 必须精确匹配）。`list_attachments` 能列出的任务产物，`read_attachment`/`deliver_artifact` 必须能按 owner 访问；WebChat 与 MSSWWEB 共用同一套本地流交付和下载裁决。
- **验收标准**:
  - [ ] `run_id=NULL`、`conversation_id=NULL`、`task_id`/`user_id`/`agent_id` 有值的任务产物，owner 可列出、可读取，并可在企微、WebChat、MSSWWEB 交付。
  - [ ] WebChat/MSSWWEB 交付后，用户能从会话卡片下载任务当时的不可变版本；不是 404，也不是最新版顶替。
  - [ ] 交付的是任务当时生成的不可变版本，不重新执行 Skill、不产生新的业务调用。
  - [ ] 其他用户/租户读取同一产物返回“不存在或不可访问”，不泄露存在性。
  - [ ] 归属不完整（`user_id` 或 `agent_id` 为空）或软删产物明确不可访问；不放行 `agent_id=NULL`。
  - [ ] `list_attachments(scope="agent")` 与 `read_attachment`/`deliver_artifact` 的归属口径一致，不再出现“列得出、取不到”。

#### FEAT-04: WebChat / MSSWWEB 单次提交回归

- **描述**: WebChat 与 MSSWWEB 共用同一套 SYNC 提交和本地流交付；附件上传和消息提交是两个 HTTP 请求，但前端等全部上传完成后再提交，`upload_ids` 随同一个 `RunRequest` 进入；本次改动不得破坏该语义。
- **验收标准**:
  - [ ] 上传成功但未提交时不创建 Run。
  - [ ] 提交时所有 `upload_ids` 在创建 Run 前完成归属/TTL 校验；失败不创建 Run。
  - [ ] 文本 + 1..N 个附件只产生一个 Run，所有 `upload_ids` 都进入同一个 `RunRequest`。
  - [ ] WebChat 与 MSSWWEB 的行为一致，不按通道分叉。
  - [ ] 不引入 WebChat/MSSWWEB 文字/附件分帧聚合。

#### FEAT-05: 可观测与失败语义

- **描述**: 聚合与归属修复必须可观测，失败不能静默。
- **验收标准**:
  - [ ] 聚合合并、窗口超时、附件失败、任务产物越权分别有指标/日志。
  - [ ] 日志只记 id/code/耗时，不记附件内容、URL、cookie、AK/SK。
  - [ ] 附件失败不伪造“已收到/已解析”，不把空附件当纯文本成功。

## 5. 非功能需求 [可选]

| 指标ID | 类型 | 要求 |
|---|---|---|
| NFR-SEC-01 | 安全 | 任务产物/工具结果必须按租户 + owner（user/agent）校验；未授权不得进入 ToolRegistry 视野，不得出现“列表可见但读取越权”或反向情况。 |
| NFR-REL-01 | 可靠性 | 聚合窗口、多附件批次、重投、崩溃恢复都不得产生重复 Run 或丢失已受理消息；批次内所有成员 `message_id` 参与去重，幂等身份取主消息 id。 |
| NFR-PERF-01 | 性能 | 纯文本消息只增加有界聚合窗口延迟；窗口值由配置定义，不因等待附件无限延长；附件数达到上限立即 flush。 |
| NFR-OBS-01 | 可观测 | 聚合/超时/失败有指标与结构化日志，能区分“没有附件”“附件失败”“聚合超时”。 |
| NFR-COMPAT-01 | 兼容 | 不新增 IM 通道、不改变 WebChat/MSSWWEB 提交契约、不新增数据库迁移；现有单帧媒体消息保持原行为。 |

## 6. 范围与边界 [必填]

| 类别 | 内容 |
|---|---|
| **范围（In Scope）** | 企微入站文字+1..N 个附件的短窗口聚合；附件枚举来源标注；`TOOL_RESULT` 显式访问；后台任务产物 owner 读取/交付（企微、WebChat、MSSWWEB）；WebChat/MSSWWEB 多附件回归测试；相关指标/日志与场景。 |
| **非范围（Out of Scope）** | 其他 IM 通道的协议差异；企微客户端行为改造；新的附件类型；任务调度/执行/投递模型；全量 ACL 重构；UI 新增页面；数据库表结构变更。 |
| **前置假设** | 生产企微固定经 Connector 接入（Gateway 直连适配器路径不承载企微）；企微文字帧和每个附件帧都没有共享关联 id，只能按同 route + 时间窗口聚合；一次发送可能包含 1..N 个附件；`artifact.user_id`/`agent_id` 是任务产物的权威 owner 字段；用户明确要求可代表内部产物交付的授权意图。 |
| **有意妥协 / 技术债** | 聚合窗口会给所有企微文本增加有界延迟；这是换取“附件不漏”的产品取舍，窗口值需可配置并可观测。若文件在窗口之后才到，仍按独立消息处理（保持现有行为），不追溯合并。若用户在窗口内连续发送两条独立文字，第二条会先 flush 第一条，避免把两条业务指令合并。 |

## 7. 依赖与风险 [可选]

| 依赖方 | 依赖内容 | 最晚交付时间 | 风险等级 |

### 7.2 风险识别

| 风险ID | 描述 | 影响 | 缓解方案 |
|---|---|---|---|
| RISK-01 | 聚合窗口让纯文本回复变慢 | 用户体验下降 | 窗口可配置、取较小值；指标观察 P95；只对同 route 生效 |
| RISK-02 | 聚合与同路由串行锁配合不当导致死锁/饥饿 | 消息卡住 | 聚合必须在路由锁之前完成；窗口有界；补并发/超时测试 |
| RISK-03 | 文件帧在窗口后到达，仍产生第二个空文本 Run | 重复回答 | 明确边界；第二个 Run 仅处理附件，模型应说明；后续可评估更长窗口 |
| RISK-04 | 允许内部产物交付导致上下文泄漏 | 安全/合规 | owner + agent + 租户三重校验；用户显式请求/确认；不默认展示 |
| RISK-05 | 直接使用 `artifact.user_id` 放宽了历史归属 | 越权读取 | 只对非空 user/agent 生效；保留租户与软删校验；补跨用户负例 |
| RISK-06 | 多附件分批到达时间跨度大，静默窗口反复刷新导致等待过久 | 响应变慢 | 设置最大等待上限；达到上限立即 flush；超时后的附件进入下一批 |
| RISK-07 | 多附件中部分失败，用户误以为全部成功 | 业务判断错误 | 任一附件失败则整批不执行业务；逐项反馈失败，提示重新发送整批；不伪造完整性 |

### 7.3 已确认决策

| 编号 | 决策 |
|---|---|
| Q-01 | 多附件中任一失败：整批不进入业务执行，逐项反馈，并提示用户连同说明重新发送整批附件；不承诺只补失败项。 |
| Q-02 | 默认值：静默 300ms、最大等待 5000ms、单批 5 个附件；系统设置页 `im` 配置可调。 |
| Q-03 | 窗口内第二条文字帧一律先 flush 前一批，避免合并两条独立指令。 |
| Q-04 | 用户明确要求即可交付内部工具结果，不需要确认卡片；工具调用保留显式参数与审计。 |
| Q-05 | 任务产物按 `task_id + OUTPUT + user_id + agent_id` 精确校验；`agent_id` 为空一律拒绝，不回填历史空 owner 行。 |
