## 2. 背景与目标

### 2.1 问题陈述

当前一次 Skill 调用失败可能直接终止本轮 Agent 执行，使用户只收到平台失败提示。不可重试本应约束同一次调用的再次执行，却被用作“Agent 无法继续”的依据；Agent 因而无法利用已获得的结果修订方案、请求补充或解释无法继续的原因。

另一个问题是进程执行状态与业务结论混在一起。`self-skill-review` 已完成审查并生成有效报告时，仍按独立 CLI 契约以 exit 1 表示存在 error 级 findings。若平台只看退出码，就会把有效审查判为工具故障。客户无设备、多客户待选择同样需要各自的业务语义，不能一概变成执行失败。

本次静态核对的事实如下，尚未运行复现或端到端验收：

| 当前源码入口 | 已核实事实 |
|-------------|------------|
| `packages/agent-core/src/muad_agent_core/skill/{executor,sandboxed}.py` | 普通非零退出被映射为执行失败；需要在结果契约支持下准确分类，不能简单放宽退出码 |
| `packages/agent-core/src/muad_agent_core/tools/outcome.py` | `ExecutionOutcome` 已保留退出码、业务状态、失败层与 retryable；Skill FAILED 进入 CONTENT 失败，但尚不能完整表达“执行完成且审查未通过” |
| `packages/agent-core/src/muad_agent_core/agent/{failure,runner}.py` | 非 retryable 失败直接设置 no_progress，Agent 停止继续调用模型；可重试失败受同类失败计数保护 |
| `apps/agent-runtime/src/muad_agent_runtime/application/{skill_tools,run_service}.py`、`finalization/render.py` | Skill 结果进入共享 outcome；NO_PROGRESS 转入平台失败收尾，用户正文由确定性文案生成 |
| Runtime `execution_checkpoint.py`、Worker `application/agentic/run.py` 与共享 `agent/recovery.py` | 恢复也消费失败事实和检查点，必须与实时执行一起调整；恢复不能盲目重放原调用 |
| `apps/agent-worker/src/muad_agent_worker/worker/execution_outcomes.py` | Task 先按执行状态分支，非 SUCCEEDED 进入失败结果分类；需同步验证业务结论与执行完成的区分 |
| `skills/self-skill-review/scripts/check.py` | 有 error 级 findings 时，先输出/写入报告再 exit 1；正常无 error 时 exit 0；目标不可读、读取/报告写入失败 exit 2 |

### 2.2 目标与价值

让 Agent 在安全边界内消费每次调用的真实结果：能恢复则继续，需要用户输入则询问，当前目标无法继续则结合上下文自然收尾；任何一种结果都不应让整个会话失去继续交流能力。

成功以第 4 节验收目标逐项通过衡量：首个场景必须完成真实 self-skill-review findings → 修订 → 重审闭环；真实失败、询问、无法继续、下一轮对话和跨路径一致性分别验证，不用单元测试数量替代。

## 3. 用户与场景

### 3.1 目标用户

- 对话用户：通过 Agent 查询客户、执行 Skill、处理异常并继续交流。
- Skill 作者：通过 self-skill-review 发现问题、修订并重新审查。
- 管理员与维护者：从 Console、Run/Task 记录准确区分执行故障、业务结果及停止原因。

| ID | 用户故事 | 优先级 |
|----|----------|--------|

| US-02 | 作为对话用户，我希望一次调用失败后 Agent 利用原因和已有结果选择下一步，以免对话突然中断。 | P0 |
| US-03 | 作为对话用户，我希望缺少条件时被准确询问、确实无法继续时得到自然解释，并能在同一会话接着聊。 | P0 |
| US-04 | 作为维护者，我希望各执行路径和 Console 对同一结果含义一致，且可以追溯原始退出码和故障证据。 | P0 |

## 4. 功能需求

### 4.1 功能清单与验收目标

| ID | 功能 | 关键验收目标 | 优先级 / 来源 |
|----|------|-------------|---------------|
| FEAT-01 | 可验证的执行结果契约 | 分别保留进程退出事实、执行是否完成、业务结论、可用结果/报告与故障；只有契约及结果验证通过，才能把特定非零退出识别为有效业务结果。 | P0 / US-01、04 |
| FEAT-02 | 失败后的 Agent 决策 | 单次调用失败及不可重试本身不直接终止 Agent；Agent 获得脱敏失败原因和已取得的有效结果，能继续、询问或收尾；不可通过全部标记 retryable 实现。 | P0 / US-02 |
| FEAT-03 | 业务结果与补充输入 | 无设备被解释为有效空结果；多客户待选择发出明确问题并按用户选择继续，未选择前不擅自选客户或执行有副作用操作。 | P0 / US-03 |
| FEAT-04 | 自然收尾与连续对话 | 无法继续时说明已完成内容、受阻环节、缺失条件及可行下一步；技术码和 Run ID 进入技术详情。已交付的有效正文、结果和附件不得被泛化失败提示替换；下一条消息仍可在同一会话正常受理。 | P0 / US-02、03 |
| FEAT-05 | 跨路径及 Console 一致性 | 同步 Runtime、后台 Skill/Worker、Agentic 执行、持久化恢复与 Console 使用一致分类；恢复不丢结果、不改变业务结论、不重复消费或盲目重跑。 | P0 / US-04 |
| FEAT-06 | 安全边界与循环保护 | 保留取消、预算、deadline、权限与出站控制、同类失败循环保护；显式区分安全重试、改方案和未知副作用，禁止因“对话可继续”放宽执行权限或重新产生副作用。 | P0 / 全部 |

**FEAT-01：首个验收场景与分类负向对照**

- 对一个确有可修订 findings 的真实 Skill 草稿执行真实 self-skill-review；有效报告且 exit 1 时，Agent 能读取报告、修订草稿并重新审查。记录每次实际退出码、报告及对应草稿版本，初审未通过不得显示成审查通过，重审未通过也不得宣称完成修复。
- 保留 self-skill-review 的独立 CLI 退出码契约，不将有 findings 改为 exit 0，不通过只识别 Skill 名或任意 stdout 关键词判成功。
- 结果契约需明确适用调用、结果格式和完成条件；验证本次调用对应的报告是否有效、完整且一致。契约及验证所需非密材料随执行冻结，恢复不能从当前定义重新解释旧结果；具体载体和字段在设计阶段决定。
- 未声明/不匹配契约、报告缺失/损坏/不完整、报告与本次调用不符、真实崩溃或报告写入失败时，准确记录工具/执行失败，保留有效部分但不得误判审查已完成。

**FEAT-02、03、04：Agent 的下一步和用户可见结果**

- 可安全恢复的真实工具失败：先把失败和已有结果送给 Agent，再由 Agent采用有依据的修正、替代步骤或有效部分结果；不会照原参数无限重试，也不会编造成功或零结果。
- 无设备：解释查询成功但未发现设备及相应业务影响；多客户：给出可供选择的有效候选，收到补充后继续。业务结论依赖明确结果证据，不能仅凭失败文案推断。
- 当前目标确实无法完成：基于当前目标、真实障碍及已完成步骤给出自然语言回复，不要求用户读错误码才能理解；不得仅给通用“执行失败”。明确区分工具失败与本轮整体目标是否达成。
- 询问及终态回复应持久化，刷新/重连后仍可见。等待输入按现有等待协议续接，已终态的 Run 不复活；用户仍可在同一会话发起下一轮，利用已保存且可访问的结果继续处理。
- 正常 Agent 决策在现有预算内完成解释；硬停止或模型不可用时使用真实持久事实做有上下文的确定性兜底，不能为收尾绕过取消、权限、预算或 deadline 强行追加模型调用。

**FEAT-05、06：一致性与安全负向对照**

- 对同一组有效 findings、审查通过、真实崩溃、缺输入、无设备和未知结果，在同步、后台、恢复路径与 Console 分别核对：原始退出码、执行完成、业务结论、报告引用及真正停止原因一致，不能一条路径完成、另一条误判为工具故障。
- Worker 保留自身任务/投递生命周期；投递失败不倒推业务失败。旧 Run 的迟到结果只能按既有契约记录并供后续交流，不能重启终态。
- 用户取消、硬预算或期限耗尽后停止实际执行；权限拒绝后不绕过权限，Agent 可在有效边界内解释或请求正当补充。
- 结果未知、有副作用且缺少可验证幂等保证的调用，不得因恢复、参数修正、模型建议或传输重试重复执行；明确提示结果未知及核查方向。
- 重复失败、重复未改善的审查 findings 必须有界停止；无关诊断调用不能制造“已取得进展”以无限续跑。阈值和预算由已有设置所有者控制。

### 4.2 边缘情况

| 场景 | 预期行为 |
|------|----------|
| 部分工具成功、另一个失败 | 保留可验证的有效部分与引用，明确未完成范围，Agent 决定是否存在安全后续步骤 |
| 有报告文件但发生崩溃，或报告属于旧调用 | 不以文件存在证明本次完成；保留证据并按契约验证结果分类 |
| 报告正文被截断或外置 | 使用可访问、可验证的完整产物；证据不足时不得凭预览宣称审查完成 |
| 多次重审仍得到相同问题 | 触发有界无进展保护，自然说明尚未解决的问题与下一步 |
| 询问后用户取消、到期或收到迟到结果 | 原终态及权限不变；迟到结果不复活执行，后续新消息按现有会话规则受理 |
| 出站窗口限流与独立故障并存 | 继续准确区分原因，保留已验证结果；不能把独立故障包装成单纯限流提示 |

## 附录：术语

- **执行完成**：按已验证契约完成预定操作并产生有效结果，不等于业务目标达成。
- **业务结论**：例如审查通过/未通过、有效空结果、需要选择；不能由原始退出码单独推断。
- **不可重试**：本次调用不应照原参数再次执行，不代表 Agent 不能解释、改方案或询问。
- **对话可继续**：等待中的执行可依法续接；终态后的新消息可发起下一轮，不复活旧终态、不自动重放旧副作用。
