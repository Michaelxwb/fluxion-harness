# 工具失败后的 Agent 恢复回合验收场景

> 这是给人工测试者使用的验收场景，不是 E2E 代码或测试注册表。
> 场景验证用户可观察的恢复、等待、交付和硬停止行为；内部错误码、表名和实现函数由自动化契约/集成测试覆盖。

## S-01 普通工具失败后改用替代路径

- **负责**：待任务拆解
- **前置**：
  - 准备一个首选查询工具会失败、备用查询路径可用的测试环境。
  - 用户可以从 WebChat 或 IM 发起请求。
- **步骤**：
  1. 向 Agent 提出需要调用首选工具才能完成的问题。
  2. 让首选工具返回一次可识别的业务失败。
  3. 观察 Agent 是否继续思考并选择备用工具或其他合法路径。
  4. 查看最终回复和运行过程。
- **期望**：
  - 首选工具失败不会立即结束会话，也不会直接把原始堆栈返回给用户。
  - Agent 可以使用备用路径完成请求，或者明确说明无法继续。
  - 只有一次最终助手回复收尾，不出现重复的失败终态消息。
- **实际结果**：待执行

## S-02 参数或资源失败后修正调用

- **负责**：待任务拆解
- **前置**：
  - 准备一个第一次调用缺少参数或引用不存在资源的工具。
  - 准备一个补齐参数或改用有效资源后可以成功的路径。
- **步骤**：
  1. 发起会触发参数/资源失败的请求。
  2. 观察 Agent 是否理解工具失败事实。
  3. 如果缺少业务参数，按 Agent 的问题补充参数；如果资源不存在，提供有效资源。
  4. 查看最终结果。
- **期望**：
  - Agent 不把资源不存在误写成空结果或成功查询。
  - 补齐信息后可以继续完成请求。
  - 历史回复中不出现两次互相矛盾的最终结论。
- **实际结果**：待执行

## S-03 频率限流后等待并重试

- **负责**：待任务拆解
- **前置**：
  - 配置一个会短暂返回频率限制、随后恢复的外部工具或 MCP 服务。
  - 限制窗口短于当前 Run 的剩余执行时间。
- **步骤**：
  1. 发起需要调用该工具的请求。
  2. 让第一次调用触发频率限制，并提供稍后重试提示。
  3. 观察运行状态和最终结果。
- **期望**：
  - 系统在允许的等待范围内退避或等待，不立即生成失败终态。
  - 重试使用同一个安全的调用身份，不重复创建不安全的副作用。
  - 服务恢复后得到正常结果；等待过程不向用户展示原始异常堆栈。
- **实际结果**：待执行

## S-04 异步 Operation 等待并续接

- **负责**：待任务拆解
- **前置**：
  - 准备一个会先提交、后异步返回结果的工具操作。
  - 允许从新连接或刷新页面观察同一个 Run/Task。
- **步骤**：
  1. 发起异步操作。
  2. 在外部结果尚未到达时刷新页面或断开后重新连接。
  3. 观察 Run 是否显示等待状态。
  4. 让外部操作完成，再查看最终结果。
- **期望**：
  - Run/Task 显示等待外部结果，而不是失败。
  - 恢复后继续使用原操作，不重新创建同一个外部任务。
  - 结果到达后只产生一次最终结果。
- **实际结果**：待执行

## S-05 产物已生成但消息交付失败

- **负责**：待任务拆解
- **前置**：
  - 准备业务操作已经生成 Artifact。
  - 暂时阻断消息/附件投递，但保留结果 Outbox 和 Artifact。
- **步骤**：
  1. 执行会生成文件或图片的请求。
  2. 让第一次投递失败。
  3. 恢复消息通道或投递端点。
  4. 观察投递重试和最终消息。
- **期望**：
  - 业务操作不被重新执行，外部数据和 Artifact 不重复生成。
  - 系统只重试消息/Artifact 投递。
  - 用户最终收到文件、图片或明确的降级取件链接后，才显示交付完成。
- **实际结果**：待执行

## E-01 身份或租户边界破坏

- **负责**：待任务拆解
- **前置**：
  - 准备一个工具请求尝试访问其他 Agent、其他租户或不匹配的 Snapshot 能力。
- **步骤**：
  1. 触发跨边界调用。
  2. 观察用户界面、Run 状态和审计信息。
  3. 尝试让 Agent 改用另一个工具绕过限制。
- **期望**：
  - 越权调用被阻止，不执行外部操作。
  - Agent 不能通过换工具、换参数或重复调用绕过限制。
  - Run/审计保留安全拒绝事实；用户看不到凭据或内部敏感信息。
- **实际结果**：待执行

## E-02 关键事实持久化失败

- **负责**：待任务拆解
- **前置**：
  - 注入 Prepared、Checkpoint 或关键事件写入失败。
- **步骤**：
  1. 发起需要工具执行的请求。
  2. 在外部执行前或结果收口时让关键事实写入失败。
  3. 观察 Run 是否继续调用模型或工具。
- **期望**：
  - 系统不在事实缺失的情况下继续执行或伪装成功。
  - Run 进入明确的宿主失败/需要处理状态。
  - 事件、日志和技术详情能够定位事实写入失败。
- **实际结果**：待执行

## E-03 已发送但结果未知的副作用操作

- **负责**：待任务拆解
- **前置**：
  - 准备一个会产生外部副作用的工具。
  - 让请求发送成功但客户端无法确认最终结果。
- **步骤**：
  1. 发起副作用操作。
  2. 让客户端在结果确认前断开或返回未知状态。
  3. 观察 Agent 后续行为。
- **期望**：
  - 原操作不会被自动重复执行。
  - Agent 可以查询状态、等待结果或选择安全替代路径。
  - 用户看到“结果未知/正在确认”等真实状态，而不是伪造成功或失败。
- **实际结果**：待执行

## E-04 相同失败持续重复

- **负责**：待任务拆解
- **前置**：
  - 准备一个不可通过重复调用解决的确定性失败。
- **步骤**：
  1. 发起会触发该失败的请求。
  2. 让 Agent 连续选择相同工具和相同参数。
  3. 观察达到恢复止损条件后的状态。
- **期望**：
  - 系统不会无限调用或无限等待。
  - 原调用被标记为不可继续重做。
  - 模型可用且仍有预算时，Agent 说明已完成范围、失败原因和可行下一步。解释期间没有新的工具调用。
  - Run 保留失败终态和技术详情。刷新页面后仍看到同一条解释。
- **实际结果**：待执行

## E-05 异步 Operation 取消与迟到结果

- **负责**：待任务拆解
- **前置**：
  - 准备一个处于运行或等待状态的异步 Operation。
  - 能够发起取消并模拟之后到达的迟到结果。
- **步骤**：
  1. 发起异步 Operation。
  2. 在结果到达前取消该 Operation。
  3. 尝试继续提交同一 Operation 的业务调用。
  4. 让外部系统发送迟到结果。
- **期望**：
  - 取消后不再接受同一 Operation 的新业务调用。
  - 迟到结果不会把已取消状态改回成功或重新触发 Agent 执行。
  - 迟到结果仍可在详情/审计中对账。
- **实际结果**：待执行

## E-06 结果证据不完整

- **负责**：待任务拆解
- **前置**：
  - 准备分页只返回部分数据、详情补全失败或 Artifact 内容不完整的工具结果。
- **步骤**：
  1. 发起需要完整证据的查询或报告请求。
  2. 让中间某一部分结果缺失。
  3. 查看 Agent 的最终结论。
- **期望**：
  - 系统明确标记结果不完整或未知。
  - Agent 可以补查；无法补查时说明限制。
  - 不把缺失数据写成“没有事件”“数量为零”或“报告已完成”。
- **实际结果**：待执行

## E-07 交付失败不触发业务重跑

- **负责**：待任务拆解
- **前置**：
  - 准备业务动作已经完成且产生可核对的 Artifact。
  - 让 Delivery Outbox 在多次投递中失败。
- **步骤**：
  1. 执行业务请求并等待 Artifact 生成。
  2. 阻断交付通道。
  3. 查看业务执行记录和投递记录。
- **期望**：
  - 业务执行只发生一次。
  - 投递失败独立显示并按交付策略重试。
  - 不因为投递失败而重新创建外部任务或重新生成 Artifact。
- **实际结果**：待执行

## E-08 模型、deadline、租约或总预算硬停止

- **负责**：待任务拆解
- **前置**：
  - 分别准备模型不可用、Run deadline 到期、执行租约丢失和总预算耗尽的环境。
- **步骤**：
  1. 在工具失败或等待恢复过程中触发其中一种硬停止条件。
  2. 观察是否还有新的模型或工具调用。
  3. 查看最终状态和技术详情。
- **期望**：
  - 宿主停止继续执行，不让 Agent 假装恢复。
  - 已发生的工具事实保留，Run 有明确终态。
  - 用户正文不暴露原始堆栈；技术详情保留可定位信息。
- **实际结果**：待执行

## B-01 多工具批次部分成功

- **负责**：待任务拆解
- **前置**：
  - 准备同一模型回合中两个或多个工具，其中部分成功、部分失败。
- **步骤**：
  1. 发起会产生多工具调用的请求。
  2. 让其中一个工具成功、另一个失败。
  3. 观察 Agent 后续决策和最终回复。
- **期望**：
  - 成功结果保留，不因另一个失败被抹掉。
  - 失败结果逐调用回到 Agent 上下文。
  - 未执行的后续调用有明确状态，不产生幽灵执行。
- **实际结果**：待执行

## B-02 限流等待接近 Run deadline

- **负责**：待任务拆解

- **步骤**：

- **期望**：
  - 系统只等待到可用预算边界。
  - 无法在 deadline 内重试时转为明确的 deadline/限流收尾。
  - 不在 deadline 之后继续发送请求。

## B-03 JOIN 与 DETACH 操作差异

- **负责**：待任务拆解
- **前置**：
  - 准备一个 JOIN 异步操作和一个 DETACH 后台操作。
- **步骤**：
  1. 分别发起两种模式的操作。
  2. 观察父 Run、Task Center 和结果投递状态。
  3. 让后台结果稍后到达。
- **期望**：
  - JOIN 使父 Run 等待结果并在结果到达后续接。
  - DETACH 不阻塞父 Run，但结果仍可在 Task/Operation 详情和交付链路中追踪。
  - 两种模式都不重复提交同一 Operation。

## 场景编写约定

- 一个场景只验证一个用户可理解的目标。
- 步骤编号从 1 开始，按真实操作顺序编写。
- 期望写用户看到什么、Run/Task/交付状态如何变化，不写内部函数断言。
- 场景不生成 E2E 代码，不登记执行结果，不阻断 `task finish` 或 `task archive`。
- 快速单元/集成回归由后续 Task 声明；浏览器和真实通道验证按本文件人工执行。
