# V1.13.1 核心设计决策（ADR 汇总）

> 本文是“为什么这样设计”的集中索引。模块文档负责“怎么实现”，本文件负责避免后续实现者因为局部方便重新推翻已评审结论。

## ADR-001 Stateless Agent Runtime

**决策**：Agent Runtime 为共享无状态 Runtime Pool，任意实例可处理任意 Agent/User。  
**不采用**：每用户 Pod、每 Agent Pod、依赖 sticky session。  
**原因**：横向扩展、故障迁移、成本、统一运维。  
**约束**：Runtime 本地仅允许连接池、有界缓存、临时 Context、metrics；持久业务事实必须外置。

## ADR-002 Service 是唯一业务发布单元

**决策**：只有 Service 采用 Draft → Validate/Test → Publish；Agent/Model/Capability/ProjectPlatform direct-effect + revision/audit。  
**原因**：统一版本中心会导致状态机膨胀；Service 才是业务上线边界。  
**影响**：禁止 Agent publish API/UI；ServiceRelease 不可变。

## ADR-003 Service 创建必须选择主 Agent

`ServiceDefinition.primary_agent_id NOT NULL`。一个 Service 一个主 Agent，一个 Agent 可承载多个 Service。

该关系表示“谁负责这个 Service”，不同于 `AgentServiceBinding`（Agent 可以调用哪些子 Service）。

## ADR-004 ProjectPlatform 与 ProjectIntegration 分离

**ProjectPlatform**：DB/API/Console 业务对象，MSS/CRM/ERP，定义用户认证模板。  
**ProjectIntegration**：代码部署扩展，manifest/provider/adapter/seed/tests，不做普通 CRUD。

## ADR-005 Capability 是原子执行合同

Capability 独立于 Skill，可直接作为 Agent Tool 或 Service Step 使用。Contract 稳定，Implementation 可替换。V1 Implementation：Platform Service / HTTP / MCP / Sandbox。

## ADR-006 只有 Platform Service 绑定 ProjectPlatform

HTTP/MCP/Sandbox 不出现项目平台字段。它们如需认证，使用系统共享 Secret/Auth；不使用用户的 ProjectPlatform Credential。

## ADR-007 用户平台认证唯一键

V1 一个 PlatformUser 对同一个 ProjectPlatform 只有一套账号/凭据：

```text
UNIQUE(user_id, project_platform_id)
```

不引入“凭据实例名称/多账号切换”。

## ADR-008 Skill 是离线 Python 代码资产

Skill 不在 Console 编排。开发人员在 PyCharm/VS Code 编写传统 Python，支持 if/for/while、数据处理、业务算法、pytest 和断点调试。

## ADR-009 Skill Capability 依赖来自 manifest

`skill.yaml capabilities[]` 是事实源。Console 只读展示，不提供“绑定/解除能力”操作。平台导入时解析并建立查询索引。

## ADR-010 Skill 平台归属只是文本标签

`platform_label` 无 FK、无认证、无路由语义，只用于列表识别、筛选和 `/skills` 分组。真实项目平台依赖来自：

```text
Skill → Capability → ProjectPlatform
```

## ADR-011 Skill Artifact 不可变

导入新 Skill 版本创建新的 Artifact + checksum。历史 Artifact 不覆盖，已发布 Service 可继续引用旧 checksum。

## ADR-012 Skill SDK 同仓独立 package

V1 不要求公共 PyPI。SDK 与主仓库同仓，但必须形成独立 Public API 边界。Skill 禁止 import Runtime/Domain/Repository/Infrastructure 内部模块。

## ADR-013 Skill 开发双模式

- MockSkillContext：纯本地单测；
- Dev Capability Gateway：SDK 通过 HTTP 调真实开发环境 Capability；
- Production：Runtime 注入同语义 SkillContext。

同一业务代码不因环境修改。

## ADR-014 Capability 自动分页属于 Executor

分页不是 Skill SOP 逻辑，也不是 LLM 多次 Tool Call。Page/Offset/Cursor 由 Data Retrieval Policy 描述，Executor 内部循环。

## ADR-015 Page 分页结束策略

优先显式 has_more/total/cursor；items=[] 是 Page/Offset 兜底，必须有 max_pages/max_items/max_duration 和重复页检测。short_page_terminates 默认 true（既有产品裁决）；下游存在中间短页时必须允许显式关闭，只有保证非末页满页才能安全依赖短页终止。UI 保留 false 并随 DTO 原样保存，不能根据返回长度自动改写策略。page_size=100、第一页 30 条但第二页有数据的用例必须在 false 下完整读取。

## ADR-016 大结果不直接进入 LLM

对全量数据优先本地过滤/聚合；需要完整交付则写 Artifact/Object Store，LLM 只收到摘要和 artifact_ref。

## ADR-017 Channel 三关系分离

```text
ChannelIdentity: external_user_id → PlatformUser
ChannelAccount:  bot_id → Agent
AgentAccessGrant: PlatformUser → Agent
```

禁止合并为万能“用户渠道 Agent 绑定表”。

## ADR-018 WeCom V1 一个 Bot 一个 Agent

一个具体 bot_id 只绑定一个 Agent；新 Agent 需要新的 bot_id。一个 Channel Gateway 可以同时维护多个 Bot WebSocket。Bot WebSocket 长连接到 Gateway，不直接连接 Agent Runtime。

## ADR-019 `/bind` 只建立身份映射

BindCode 不含 bot_id/agent_id。用户通过某个 Bot `/bind` 后建立 ChannelIdentity。用户是否能访问该 Bot 对应 Agent 仍由 AgentAccessGrant 校验。

## ADR-020 IM 身份复用现有 User Tab

用户详情不新增“绑定码”独立 Tab；复用“IM 身份”，同时展示已绑定身份和 BindCode 管理。

## ADR-021 Builder/Admin 页面级权限优先

V1 不建设复杂 ABAC。Builder 负责定义/测试，Admin 负责用户、授权、用户 Credential、绑定码和正式发布。

## ADR-022 Knowledge 后置

Knowledge 保留规划入口，但当前不冻结 API、DB、Provider SPI。禁止为了“文档完整”编造未经评审的知识库字段。

## ADR-023 Async Task 统一纳入 Execution

Async 不是 Capability Implementation Type，也不设一级菜单。ExecutionStep 可有 `execution_mode=ASYNC` 和 AsyncTaskRun 明细，Execution Timeline 统一展示 Task ID/状态/结果。

## ADR-024 `/stop` 是 Execution/Run 取消

`/stop` 不删除会话、不换 Agent；取消当前 Run/Execution。异步 Provider 支持 cancel 时级联取消，否则停止后续执行并记录远端任务状态。

## ADR-025 `/new` 只创建新会话

Bot→Agent、User→Agent grant、IM identity 全部保持不变。

## ADR-026 `/skills` 只展示当前 Agent Skill

不展示全局 Skill Registry；按 Skill `platform_label` 分组。标签是产品分类，不作为执行路由。

## ADR-027 Console 不管理基础设施状态

PG/Redis/ObjectStore/SecretProvider/OTel 是外部运维依赖。无“系统设置”菜单展示依赖状态。列表每页条数在各列表右下配置，不设全局分页设置。

## ADR-028 Console 页面不重复大标题

左侧导航 + breadcrumb 足够表达页面上下文；页面正文直接从操作区/列表开始。字段含义通过字段说明/帮助 Drawer 解释。

## ADR-029 时间展示统一

Console 时间统一 `YYYY-MM-DD HH:mm:ss`；API/DB 保留时区语义。

## ADR-030 Execution 详情包含 Timeline

执行列表只保留“详情”入口；Timeline 在详情内，不再放重复“详情/时间线”两个按钮。

## ADR-031 Skill 与确定性 Workflow 分层

Skill = 短生命周期、Python 代码型/柔性 SOP；Service Execution = 需要持久状态、等待、审批、补偿、恢复的确定性流程。V1 不做 Skill 低代码 Designer。

## ADR-032 设计文档采用 design-full 详细模板

核心模块不能用概念摘要替代详细设计。至少包含：需求、规则/场景、范围、架构、数据、接口、DFX、部署、风险、追溯、Spec Compliance。交互/API/DB 字段必须可互相追溯。

## ADR-033 IM 命令走受信内部 Contract，不复用 Console API

Gateway 解析 /bind、/skills、/new、/stop 与人工"继续/终止"后，经 **CH-INT-02 内部命令 Contract**（service-to-service token）调用各领域 Application Service，注入真实 END_USER 身份与归属校验；不冒充 Admin 会话、不走 `/api/v1`（R06 裁决）。Console 管理权限（EXE-API-03/04/05）保留独立。

## ADR-034 Skill SDK 采用同步门面，异步宿主桥接

Playbook D05 上游合同是同步 `def run(ctx)`；SDK 公共 API 一律同步（`ctx.capability.call(...)` **直接返回 Capability 归一化输出本身**：列表能力返回数组、映射返回对象、标量返回标量，调用方可直接迭代/下标/过滤）（R12 裁决）。Skill 代码不感知 asyncio。

**宿主执行模型（R24 修订）**：宿主**不在事件循环线程内执行 Skill**。生产一律由 `SandboxExecutor` 的**隔离子进程**执行（ADR-035），宿主进程只处理 FD3/FD4 上的 RPC 帧；所谓“异步宿主桥接”指宿主的 async 事件循环与子进程的同步调用之间做 request/response 代理，**不是**“在宿主线程池里 import 并运行 Skill”。Local/Mock 模式（仅开发）可用进程内执行，但该路径在生产部署被禁用。

**Skill 调用路径的取数语义（R12/D3 修订）**：Skill 直调 Capability **禁用大结果外置**——始终返回归一化数据；超过 inline 阈值时按该 Capability 的 `data_retrieval_policy.limits` 截断并记录警告，**不得**用 `artifact_id` 摘要替代数据。需要完整大结果的场景必须走 Service Step（`execution_mode=ASYNC`）或 Artifact 路径，不使用 Skill 直调。Skill 入口必须是同步 `def run(ctx, input)`，声明 `async def` 或缺 `run` 在导入时即 `SKILL_ENTRYPOINT_INVALID`。

**Skill 不可提交 Async Capability**：异步外部任务只能由 Service Step 声明并由 Worker 提交（见模块 06/07），Skill 越界调用返回确定性错误，不静默阻塞。

## ADR-035 V1 生产沙箱后端 = 隔离子进程执行器

Local executor 仅开发；生产使用 SandboxExecutor 的隔离子进程实现（R24 裁决）：独立 user/mount/PID/IPC/network namespace、non-root + `no_new_privs` + seccomp、最小只读 rootfs（不挂宿主根/socket/`/proc`/home/Secret volume）、默认无外部网络路由（业务网络只经宿主 Capability RPC）、cgroup v2 + rlimit（CPU/内存/进程数/输出）、超时 SIGKILL + 进程组清理、父进程退出即回收。容器化后端留作 V2 演进，SandboxExecutor SPI 不变。

未配置隔离子进程后端时启动即失败（fail-closed），**禁止 fallback 到 Local**（`SANDBOX_ISOLATION_UNAVAILABLE`）。

## ADR-036 外部 Session 过期与长期凭据失效分离

AuthProvider 合同区分 materialize 失败原因：`SESSION_EXPIRED`（凭据有效，调 provider refresh 端点自动续期并回写 external_session_ref，按 provider 串行化）与 `CREDENTIAL_INVALID`（立即拒绝并标记，通知用户重新配置）（R11 裁决）。Execution 恢复时用 current Credential + 已刷新 Session。

## ADR-037 Memory 由 Runtime 受控写入，用户经 IM 自助治理

Memory 写入仅经 Runtime 的受控工具（显式用户请求"记住…"，带 source=agent_tool、MemoryPolicy 过滤），Console 写接口仅 Admin 管理；END_USER 通过 IM 命令 `/memory list|clear`（走 ADR-033 内部 Contract）查看/清理本人记忆（R16 裁决，承接 U06）。

## ADR-038 失败重试 = 新建关联 Execution，沿用已成功步骤幂等键

终态不可回退不变；EXE-API-04/RETRY 命令创建**新 Execution**（parent_execution_id 指向原执行，attempt+1），Step 级沿用原执行中已成功步骤的 idempotency_key（外部副作用不重做），从首个失败步骤继续（R07 裁决）。

## ADR-039 Draft 测试走草稿快照，正式执行走 Release 快照

SVC-API-06 测试执行创建 **Draft 快照**（draft_revision + content_hash 冻结），`service_execution.execution_source = TEST`、service_release_id 可空、不入正式执行统计；正式执行仍强制 current release（R02 裁决）。测试结果与草稿修订绑定，Draft 再修改后旧测试结果标记过期。

## ADR-040 人工等待与阶段进度由平台主动投递，不依赖编排

进入 `WAITING_HUMAN` 时，**平台在同一事务内预建恰好一条投递行**并推送一条 `human_wait` 通知，内容必须覆盖 Playbook U03 的六要素（发生了什么 / 影响哪一步 / 系统已经做了什么 / 为什么需要我处理 / 有哪些选择 / 不同选择意味着什么）。Service 若编排了承载提示的 DELIVERY 步骤，其文案**覆盖**平台默认文案、缺失的六要素由平台补齐，**合并为同一条消息**（不追加第二条通知）。阶段进度只推 STAGE 级与完成/失败，不推 PROGRESS 级（避免轰炸）。投递对象固定为该 Execution 的 `actor_user_id` 对应 DeliveryRoute，不得改投。END_USER 不进入 Console，因此该通路是 U03 的唯一可用出口。

## ADR-041 Capability Contract 携带分流与授权元数据

> **⚠️ 本条已被 ADR-057 取代（V1.13.1，第四轮 D1 裁决）**：`capability_definition` 的判定元数据收敛为 `side_effect`（四值）+ `risk_level` + 单一结论字段 `invocation_policy ∈ {DIRECT, EXECUTION_ONLY}`；`authorization_requirement` 与 `error_semantics` 已删除（凭据来源唯一由 `capability_implementation.auth_mode` 表达，失败分类以《10-错误码与错误分类基线》为唯一来源）。下方原文仅作历史溯源。

原文（已失效）：`capability_definition` 必须携带 `side_effect ∈ {none, read, write, destructive}`（四值，**不是布尔**）、`risk_level ∈ {LOW, MEDIUM, HIGH}`、`execution_characteristic ∈ {DIRECT_OK, WORKER_PREFERRED}`、`authorization_requirement ∈ {NONE, USER_PLATFORM, SHARED_SECRET, ADMIN_ONLY}`、`error_semantics`。Chat 直调与 Worker 可靠执行的分流**只由 Contract 元数据判定，不由 Capability 名称硬编码**（该原则仍然有效，见 ADR-057）。

## ADR-042 Worker 租约 TTL 必须覆盖最长步骤，长步骤必须心跳

`WORKER_LEASE_TTL_MS` 默认 300000（5 分钟），且必须 `>= max(step_timeout_ms)`；`WORKER_HEARTBEAT_INTERVAL_MS = TTL/3`。超过一个 heartbeat 周期未续租即视为失联，其他 Worker 可在租约到期后 reclaim。禁止在租约短于步骤耗时且无续租的情况下执行长步骤（否则会出现双 owner 与外部副作用叠加）。

## ADR-043 确认摘要与交付内容采用受控变量模板，渲染结果进入冻结与摘要

`confirmation.summary_template`、步骤级 `deliverable_template` 与 `deliverable.template` 使用受控变量语法（`${input.<path>}`、`${scope.<path>}`、`${steps.<step_key>.output.<path>}`），由确定性渲染器渲染，**不允许 LLM 参与渲染**。渲染结果随快照冻结、其 canonical hash 进入 `confirmation_digest`，并在发布校验时验证模板变量可解析。这样“用户确认了什么”才可复现、可举证。

## ADR-044 模型配置以秒为超时单位，支持非敏感额外请求头

`model_config.request_timeout_seconds`（秒，默认 60，范围 1..600）取代 `request_timeout_ms`；`extra_headers` 为 V1 支持的 JSONB 字段（仅非敏感 Header，禁止承载凭据；敏感 Header 走 SecretProvider 引用）。Console 与 DTO 单位一致，避免秒/毫秒换算导致的静默错误。

## ADR-045 Console 不提供会话管理，执行固定创建时投递路由

Console 不设会话页面（总设 §6.6 IA 无会话菜单），会话生命周期由 IM `/new`（CONV-LIB-02）与 Runtime 内部驱动；原 `CONV-API-01..04` 四个 Console 端点删除。Execution 创建时由可信上下文**固定写入 `delivery_route_id`**（总设 §4.4 的“服务端补充”），此后结果投递按该持久路由；用户换会话后用 `/result` 主动重取，不做“跟随最近活跃会话”的隐式改投。

## ADR-046 Builder 只读依赖选择采用安全只读 DTO

Builder 定义 Agent/Capability 必须能选择模型与项目平台，因此模型/平台**读接口对 Builder 开放**，但**列表**响应使用安全只读 DTO：模型可见 `id/key/name/protocol/model_name/enabled/revision/api_key_configured`，平台可见 `id/key/name/enabled/revision/configured`（`auth_type` 自 V1.13.1 起对 Builder 可见，它是 Provider 机器 key，不含凭据与模板）。

**列表与详情的边界（V1.13.1 澄清，见 ADR-058）**：从列表剔除 `base_url`/`default_parameters`/`extra_headers` 是**降低噪声与减少暴露面**，不是安全边界——`base_url` 与 `default_parameters` **不是凭据**。写接口改为字段级授权后（ADR-058），Builder 在**新增/编辑表单**必须能填写 `base_url`、`request_timeout_seconds`、`default_parameters`（否则无法创建模型）；真正仅 Admin 的是 `api_key`（Secret 引用）与 `extra_headers`（可能承载网关凭据）以及平台的 `auth_schema`。Builder 的**详情只读视图**按同一字段级口径输出，不再与表单自相矛盾。前端按钮可见性、字段可见性与后端授权列必须一致。

## ADR-047 Skill 发布审核在 V1 后置，风险显式接受

总设 §5.1 要求 Skill 具备 publisher/scope/publish review 治理。V1 **不实现发布审核**（不做审核态、不做审核人角色、不做范围治理），缓解手段限定为：manifest/entrypoint/依赖/供应链静态扫描 + checksum + 不可变 Artifact + 生产隔离子进程执行 + 导入与使用审计。**“Builder 导入即在租户内可用（current 切换）”是 V1 显式接受的产品风险**；当出现多团队共享租户或外部 Skill 供给时，必须引入审核态与范围治理。

## ADR-048 执行详情展示脱敏资源范围摘要

Playbook A04 要求排障能回答“哪个客户”。`ExecutionView`/`ExecutionSummary` 增加脱敏 `resource_scope_summary`（`{type, refs[], labels?}`，`refs` 直接取 `resource_scope.refs`，见 ADR-050；仅 Builder/Admin 可见），`EXE-API-01` 支持按范围引用（`scope_ref`）筛选。原始 `attributes` 不进入摘要。

## ADR-049 提案与确认摘要的最小契约

（第四轮 Q-04 / Q-10 裁决）

1. **状态两态**：`execution_proposal.status ∈ {PENDING, CONFIRMED}`；“过期”按 `expires_at <= now` 派生、“被取代”按 `superseded_at IS NOT NULL` 派生，**两者都不进状态机**（partial unique 已保证同会话唯一 PENDING）。
2. **摘要只覆盖结构化事实**：`confirmation_digest = sha256(tenant|actor|service_release|input|resource_scope|template_hash|expires_at)`。`rendered_summary` 是“模板 × 上述输入”的确定性函数，纳入摘要不增加绑定力，只把“渲染必须成功”变成确认链路上的硬失败点；模板版本由 `template_hash` 表达。渲染结果仍随快照冻结并展示。

## ADR-050 `resource_scope` 收敛为最小 typed 形态

（第四轮 D5 裁决）`resource_scope = {type, refs[], attributes?}`：`type` 白名单来自当前部署 Integration manifest 的 `resource_scope_types`（**内存投影、装配期校验、不落库**）；`refs` 即对外展示与筛选使用的范围引用；`attributes` 仅允许该类型声明的字段。**取消** Service 级 scope JSON Schema、`schema_hash` 与“按 Registry 类型元数据投影”的脱敏规则——V1 只有一个参考 Integration，泛化留待第二个 Integration 接入（总设 §9.9 的判断机制）。

## ADR-051 「当前阶段」必须展示业务可读名

（第四轮 B2 裁决）`ExecutionSummary`/`ExecutionView` 增加 `current_step_name`（取 snapshot 中该 step 的 `name`，终态取最后一条 STAGE 事件的 `stage`）。列表与详情的「当前阶段」列渲染它；`current_step`（step_key）只作技术标识（筛选/跳转/hover）。不允许把内部 key 直接当业务文案展示（Playbook 要求“用业务阶段展示进度”）。

## ADR-052 Builder 的执行可见范围

（第四轮 D6 裁决）`service_definition` 增加不可变 `created_by`。执行列表/详情可见范围：**Admin = 当前租户全部；Builder = 自己创建的 Service 的执行 ∪ 自己被授权 Agent 相关的执行**。越界不是 403 而是**视为不存在**（`EXECUTION_NOT_FOUND`），避免泄露“某个执行存在”这一事实。发布/转交不改变 `created_by`。

## ADR-053 产物访问判定以 `artifact` 表为准

（第四轮 B6 裁决）产物访问校验一律 **join `artifact` 表**（以 `execution_id`/`execution_step_id` FK 与同 root/actor 为准）；`service_execution.artifact_ids` / `execution_step.artifact_ids` 数组**只记录“重试复制来源”**，不作为访问判定的唯一依据（数组无法 FK，清理后会留下悬空 ID）。已清理的产物一律 `ARTIFACT_EXPIRED`(410)，不因数组残留而放行。

## ADR-054 「重新投递」与「重新执行」是两个动作

（第四轮 D4 裁决）冻结交互稿里的「重试」按钮按投递状态门控，实际指的是**重新投递**；而设计原有的 `EXE-API-04` 是**重新执行**。两者语义不同、代价不同，必须拆开：

- **重新执行**（`EXE-API-04`）：仅 `status=FAILED`，新建关联 Execution、沿用已成功步骤的幂等键，Admin 执行；
- **重新投递**（`EXE-API-07`）：仅 `delivery_status ∈ {FAILED, UNKNOWN}`，**不重跑任何业务步骤**，只新建一次投递尝试，Admin 执行；`UNKNOWN` 情形可能造成重复通知（产品已接受的语义，前端须二次确认并说明）；
- END_USER 不重试、不重投：用 IM `/result` 主动取件；**用户自助重试（IM `/retry`）与 Admin 查看来源会话消息在 V1 显式后置**。

## ADR-055 步骤级人工介入策略 `human_policy`

（第四轮 B11 裁决）`ServiceDraft.steps[].human_policy ∈ {never, on_uncertainty, always}`（默认 `never`），与 `failure_policy` **正交**：

- `always`：编译器在该步骤**之前**插入一个 HUMAN 检查点，消费后继续原步骤；
- `on_uncertainty`：允许该步骤在语义不确定、业务拒绝或达自动恢复上限时转 `WAITING_HUMAN`；**不得**仅因技术故障转人工（技术故障按错误分类处理）；
- `never`：禁止本步转人工，命中时按 `failure_policy` 收敛。

Service 级 `confirmation.required` 仍只决定“发起前是否需要用户确认”。冻结交互稿的「人工介入（否/必要时/始终）」映射为 `never/on_uncertainty/always`。

## ADR-056 集群级 Resource Class 槽位用 PG 信号量

（第四轮 B4 裁决）`browser` / `external-scan` / `large-report` 三类槽位改为**集群级 PG 信号量**（`worker_slot_lease` 协调表：`INSERT ... ON CONFLICT DO NOTHING` 抢占槽位号，lease 过期即视为释放），其余 Resource Class 保持单 Worker 进程内计数。理由：这三类对下游有真实压力或外部副作用，进程内计数会让实际并发 = 上限 × Worker 数；`worker_slot_lease` 是**协调表而非业务事实表**，可清空重建。

## ADR-057 Capability 判定收敛为单一结论字段

（第四轮 D1 裁决）`capability_definition` 保留 `risk_level` 与 `side_effect`（none/read/write/destructive）作为**安全与审计维度**，新增单一结论字段 `invocation_policy ∈ {DIRECT, EXECUTION_ONLY}`（命名为 `invocation_policy` 而非 `execution_policy`，以与 implementation 层的超时/重试策略 `execution_policy` 消歧）；**删除** `execution_characteristic`、`authorization_requirement`、`error_semantics`。理由：三维组合的结论只有两类，把组合责任推给每个 Capability 作者与每个调用方会漂移；`error_semantics` 是运行时分类的冗余声明；`authorization_requirement` 与 `capability_implementation.auth_mode` 重复表达同一件事（凭据来源唯一由 `auth_mode` 表达）。直调判定谓词（`side_effect ∈ {none,read} AND risk_level ∈ {LOW,MEDIUM} AND invocation_policy=DIRECT`）**只在模块 07 定义一次**，其余调用方只比较 CAP-API-06 返回的派生字段 `direct_invocation`。

## ADR-058 模型与项目平台采用字段级授权

（第四轮 D2 裁决）模型与项目平台的**写操作对 Builder 开放**，敏感字段**仅 Admin 可写**：模型 `api_key`、平台 `auth_type`/`auth_schema`。非 Admin 请求中出现敏感字段一律 `FIELD_ADMIN_ONLY`(403) 并**原子拒绝**（不部分写入）。理由：Builder 定义 Agent 必选模型、定义 PLATFORM_SERVICE 必选平台，整接口 Admin-only 会形成审批瓶颈（与冻结交互稿的角色矩阵、ADR-021 原始分工都不一致）；而真实敏感面只有那两个字段。读投影仍用安全只读 DTO（ADR-046），Builder 可见 `auth_type`（机器 key，不含凭据与模板）但不可见 `auth_schema`。

## ADR-059 用户角色的三条守卫

（第四轮 Z-12 裁决）`USR-API-04` 必须实施：① 不接受修改**当前登录用户自己**的 `role`（`SELF_ROLE_CHANGE_DENIED` 403）；② 角色提升为 `ADMIN` 需前端二次确认；③ 禁止降级或停用**最后一名启用状态的 Admin**（`LAST_ADMIN_PROTECTED` 409）。理由：`role` 是 Console 唯一的权限承载字段，误操作可直接锁死 A01 发布 / A02 授权旅程。

## ADR-060 Console 运行面数据通路保持 agent-runtime 承载

（第四轮 D3 裁决）`CH-DATA-01..04` 与 `CH-INT-02` 继续由 **agent-runtime** 承载（V1.13 的 N01 修复），但必须显式声明可用性合同：这些端点是**运行面**（只读、幂等、可安全重试），与 platform-api（管理面）进程与依赖分离，管理面停机不影响它们；agent-runtime 故障时 IM 入站与投递许可不可用，但已创建的 Execution 仍由 Worker 推进，投递行保留并在恢复后由 `WORK-LIB-06` 继续调度。**备选与触发条件**：若“agent-runtime 故障”成为 IM 可用性的真实瓶颈，则为 Gateway 增加受限只读 DB 角色（只读视图 + account scope 行级过滤）；在此之前不放开 Gateway 直连业务库。
