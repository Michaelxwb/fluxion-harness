# 数据保留与清理策略（V1.13）

> 第四轮合理性 Review 的 B3/Q-06 修复：**每类数据都必须有保留期与清理触发者的 Owner**，否则对象存储与元数据行会无界增长，而"保留多久"由实现者随手决定。
> 本文件的期限是**V1 默认值**，可由部署配置覆盖（`RETENTION__*` 环境变量）；任何期限变更必须同步本文件与对应模块的约束段。
> 清理**一律软删优先**：置 `is_deleted=true`（或状态置终态）并写审计；Object Store 的物理删除由 GC 在软删后延迟执行，且必须先确认无引用（`INFRA-LIB-06`）。

## 1. 清理触发者与责任划分

| 角色 | 职责 | 禁止 |
|---|---|---|
| 各领域模块（Owner） | 定义本模块数据的保留期与"何时标记为可清理" | 不自行决定其他模块数据的期限 |
| **维护任务（Maintenance Job）** | 唯一的批量清理执行者：按本表扫描、软删、调用 `INFRA-LIB-06/07` 回收对象与 Secret、写审计与指标 | 不做跨租户越权删除；不删未到期数据 |
| Worker Engine | 只负责 `channel_delivery` 的投递重试调度（outbox），**不做数据清理** | — |
| `14-存储与基础设施适配` | 只提供 `delete_object` / `delete_secret` 能力 | 不决定"何时删" |

- 维护任务是**独立运行角色 `maintenance`**（与 worker 同镜像、不同 entrypoint `maintenance`；独立副本数 =1、独立 PG 连接池、独立开关 `MAINTENANCE_ENABLED`），复用 PG 作为事实源；Worker 进程内**不跑**任何清理循环，只留投递调度（WORK-LIB-06）。清理失败只影响 maintenance 自身，不抢 Worker 的连接与 CPU。
- 所有清理必须输出指标：`retention_deleted_rows{table}`、`retention_gc_bytes`、`retention_job_failed`；清理失败**不得**影响执行主链（best-effort + 次日重试）。

## 2. 保留期限表

| 数据类 | Owner 模块 | V1 默认保留期 | 到期动作 | 备注 |
|---|---|---|---|---|
| `execution_proposal`（PENDING） | 05 | `expires_at`（默认 300s） | 视为过期（派生判定，不新增状态）；行保留 30 天 | 见 ADR-049 的状态收敛 |
| `execution_proposal`（CONFIRMED） | 05 | 与关联 Execution 同龄（见下） | 随 `service_execution` 一起软删 | 保留作为"确认了什么"的证据 |
| `task_progress_event` | 05 | 90 天 | 软删 | Timeline 查询按 `occurred_at` 分区/索引 |
| `execution_command` | 05 | 与 Execution 同龄 | 随 Execution 软删 | — |
| `execution_step` / `service_execution`（FORMAL） | 05 | **365 天** | 软删（`result_ref`/`artifact_ids` 保留元数据） | 审计与排障诉求；可按租户配置缩短 |
| `service_execution` / `execution_snapshot`（TEST） | 05 | **30 天** | 软删 | 测试数据量大、价值低；快照按 `(service_id, source, content_hash)` 去重，只随最后引用过期 |
| `async_task_run`（`SUBMITTED_UNKNOWN` 悬挂行） | 05 | 到达 `reconcile_deadline` 后 **7 天** | 置 `FAILED(SUBMISSION_UNCONFIRMED)` 并软删 | **必须有终局**，不允许永久悬挂 |
| `artifact`（Object Store 对象） | 05 | 跟随其 Execution 的保留期；`artifact_type=REPORT` 可单独延长至 730 天 | 软删元数据 → GC 删对象 | 删除后 `EXE-API-06` 返回 `ARTIFACT_EXPIRED`(410)（已冻结语义） |
| `conversation_run` / `channel_command_receipt` | 11 | 90 天 | 软删 | 幂等回执过期即失去意义 |
| `message` / `conversation` | 11 | 365 天（会话历史） | 软删；`conversation` 仅在无未删 message 时软删 | 大表按 `conversation_id, create_time` 索引/归档 |
| `channel_delivery`（终态：DELIVERED/FAILED） | 10 | 90 天 | 软删 | UNKNOWN 行在 7 天后转 FAILED 再按此规则 |
| `audit_log` | 15 | **不自动删除**（append-only） | 仅归档，不软删 | 合规诉求；容量由运维治理 |
| `skill_import_preview` | 08 | 30 分钟（未提交） | 删暂存对象 + 置 EXPIRED | 已冻结 |
| `skill_artifact`（旧版本） | 08 | 只要仍被 Service 快照或 Agent 绑定引用则保留；否则 **365 天**后软删元数据 → GC 删包 | 软删 + GC | 「旧版本保留」不等于"永久保留" |
| `workspace` | 13 | 按 `expires_at`（已有字段） | 过期即清理根目录对象并软删 | 正式 Artifact 必须先持久化再清理临时 Workspace（总设 §5.1） |
| `user_project_credential` 的旧 `credential_ref` | 09 | 轮换后 **7 天** | `INFRA-LIB-07` 删除旧 Secret | 补偿清理，避免旧凭据残留 |
| `model_config` 的旧 `api_key_secret_ref` | 19 | 轮换后 **7 天** | `INFRA-LIB-07` 删除旧 Secret | 同上 |

## 3. 硬约束

1. **引用优先**：任何清理前必须确认无引用（`OBJECT_STILL_REFERENCED` / `SECRET_STILL_REFERENCED`）；`service_release` 与 `execution_snapshot` 引用的 Artifact **不得**先于发布版本删除。
2. **审计不可删**：`audit_log` 与"发布/授权/凭据/停用"相关事实只归档不删。
3. **测试数据不污染统计**：`execution_source=TEST` 的清理**不得**影响 FORMAL 聚合（OPS-API-04 已按 FORMAL 过滤）。
4. **软删唯一约束**：清理使用软删时，重建同名资源必须能成功（依赖各表的 partial unique，见 `08-数据库表所有权与字段索引`）。
5. **容量兜底**：若某租户的 Artifact/对象存储连续 7 天超过配额阈值，维护任务必须产生告警（`retention_quota_exceeded`），但不自动删除未到期数据。
6. **不做自动清理的例外**：`audit_log`（仅归档）。若某部署选择"不自动清理执行历史"，必须显式配置并把容量风险写入运维文档——默认策略是**清理**。

## 4. 各模块的引用义务

模块文档在涉及上述数据时必须：
- 引用本文件（例如「保留与清理按《11-数据保留与清理策略》执行」）；
- 不自行声明与本表冲突的期限；
- 新增持久化数据时**必须**在本表补一行（否则视为设计未完成）。
