## 尚未闭合及新增发现

### R01 [P1] 签名提案没有接上下一轮真实用户确认事实

[CORE-LIB-04](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/01-核心领域与发布模型/design-full.md:221)已补输入、HMAC、摘要和 TTL；但 [Proposal Builder](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/04-Agent-Core与Agent-Executor/design-full.md:942)仍只构造候选，[Chat 入站](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/03-Agent-Runtime/design-full.md:191)没有提案确认的专门投影/定位合同。

**仍需修订**：confirmation_ref 的签发者、待确认提案的保存位置、跨 Pod 如何取回、如何把一条真实用户确认消息绑定到 proposal/actor/tenant/service 没有定义。摘要列只列 input、范围、release_no 和模板；签名有效不能单独证明此用户已经同意。conversation_id 缺失可以由可信 context 补，但当前也未明确该绑定。成功后写 Execution 审计解决不了确认前的取回。

**修正方向**：明确 Proposal 的签发/保存/取回/确认消费 Owner；把用户、租户、服务、版本、输入、范围、截止时间与真实确认事件绑定，和 Execution 创建原子幂等。可用现有持久消息或签名载荷，不强制新增表。

**最小验收**：Runtime A 给出提案，A 退出，用户在 B 说“确认”；只能启动本人确认的同一服务/版本/输入；复制另一用户或另一服务的 ref 必须拒绝。

### R02 [P1] Draft 测试仍无法同时满足快照与执行表约束

[测试补充合同](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/05-Service与Execution/design-full.md:963)允许 TEST 无 Release；[execution_snapshot](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/05-Service与Execution/design-full.md:274)和 [service_execution](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/05-Service与Execution/design-full.md:301)的 service_release_id 列仍均标 N。

**仍需修订**：补充段只声明 service_execution 的 TEST 例外，execution_snapshot 仍无合法的 Draft 来源字段/非空例外与去重键；因此新服务的首次测试快照仍无法按表定义落库。另外 DRY_RUN 是 HTTP 入参，持久执行/快照/Capability context 未定义该模式的传递，Worker 恢复后如何强制不产生真实副作用仍无合同。

**修正方向**：统一两张 Owner 表的 FORMAL/TEST 判别及条件约束、Draft 快照去重身份；持久化测试模式并传到每层调用。同步测试过期标识和统计排除规则到实际 View/聚合合同。

**最小验收**：无 current release 的 Service 可创建 TEST 快照；DRY_RUN 在 Worker 重启后也只调用 mock/dry Provider；草稿修改后旧结果可识别，正式统计不包含它。

### R03 [P1] 快照优先级有了，投影传递和 Agent 冻结仍未接通

[Skill 执行流程](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/08-Skill-Runtime/design-full.md:791)和 [模型执行流程](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/19-模型配置与调用/design-full.md:596)已改为冻结优先；但 [Agent Resolver](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/04-Agent-Core与Agent-Executor/design-full.md:798)仍按 current references 装载 Prompt/绑定。

**仍需修订**：ExecutionProjection 只出现在处理说明中，没有冻结结构/创建方及到 AgentExecutionContext、SkillContext、TrustedExecutionContext 的映射。SkillRunner 签名没有 frozen checksum，SkillContext 也没有投影字段。尤其 Agent instructions、绑定和 MemoryPolicy 的旧投影还没有独立入口。不能再报“Skill/Model 无条件取 current”，但也不能判定 Gate C/A05 已闭合。

**修正方向**：冻结投影字段及创建/消费签名；Worker 的 Agent 解析使用 snapshot 投影，Chat 解析使用 current；显式说明缺快照时拒绝执行，安全禁用/授权仍实时。

**最小验收**：Execution 等待时修改 Agent instructions、解绑旧 Skill 并导入新版本、修改模型参数，再恢复：业务逻辑仍用原快照，撤销授权/紧急禁用则拒绝。

### R04 [P1] 新增 claim 分支没有排除其他 Worker 的有效租约

[逐状态 claim 表](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/06-Worker-Engine/design-full.md:230)将 CANCELLING 设为无附加条件，WAITING_HUMAN 只看动作/deadline；[取消接口](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/05-Service与Execution/design-full.md:1330)可在原 Worker 工作中把状态改为 CANCELLING。

**仍需修订**：A 持有未到期 lease 时取消请求改变状态，B 即可匹配 CANCELLING 并覆盖租约。WAITING_HUMAN claim 又声明不切 RUNNING，提交事务后 B 仍可再次匹配同一行。SKIP LOCKED 只保护 claim 事务，不替代提交后的有效租约判定；这会破坏同一执行只有一个 owner 的规则。

**修正方向**：所有 claim 分支先应用统一的 lease 为空/已过期前提；活动 owner 接收命令时定义不抢租约的处理路径。WAITING_HUMAN 扫描/决策需要同样的占有与版本检查，避免两个 owner 同时应用。

**最小验收**：A 持有效租约时提交 CANCEL，B 不得抢走；两 Worker 同时处理一个人工 deadline 时只产生一次终态迁移/命令应用。

### R05 [P1] 人工审批移走错误逻辑后，没有补完整的正确逻辑

[人工审批接口](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/05-Service与Execution/design-full.md:1398)现在停在请求/响应/错误表；[总设 Human Checkpoint](/Users/jahan/workspace/fluxion-harness/docs/00-总体设计/01-通用智能服务执行框架-V1.8-完整总体设计说明书.md:3855)明确不做改参。

**仍需修订**：未定义在什么事务写 execution_command、requested_action、决策人及时间，Worker 如何释放 Human Step 并继续。接口仍接收“审批输入”，而总设禁止改参；context_summary 没有 DTO/持久化来源（human_prompt 只补了提示词）。与 deadline 同时到达时按收到时间还是 Worker 应用时间裁决、重复提交返回同 command 还是状态错误也未定。

**修正方向**：补完整 RESUME/CANCEL 的持久化、状态与幂等合同；明确 input 仅为不改执行参数的确认元数据或删除它；冻结审批上下文摘要及超时竞争裁决。

**最小验收**：决策与 deadline 并发、重复决策、过期决策均有唯一结果；用户能看到实际待批准操作，RESUME 不得偷偷改变已确认输入。

### R06 [P1] IM 命令幂等键会吞掉后续合法操作，STOP 仍漏 Chat Run

[内部命令合同](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/10-Channel-Gateway/design-full.md:806)已经替代冒用 Console 身份的方向，但规定所有命令按 (platform_user_id, command, execution_ref) 幂等。

**仍需修订**：NEW、MEMORY_CLEAR 没有 execution_ref，因此同一用户第二次 /new 或清理另一个 key 与第一次共享幂等身份；键也未包含 agent/conversation/payload 或渠道消息 ID。STOP 只路由模块 05 的 Execution，当前实时 Chat Run 仍无定位与取消合同。RULE-CHAN-06 还保留 /stop→EXE-API-03 的旧说明。

**修正方向**：以真实入站消息/命令请求 ID 作为幂等身份，绑定 tenant、actor、目标和参数摘要；区分消息重放与用户再次操作。明确 STOP 对 Chat Run/Execution 的目标选择和内部应用路径，回写旧路由规则。

**最小验收**：同一消息重放只生效一次，两条不同 /new 各建新会话；先 clear A 再 clear B 均有效；没有 Execution 的长 Chat Run 也可被本人停止。

### R07 [P1] 新建重试 Execution 没有覆盖失败/未知副作用身份

[重试接口](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/05-Service与Execution/design-full.md:1335)已选定新执行并复制成功步骤结果；[ADR-038](/Users/jahan/workspace/fluxion-harness/docs/00-总体设计/03-核心设计决策.md:181)也保持原执行终态。

**仍需修订**：合同只明确沿用“已成功步骤”的幂等键。真正需要重试的失败步骤可能已经提交外部副作用、仅结果响应丢失；新 Execution 的失败 Step 如何沿用原 key/async_task_run 或进入对账没有定义。请求 from_step 与“从首个失败步骤继续”也不一致；流程直接创建新执行，响应却仍只有 command_id/PENDING，无法按响应定位新执行。

**修正方向**：冻结重试派生事务，明确成功结果、失败/未知步骤的外部调用身份和恢复规则；定义 from_step 的允许边界及重复请求语义；返回 new_execution_id/parent_execution_id，并统一 command 是否存在及 Worker 是否再创建。

**最小验收**：外部提交成功、本地响应丢失后重试：只恢复/对账同一外部任务，不新建副作用；前端从重试响应可打开正确的新执行。

### R08 [P1] WAIT 进了 Schema 和 DB 枚举，仍没有 Worker 执行分支

[Draft Schema](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/05-Service与Execution/design-full.md:818)和 execution_step 已加入 WAIT；[Worker dispatch](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/06-Worker-Engine/design-full.md:310)仍只有 Capability/Agent/Human/Delivery。

**仍需修订**：未说明 wait_seconds 如何首次换算持久 wait_until/next_run_at，以及恢复时避免重新计时。新 Schema 还没有承接前端必填步骤名称、可选说明，failure_policy 是 FAIL_FAST/SKIP_ON_ERROR/RETRY，而交互仍有 wait/manual；output_var 与 ${steps.<key>.output} 的关系未定，Scope Schema 的可编辑字段与 Registry 只读 hash 也没有映射。

**修正方向**：补 WAIT executor 的进入/释放租约/到期推进；把编排表单每个字段映射到 DTO，明确失败转人工的受支持语义和引用规则。

**最小验收**：保存含 Wait 的真实前端 payload，等待中重启 Worker 后按原截止时间继续；选择 wait/manual 失败策略能得到合法可验收的状态迁移。

### R09 [P1] 失败投递不能再次发送，超时防重保证也没有成立

[Gateway 投递处理](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/10-Channel-Gateway/design-full.md:897)只接受 PENDING，其他状态幂等返回；[Worker 重试合同](/Users/jahan/workspace/fluxion-harness/docs/02-模块设计/10-Channel-Gateway/design-full.md:902)却要求 FAILED 行再次调用。

**仍需修订**：FAILED→PENDING 的原子重试转换没有定义，按现有合同重试只会返回旧失败。结果未知时保持 PENDING，远端若已发送而本地 ACK/落库丢失，再次发送仍会重复通知；本地 dedupe_key 唯一只防新建行，不防同一行第二次对外发送。DB 的 dedupe 示例还没加入 route/event_seq；新的拼接键使用 UUID 与最长 step_key 时也可能超过 VARCHAR(128)。

**修正方向**：定义每次 attempt 的领取、状态转换、计数/退避/上限；明确远端可用幂等/ACK 对账能力与超时未知策略，不能把本地唯一约束描述为端到端恰好一次。统一 dedupe 组成及有界编码长度。

**最小验收**：第一次明确失败后第二次能真实发送；“远端已发送但本地结果丢失”有明确去重或允许重复的产品语义；最大长度输入不触发数据库长度错误。
