# 设计合理性 Review（第四轮，2026-09-12）

## 结论

**不是"都最优"。** 但需要分清层次，否则会误伤正确的设计：

| 层次 | 判定 |
|---|---|
| **架构主干**（PG 为执行 SoT、Service 唯一发布单元、无状态 Runtime、Capability Contract/Implementation 分离、Chat≠Execution、Skill=离线 Python+不可变制品、明确后置 Workflow/Approval/Knowledge） | **合理，不建议改**。这些选择有上游依据（含 DBOS/Restate 实测教训），在当前 V1 范围下没有更优替代 |
| **机制层**（辅助表、状态机、lease 实现、元数据、生命周期） | **存在 16 处次优**：复杂度超过价值、同一机制两处实现、未验证抽象、缺生命周期 owner。附替代方案 |
| **交互契约层**（设计 vs 冻结交互稿 `fluxion-console-interaction-prototype-v0.8-final.html`） | **14 处行为级分歧**，其中 7 处需要产品裁决或回写原型；另有 3 处是本轮（V1.13）修复**新引入**的偏差，需要一并处理 |

**"最优"本身不可证明**，本报告给的是三档判断（不合理 / 次优 / 合理）+ 具体替代方案 + 以哪边为准。判定口径：**成本（表/状态/接口/测试面/认知负担）是否与其服务旅程的价值相称**；**是否在只有一个参考实现（MSS + Demo）时就冻结了通用抽象**；**是否与上游旅程/原型的可观察行为一致**。

> 与前三轮的关系：前三轮全库审查查"有没有承接"（其 25 + 60 条发现的编号索引与闭环记录分别见 `05-变更记录/08-V1.12.1-复审修复与收尾.md` 与 `05-变更记录/09-V1.13-第三轮Review裁决修复.md` 的附录），本轮查"承接的东西本身对不对"。为避免重复，本轮不报命名/登记/索引类问题，只报**会导致行为错误或成本失衡**的项。

## 一、需要你裁决的设计取舍（有真实 tradeoff，我不替你决定）

### D1 [高] Capability 判定：三维元数据 vs 直接给结论

- **现状**：`02-模块设计/07-Capability-Runtime/design-full.md:195-210` 现在有五个判定字段——`risk_level`、`side_effect`(4 值)、`execution_characteristic`、`authorization_requirement`、`error_semantics`；`04:906` 的分流规则要求实现者自己组合（`side_effect ∈ {none,read}` **且** `risk ∈ {LOW,MEDIUM}` **且** `characteristic=DIRECT_OK` 才可直调）。
- **为什么不是最优**：(a) 三维笛卡尔积 4×3×2 中真正有意义的结论只有两类（可直调 / 必须可靠执行），却把组合责任推给每个实现者与每个未来的 Capability 作者；(b) `error_semantics` 是**声明性冗余**——重试分类的事实来源是运行时 Provider 错误（`06` RULE-WORK-04 已定），声明"可能返回哪些分类"不改变任何判定；(c) `authorization_requirement` 与 `capability_implementation.auth_mode`（USER_PLATFORM/SHARED_SECRET/NONE）**表达同一件事**，两处声明必然漂移；(d) `error_semantics` 还是 JSONB 自由键值，与自家 `04-数据库设计基线` §5「不得用 JSONB 替代受 Schema 约束的字段」的精神冲突。
- **备选**：
  - **A（推荐）**：收敛为**一个结论字段** `execution_policy ∈ {DIRECT, EXECUTION_ONLY}`（由安全校验兜底：`write/destructive` 或 `HIGH` 一律不得 DIRECT），保留 `side_effect`/`risk_level` 作为**审计与安全校验**维度，删除 `error_semantics` 与 `authorization_requirement`（授权统一由 `implementation.auth_mode` 表达）。
  - **B**：保持现状，但把"何时可直调"写成一个**共享判定函数**（Core Library）而不是散文规则，消除实现者组合责任。
- **建议**：A。收益是删掉 2 个字段 + 1 个 JSONB + Console 上 2 个新控件；代价是需要改 Console 表单（原型本来就没有这几个控件，见第三节第 4 条）。
- **影响面**：`07` 表/DTO/CHECK、`04` 分流、`08` 数据库表所有权索引、FE-04、90-规格 §4.1。

### D2 [高] 模型/项目平台写权限：Admin-only 是否造成 Builder 关键路径阻塞

- **现状**：`02-模块设计/README.md:61` 的全局 RULE 把「模型/项目平台」写入列为仅 Admin；`09`/`19` 的写接口已收紧；Builder 只能用安全只读 DTO 选择依赖。
- **为什么可能不是最优**：Agent 定义**必选**模型（`04:91`）、PLATFORM_SERVICE 能力**必选**项目平台（`07:247`），因此 Builder 的每一步定义都依赖 Admin 先建好模型/平台 → 形成审批瓶颈；而冻结原型（`HTML:283` 角色矩阵）明确写「服务/智能体/能力/Skill/模型/项目平台 → Builder：创建、配置、测试」，ADR-021 原始分工（`03-核心设计决策.md:113-115`）也只把**用户/授权/Credential/绑定码/正式发布**划给 Admin，并未包含模型/平台。
- **备选**：
  - **A（推荐）**：**字段级保护**而不是整接口收权——模型/平台由 Builder 可创建/编辑，但 `api_key`（写 Secret）与 `auth_type/auth_schema`（认证模板）仅 Admin 可写；读取时 Secret 永不回显。
  - **B**：保持 Admin-only，但在 Console 用"待 Admin 配置"占位并在申请流程上给出 SLA（增加组织成本）。
- **建议**：A。安全目标（Secret 不外泄）用字段级即可达成，不需要把整个资源的管理权收走。
- **影响面**：`README:61` RULE、`09`/`19` 授权列、FE-07/08 角色段、原型角色矩阵。

### D3 [中] Gateway 运行面数据通路：agent-runtime 代管 vs Gateway 只读库

- **现状**：`10:152` 规定 Gateway（Node）不直连业务库，Bot 配置与短时 SecretLease、入站解析、发送许可、附件取流全部经 agent-runtime 承载的 `CH-DATA-01..04`。
- **为什么可能不是最优**：这使 agent-runtime 从"无状态实时计算服务"扩张为"领域数据网关"——它要装配 Channel/Conversation/Execution 的 Application 与 PG Repository（`03:141`），并成为 IM 入站与投递的**同步依赖**（agent-runtime 滚动升级/故障会影响 Bot 配置读取与投递许可）。原先 Worker→Gateway 的投递链，现在多跳一层。
- **备选**：
  - **A**：给 Gateway 一个**受限只读 DB 角色**（只读视图 + account scope 行级过滤 + 只读事务），直接 `CH-DATA-01/03/04` 的读；写仍走 Python 侧。
  - **B（现状）**：agent-runtime 代管（好处：单一数据访问实现、Node 不写 SQL、scope 校验集中）。
  - **C**：把 CH-DATA-* 放在一个新的轻量运行角色（edge-api），职责单一但多一个镜像。
- **建议**：若把"运行面可用性优先"排在"技术栈整洁"之前，选 A；若把"只有 Python 侧拥有领域数据访问"视为硬约束，选 B。**这条需要你定调**，因为它决定 agent-runtime 的部署敏感度与 Gateway 的故障域。
- **影响面**：`01-架构基线` 角色表、`10` CH-DATA-01..04、`03` 装配段、Gate H 场景。

### D4 [高] "重试"一词在两个语义间摇摆，且原型要的"投递重试"没有 API

- **现状**：设计里"重试"= **执行重试**（`05:1609-1621` EXE-API-04，新建关联 Execution、沿用已成功步骤幂等键、仅 Admin）；冻结原型里"重试"= **投递重试**（`HTML` openExecution：「重试」按钮仅在 `投递状态=投递失败` 时可用；`90:662` 又把交付写成"UNKNOWN 不触发业务重试"）。
- **为什么是问题**：(a) 用户点同一个按钮期望两件事；(b) 设计的投递重试是**自动**的（`06` WORK-LIB-06 有界重试 + UNKNOWN 不自动重发），因此原型那个按钮**在设计中没有任何 API 可调**——这是设计缺口而非纯文案问题。
- **备选**：
  - **A（推荐）**：拆成两个明确动作——「重新投递」（新增 `EXE-API-07`，仅对 `delivery_status ∈ {FAILED, UNKNOWN}`，Admin，触发一次新的投递 attempt，遵守 `attempt_token`/epoch 语义）与「重新执行」（现有 EXE-API-04，仅对 `FAILED`）。
  - **B**：删掉原型的投递重试按钮，改为"用户 `/result` 主动取件"（当前设计已有）。
- **建议**：A。运维排障（Playbook A04）确实需要"结果没送到，再送一次"。
- **影响面**：`05` 新增接口、`10` 投递状态迁移、FE-10 两个按钮文案与门控、原型回写。

### D5 [中] `resource_scope` 在只有一个参考实现时冻结为通用抽象

- **现状**：`05:1253` 定义 `resource_scope` 为业务输入范围 Schema，配 Scope Registry（由 Integration 提供 scope schema）、服务端计算的 `schema_hash`、脱敏投影 `resource_scope_summary`、以及按 `scope_ref` 的列表筛选。
- **为什么可能不是最优**：V1 只有 MSS + Demo 两个 Integration，`12:213` 里 Scope Schema 只占 LoadedIntegrationSet 的一个单元格——**抽象的成本（校验/快照 hash/脱敏/筛选/表单）已经付了，而验证它是否通用的样本只有 1 个**。这与总设 §2.4「不为未验证能力提前建模型」、§9.9 判断机制相冲突。
- **备选**：**V1 收敛为最小 typed scope**（`{scope_type: string, refs: string[], attributes?: object}`），Registry 只声明 `scope_type` 白名单与展示标签，去掉 `schema_hash` 参与 digest（或保留但标注"V1 仅记录不校验"）；等第二个真实 Integration 接入再泛化。
- **建议**：收敛。收益是去掉一层校验与一个 hash 依赖；代价是未来泛化时改一次快照结构（已由 snapshot schema_version 兜底）。
- **影响面**：`05` Draft Schema/快照/EXE-API-01 筛选、`12` Scope schema、FE-02 Tab C、`01` CORE-LIB-05。

### D6 [中] Builder 的执行可见范围没有定义，而原型明确要求限定

- **现状**：`05:1511` EXE-API-01 的授权写「Builder + Admin；仅当前 tenant 的管理可见范围」——即 Builder 可看本租户**全部**执行；冻结原型角色矩阵写「执行记录 → Builder 查看**开发/授权范围**，Admin 查看全部」。
- **为什么是问题**：这不是文案差异，而是**数据可见性规则缺失**：Builder 能否看到别人的执行（含发起用户、范围、结果）？若无限制，等于把所有用户的任务元数据开放给所有 Builder。
- **备选**：**A**：Builder 只能看 `service_definition.owner/created_by = self` 或自己被授权的 Agent 相关执行（需要给 Service 加 owner 字段，V1 可从 `created_by` 推导）；**B**：维持全租户可见，并**明确记录为已接受风险**并在前端不展示"用户"信息以外的敏感字段。
- **建议**：A（与原型一致），但注意当前 Service 表没有 owner 字段——需要补 `service_definition.created_by` 或复用审计。
- **影响面**：`05` Service/Execution 表与授权列、FE-10 云云、`04-追溯` 的权限矩阵。

### D7 [低] END_USER 无法自助重试，也无法看到自己的会话上下文

- **现状**：IM 命令集为 `SKILLS/NEW/STOP/RESUME/CANCEL/MEMORY_LIST/MEMORY_CLEAR/RESULT/CONFIRM`（`10:96`），**没有重试**；"重试"仅 Console Admin 可做（`05:1609`）；Console 不提供会话/消息查看（ADR-045），因此 Admin 排障时**看不到用户当时说了什么**。
- **为什么值得确认**：Playbook U02 的用户诉求是"失败时保留已完成结果 + 可继续"，并未要求自助重试；A04 排障要求"谁发起的/哪个客户/失败原因"，也**未要求看对话原文**。所以现状不算违约，但两项都影响真实运维体验。
- **备选**：(a) 增加 `/retry <execution_id>`（复用 EXE-API-04 的 Application，校验本人 + 服务允许用户重试）；(b) 在 EXE-API-02 返回 `conversation_id` 并提供一个**只读、脱敏、仅 Admin** 的"来源会话消息"入口（不做会话管理页面，只做追溯视图）。
- **建议**：V1 可后置，但**显式写进"暂不建设"清单**（当前文档既没做也没说明）。

## 四、判定"合理、不建议改"的设计（防止误伤）

1. **PG 为执行事实源、Redis 仅唤醒/cache/cancel hint** —— 有 DBOS 实测教训（recovery/queue 不可信）支撑，且 PG polling 兜底可自证。
2. **V1 自研 Worker 而不引入 Temporal/DBOS** —— 范围匹配真实旅程，并已设置"何时引入成熟 durable engine"的决策阈值。
3. **LangGraph 仅作 Agent Executor、不承担 ServiceExecution 调度** —— 把 durable 语义留给 Worker，避免把框架绑死在 Agent 生态。
4. **Service 是唯一发布单元（Agent/Model/Capability direct-effect + revision）** —— 版本管理减法，避免管理员陷入版本状态机。
5. **Capability Contract 与 Implementation 分离 + Data Retrieval Policy 下沉到实现** —— 让 Skill 不写分页/认证/服务发现（P20），是 V6 最有价值的一条抽象。
6. **快照只冻结业务逻辑，授权/Credential/紧急禁用实时解析** —— 一致性与安全的正确切分（冻结太多会导致撤销不生效）。
7. **Skill = 离线 Python + 不可变 Artifact + Mock/Dev/Prod 同语义 SDK** —— 保住开发者体验，同时用 Sandbox 隔离与 Artifact 不可变控制风险。
8. **Chat ≠ Execution（读+短时+无副作用直调；写/长任务/高风险进 Execution）** —— 避免把每条消息都变成后台任务。
9. **Console 11 菜单收敛、Channel 配置在 Agent 内、无系统设置菜单、随 platform-api 交付** —— 与三类用户旅程一致，避免技术资源清单式导航。
10. **人工检查点用 task-level（不做通用 Approval Center）** —— 满足 U03 的最小闭环，避免过早建审批平台。
11. **V1 Memory 不做向量检索/自动画像**（`11:80,133` 明确 out of scope）—— 符合 §9.9 的"真实旅程驱动"判断机制。
12. **明确后置清单**（Workflow Designer / Knowledge / WebChat / Browser / Marketplace）—— 有清单本身就是设计质量。

### 本轮执行中的六处追加裁决（由实施过程暴露）

1. **命名消歧**：`capability_definition` 的直调结论字段命名为 **`invocation_policy`**（而非 `execution_policy`）——后者已是 `capability_implementation` 的超时/重试策略（JSONB）。同名不同表会造成实现事故，故故意不同名。
2. **上游同步（D1 的连带影响）**：D1 收敛删除了 `总设 §4.2/§4.3.2A/§5.1` 与 `Playbook §8.1` 明文要求的 `execution_characteristic`/`authorization_requirement`/`error_semantics`。按总设 §6.4「总设必须同步更新」的规则，**已就地修订这两份上游文档**并把 ADR-041 标注为被 ADR-057 取代（保留原文作历史溯源）。
3. **新增协调表**：集群级槽位引入 `worker_slot_lease`，因此模块 06「不拥有独立业务表」的自我约束新增一条**显式例外**（协调表 ≠ 业务事实表），并同步登记进 `08-表所有权` 与模块 README。
4. **模型字段可见性统一（消除"表单可填但详情不可见"）**：`base_url`/`default_parameters`/`request_timeout_seconds` **不是凭据**，故对 Builder 在**详情与表单均可见且可写**（`base_url` 的写入受模块 19 已定的 SSRF allowlist 约束）；**仅 `api_key` 与 `extra_headers`** 为 Admin-only（后者可能承载网关凭据）。据此修订 ADR-046 的澄清段、模块 19 的角色投影表与 `90` §6.2/FE-07；`RISK-07-03`（Builder 编辑拿不到 `base_url`）随之闭合。
5. **能力测试权限以 API 合同为准**：`CAP-API-05` 的授权是 **Builder + Admin**（D03/D04 旅程要求 Builder 先验证能力再给 Agent 用），因此 `90` §4.7/FE-04 按 Builder + Admin 落地——与「模型连通性测试仅 Admin」是不同的判断（后者用已存 Secret 出站，属凭据使用 + 出站探测）。
6. **恢复用户列表「角色」列与筛选**：冻结交互稿有该列与筛选、`USR-API-01` 也支持 `role` 参数，V1.13 误删，已在 `90` §8.1 与 FE-09 恢复（Admin 需按角色找人/筛人）。
