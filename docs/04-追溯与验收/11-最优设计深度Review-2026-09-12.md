# docs/ 最优设计深度 Review（零兼容）

- 日期：2026-09-12
- 范围：`docs/00-总体设计/`、`docs/01-架构与规范/`、`docs/02-模块设计/`、`docs/03-前端设计/`、`docs/04-追溯与验收/`、`docs/05-变更记录/`、`docs/README.md`
- 立场：Greenfield 最优最简，不做兼容性设计
- 结论：当前不是最优设计，而是“V1.8 正文 + ADR 补丁 + 双源索引 + 兼容分支”的拼盘，见下文 P0/P1/P2。

> 原则：凡“双写/双读/缺省回退/已废止留列/两套入口/缺失隐藏/取代声明代替删除”一律判为缺陷，直接删，不设过渡期。

## 总结论

1. **双源头**：`08/09` 汇总索引 vs 模块 `§3.3/§3.4`，`90` vs `FE-*`，总设 vs ADR，均自认“不一致以 XX 为准并重生成”——最优做法是只留一个源。
2. **兼容制度化**：`04-§9` 双读双写、`06-§9` 兼容期、`rendered_summary/artifact_ids` 死列、`archive/*.html` 留仓、“缺失时不渲染”——V1 无生产数据，全部应 `DROP`。
3. **执行面三套状态机**：`conversation_run` + `service_execution` + `message.processing_status` 同构，`cancel/resume` 双入口，`message_key/event_id/dedupe_key` 三幂等——这是全部 E2E 复杂度的根。

### P0-4 双 durable loop：`conversation_run` vs `service_execution`

- 文件+章节：`02-模块设计/03-Agent-Runtime/design-full.md §3.4 RT-LIB-03/RT-INT-02` vs `02-模块设计/11-Conversation与User-Memory/design-full.md §3.3` vs `02-模块设计/05-Service与Execution/design-full.md §3.3` vs `02-模块设计/06-Worker-Engine/design-full.md §3.4 WORK-LIB-01`。
- 问题：同一 turn 三处状态：`message.processing_status` + `conversation_run.status（6 态 + lease 三列）` + `service_execution.status（9 态 + 同名 lease）`；取流/取消双入口 `RT-INT-02/03` vs `EXE-API-03/06`。
- 伤害：同一 turn 两套 claim/lease/fencing/恢复/取消测试矩阵；调用方永远要问“这是 Run 还是 Execution”。
- 整改：砍 `conversation_run` 表 + `RT-LIB-03` + `RT-INT-02/03`。Chat turn 非 durable，`processing_status` 即唯一调度态；只有需可靠副作用才建 `service_execution`（唯一 durable 引擎 = Worker）。
