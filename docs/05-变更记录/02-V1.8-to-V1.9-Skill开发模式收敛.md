# V1.8 → V1.9 Skill 开发模式收敛

## 背景

V1.8 将 Skill 与 Capability 解耦，但仍把 Skill Capability 依赖当作 Console 可编辑 Binding，并保留“标准/快速验证 Skill”等产品概念。进一步评审发现，这会导致：

- SOP 开发人员需要学习新的平台编排方式；
- Console 与 Skill 代码形成双事实源；
- 传统脚本中成熟的数据处理/转换能力无法自然迁移；
- Skill 容易被错误演进为第二套 Workflow Engine。

## V1.9 变更

1. Skill 正式定义为离线 IDE 开发的 Python 代码资产。
2. Console 不再提供 Skill 在线开发和执行编排。
3. 删除“标准 Skill / 快速验证 Skill”领域类型。
4. `skill.yaml` 成为 Skill 元数据和 Capability 依赖事实来源。
5. Console Skill 详情全部只读。
6. 删除 Skill Capability 人工绑定 API/DB 关系；改为 `skill_artifact_capabilities` Artifact 依赖索引。
7. Skill 文件更新改称“导入新版本”，每次创建 immutable Artifact。
8. 增加同仓 `fluxion_skill_sdk` Public API 边界。
9. 增加 Dev Capability Gateway，SDK 在线下通过 HTTP 调开发环境真实 Capability。
10. 增加 Mock SkillContext，支持 pytest/PyCharm 本地断点调试。
11. Skill 继续用普通 Python 完成数据过滤、转换、算法和 SOP。
12. 认证、分页、服务发现、Retry、Timeout、Secret 下沉 Capability Runtime。
13. 区分 AgentDirectCapability 与 SkillDependencyCapability；Skill 依赖不自动暴露给 LLM Tool。

## 最终原则

> 传统 Skill 开发体验不变，Fluxion 只抽离公共基础设施复杂度，并提供稳定 Capability SDK。
