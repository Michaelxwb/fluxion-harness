# V1.6 → V1.7 整改对齐说明（最终对齐结论）

> **版本**：V1.7 整改基线
> **日期**：2026-09-10
> **适用基线**：总体设计 V1.6 + 02/03 模块设计 v1.0
> **性质**：8 大锁死决策 + DB/Settings/Gate 收口。各模块 v1.1 均以本文为准，不再保留多套可选方案。
> **原则**：做减法，不为未来建版本中心、Human Task 平台、Delivery 子系统、Plugin Marketplace。

## D01 ResourceScope（P0）

* `Integration Manifest` 声明 `resource_scope_types: {<type>: {schema: <JSON Schema>}}`；Manifest 本身用 Pydantic 校验。
* `ServiceDefinition.resource_scope_type` 放入 **Service Draft/Published Payload**（不新增 DB 列），随 `ServiceRelease.published_payload` 快照；同时冻结当时 `schema_hash`，防 Manifest 改 schema 导致老 Release 语义漂移。
* 执行链：`Proposal.resource_scope（未验证候选）→ ES resolve Service.resource_scope_type → ResourceScopeRegistry JSON Schema 校验 → Framework授权 → 外部业务授权 → ValidatedResourceScope → ServiceExecution`。
* `TrustedExecutionContext` 只承载 actor/tenant/auth/delivery 等可信系统上下文，不承载未验证业务 Scope。
* 错误码：`SCOPE_INVALID(400)` / `SCOPE_FORBIDDEN(403)` / `SERVICE_CONFIGURATION_INVALID(500)`。
* 验收：`REQ-EXEC-001`，`S-EXEC-001 / E-EXEC-003 / E-EXEC-004`。

## D02 Human Wait（P0）

* V1 只支持 `RESUME / CANCEL`；明确不做 `PAUSE / TRANSFER / MODIFY_INPUT / 自定义Decision / 审批中心`。`RetryExecution` 仅用于 FAILED 后 Admin 重试，不属 WAITING_HUMAN 选择集。
* 状态机：`RUNNING → WAITING_HUMAN → (RESUME→RUNNING | CANCEL→CANCELLING→CANCELLED | deadline到→FAILED/HUMAN_TIMEOUT)`。
* `deadline 必填，默认 entered_waiting_human_at + 24h`；Service 可配更短/更长，不可 NULL。Worker 进入 WAITING_HUMAN 时 `next_run_at = human_deadline`，复用 timer，无独立 Human Scheduler。
* `FAILED/HUMAN_TIMEOUT` 定义为 `USER_INACTION`（用户未行动），非业务失败；Console/告警/失败率单独归类过滤。
* 无新增 Human 表：复用 `service_execution / execution_step / execution_command`；`execution_step.output.human_request{reason/context_summary/deadline}` + progress event 记录；超时后到的 RESUME/CANCEL 幂等拒绝。
* 验收：`REQ-EXEC-002`，`S-HUMAN-001/002 / E-HUMAN-001`。24h 属业务策略验证（E2E），非性能参数。

## D03 Delivery Retry（P0）

* 唯一 Owner：`Worker = Delivery Retry Owner`；`Channel Gateway = 单次 best-effort send`，只返回 `SUCCESS / RETRYABLE_FAILURE / NON_RETRYABLE_FAILURE`，可做连接重连/SDK 内单次重试，禁业务级重试与历史重放。
* 策略：`max_retries = 5, base = 30s, 指数退避 base*2^(n-1) + bounded jitter`，总跨度约 15min；允许按 channel 覆盖，需 Pydantic 范围 + 跨字段校验（如 `max_elapsed >= base*(2^n-1)`）。
* 同一逻辑通知全重试共用同一 `dedupe_key`（`delivery:{execution_id}:completed` / `delivery:{execution_id}:progress:{stage}`）；语义 `at-least-once + best-effort 去重`，不承诺 exactly-once。
* 最终失败不建死信表：写 `task_progress_event(event_type=DELIVERY_DEAD_LETTER)`，Console 分开展示 `Execution=SUCCEEDED / Delivery=FAILED`。
* 验收：`REQ-EXEC-003`，`S-DELIVERY-001 / E-DELIVERY-001/002`。

## D04 Agent 发布（P1）

* 删除“关键 Agent”概念。V1 统一：`AgentDefinition → Save 直接生效 + revision/audit`，无 Draft/Published；只有 `Service → Draft/Published`。
* `ServiceRelease` 发布时冻结当时 resolved Agent 配置；Execution 由 `ServiceRelease → ExecutionSnapshot` 继承。
* Console Agent 页改为 `编辑/保存/启用/禁用`，不显示发布。同时解决版本膨胀（P3-10）。
* DB：唯一真正的 Contract Migration 是 Agent 去发布化（`agent_definition.draft_payload/published_payload` 回填 revision 后走 `expand→migrate→switch→contract` 废弃双 payload，`adapters/postgres/agent_repository.py` 同步改）。其余不机械加列。

## D05 Channel Gateway（P1）

* V1 唯一方案：一个 `channel-gateway` 镜像 + `CHANNELS/--channels` 加载多 Adapter（如 `CHANNELS=wecom,webchat`）。按 Channel 拆 Deployment 仅作未来 ADR 选项（相同镜像 + 不同 `--channels`）。
* 连接 ownership：Redis 只管临时 lease `channel-owner:{channel}:{account_id}`，Reference 默认 `TTL 30s / renew 10s`（benchmark 校准）；Redis 失效时现连接短暂续服，禁新实例盲抢。
* E2E：`A owns → SIGKILL A → lease过期 → B接管 → 重连 → 收发恢复 → Conversation/Execution/Route 不丢`。

## D06 UserAgentBinding（P1）

* V1 从总设 ER/Domain/DB/API/Console 全部删除。路由由 `ChannelAccount.default_agent + Channel Routing Policy` 决定；per-user 个性化未来单独建模。

## D07 Knowledge Evidence（P1）

* 不建 `knowledge_retrieval_event` 表。Durable Agent Step 证据写 `execution_step.output.knowledge_evidence[{source_id/document_ref/retrieved_at/source_revision?/content_hash?}]`；Realtime 问答只写 OTel Trace，不建 Execution 记录。

## D08 Integration Manifest（P2）

* 锁定三层：`Authoring=YAML → Runtime校验=Pydantic IntegrationManifest → Hash输入=canonical JSON → SHA-256 manifest_hash`（`integration_registration.manifest_hash` 已存在，不新增列）。
* 流程 `integration.yaml → parse → validate → model_dump(mode=json) → canonical → SHA-256`；Provider key 冲突 fail-fast。
* 第二 Demo 锁定 `local-weekly-report`（Workspace input → glob/read → Agent summarize → write → Artifact），零 MSS/外部API/Auth 依赖，专证通用性。

## DB/Settings/Gate 收口

* 三公共字段不变：`is_deleted/create_time/update_time` + `WHERE is_deleted=false` + partial unique；Audit 默认 `is_deleted=false` 永不清，走保留策略。Checkpointer 第三方表不动。
* Reference Defaults 全进 Pydantic Settings（`HUMAN_WAIT_DEFAULT_TIMEOUT=24h / DELIVERY_MAX_ATTEMPTS=5 / DELIVERY_BACKOFF_BASE=30s / CHANNEL_OWNER_LEASE_TTL=30s / RENEW=10s`），允许部署覆盖 + 范围/跨字段校验。
* 性能只锁框架自控指标：`PG fallback claim lag P95 < 5s` + 固定 Benchmark Profile（PG版本/Worker数/总量/due/batch/poll/Redis开关/mock延迟）；QPS/LLM/SLA 部署实测后再定。
* Core 脱敏立即固定最小集（Authorization/Cookie/Password/Token/...)，Integration 只能追加不能取消。
* 新增 Gate：G19 Scope / G20 Human / G21 Delivery / G22 Agent生命周期 / G23 Manifest / G24 Production Executable（`scan==PASSED && isolated_sandbox && !embedded_credential`）/ G25 Gateway Ownership / G26 Worker Performance。
* 追溯先建 `REQ-EXEC-001~003 → FEAT → RULE → Interface → S/E → Test`，其余 REQ 后续扩；各模块 Owner 按角色（Backend/Channel/Frontend/Security/Architecture）填，不伪造人名。
* 实施序：R1（Scope/Human/Delivery Contract）→ R2（Agent/Binding/Evidence/Manifest/Audit）→ R3（Perf/Auth注入/Executable/Gateway/Browser池边界）→ R4（追溯/Owner/Demo/V1.7全同步）。R1 未完不进黄金旅程编码。
