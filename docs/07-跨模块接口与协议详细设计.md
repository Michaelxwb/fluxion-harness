# 07 跨模块接口与协议详细设计

## 1. 统一协议约定

### 1.1 HTTP

- JSON：`application/json; charset=utf-8`；
- SSE：`text/event-stream`；
- 时间：RFC3339；
- ID：UUID string；
- Internal API 不对公网 Ingress 暴露；
- 服务间必须透传 `traceparent`，同时传业务关联头。

### 1.2 统一 Header

```text
X-Trace-Id
X-Request-Id
X-Caller-Service
X-Tenant-Id
```

Phase 1 防御性服务身份：内部 NetworkPolicy + 可选共享 `X-Service-Token`（来自服务配置）；未来可升级 mTLS，不改变业务 Contract。

### 1.3 错误 Envelope

```json
{
  "error": {
    "code": "AGENT_ACCESS_DENIED",
    "message": "agent access denied",
    "details": {},
    "trace_id": "..."
  }
}
```

用户可见消息由上层映射，Internal API message 不作为最终 UI 文案。

## 2. IM Gateway -> Agent Runtime

### 2.1 `POST /v1/runs`

创建并流式执行一次 Run。

该接口部署在 `agent-runtime` Service 后面。调用方只传 `agent_id`，**不得传 runtime_pod_id**；负载均衡可把请求发到任意 Runtime Pod。

请求：

```json
{
  "agent_id": "uuid",
  "platform_user_id": "uuid",
  "conversation_id": "uuid-or-null",
  "channel": {
    "type": "WECOM",
    "bot_id": "bot_xxx",
    "external_conversation_id": "xxx"
  },
  "message": {
    "id": "msg_xxx",
    "type": "text",
    "text": "帮 A 客户做一次策略检查",
    "attachments": []
  }
}
```

响应：SSE。

首个事件：

```text
event: run.created
data: {"run_id":"...","conversation_id":"...","resumed":false,"trace_id":"..."}
```

调用语义（V1.4）：

- 同一 conversation 同时最多一个非终态 Run；
- 若存在 `WAITING_INPUT` Run，本请求被当作 resume 输入继续该 Run（`run.created` 带 `"resumed": true`）；
- 若存在 `CREATED/RUNNING` Run，返回 `409 RUN_BUSY`；
- 否则创建新 Run。

### 2.2 `POST /v1/runs/{run_id}/resume`

```json
{
  "platform_user_id": "uuid",
  "input": {
    "id": "原入站消息ID",
    "type": "text",
    "text": "选择设备 1 和 2"
  }
}
```

约束：`platform_user_id` 必须与本租户 Run 的用户一致；幂等键取 `Idempotency-Key` 或 `input.id`，指纹绑定租户、用户、Run 与原输入。已终态重放当前终态；新的恢复须为 `WAITING_INPUT` 且未超过绝对 deadline。响应与 `POST /v1/runs` 相同（SSE 事件流）。IM 普通回复经 `POST /v1/runs` 自动 resume；本接口服务显式恢复与诊断。`MEMORY_CONFIRMATION` 只接受完整“确认 <候选UUID>”或“拒绝 <候选UUID>”，无效输入保留等待；合法但失效的提议消费为 STALE 后续跑，保存结果追加新事件，原工具回执不改写。

### 2.3 `POST /v1/runs/{run_id}/cancel`

幂等。已终态返回当前终态。取消为协作语义：`WAITING_INPUT` 直接置 `CANCELLED`；`RUNNING` 返回 `CANCELLING`，执行 Pod 协作停止后置 `CANCELLED`。

### 2.4 `POST /v1/runs/cancel-active`

```json
{
  "agent_id": "uuid",
  "platform_user_id": "uuid"
}
```

语义：

- 无活跃 Run → `404 NO_ACTIVE_RUN`；
- `WAITING_INPUT` → 直接 CAS 置 `CANCELLED`（无执行者）；
- `CREATED/RUNNING` → 写 `cancel_requested=true` + Redis hint `run:cancel:{run_id}`，响应 `{"run_id":"...","status":"CANCELLING"}`，执行 Pod 协作停止后置 `CANCELLED`；
- 用户提示为受理语义“正在停止当前任务…”。

### 2.5 `POST /v1/conversations`

```json
{
  "agent_id": "uuid",
  "platform_user_id": "uuid"
}
```

用于 `/new`。

### 2.6 `GET /v1/runs/{run_id}`

返回 Run 当前状态与 Snapshot 摘要引用（不含 Secret），用于 Gateway 诊断与 Console 详情。

```json
{
  "agent": {

    "revision":12,
    "instructions":"...",
    "runtime_config":{}
  },
  "model": {
    "id":"uuid",
    "revision":4,
    "protocol":"OPENAI",
    "model_id":"qwen3-235b-a22b",
    "base_url":"http://model-gateway.internal/v1",
    "api_key":"sk-…",
    "params":{}
  },
  "skills":[
    {
      "skill_id":"uuid",
      "artifact_id":"uuid",
      "key":"policy-check",
      "name":"设备策略检查",
      "description":"...",
      "version":"1.3.0",
      "checksum":"sha256:...",
      "storage_key":"skills/{skill_id}/{artifact_id}/skill.zip",
      "frontmatter":{},
      "execution_mode":"ASYNC"
    }
  ],
```

权限解析语义（完整判定见 00 §0.9 / 02 §5.10）：

```text
skills =

∩ Agent.enabled
∩ AgentSkillBinding(is_deleted=false)
∩ Skill.enabled ∩ Skill.is_deleted=false
∩ Skill.user_scope(ALL/SELECTED + SkillUserGrant.is_deleted=false)

mcp_servers =
AgentAccessGrant(is_deleted=false)
∩ Agent.enabled
∩ AgentMcpBinding(is_deleted=false)
∩ MCP.enabled ∩ MCP.is_deleted=false
∩ MCP.user_scope(ALL/SELECTED + McpUserGrant.is_deleted=false)
```

因此响应里的 `skills/mcp_servers` 已是 Effective Capability，不是 Agent 的原始全量绑定。

```text

AGENT_DISABLED
AGENT_ACCESS_DENIED
MODEL_DISABLED
```

### 4.2 `POST /internal/runtime/resolve-egress-access`

该接口只做：

- ProjectPlatform 解析；
- `adapter_key/adapter_config` 返回；
- 凭据选择策略与 CredentialRef 解析；
- 调用授权/审计归因。

不返回 Secret Value，也不在 Console 层执行平台登录。

`execution_ref.type` 只允许 `RUN/TASK`；Runtime 用 RUN，Worker 用 TASK。`target.type` 与数据库审计统一为 `PLATFORM_SERVICE/HTTP/MCP`。

请求：

```json
{
  "actor_user_id":"uuid",
  "execution_ref":{"type":"RUN","id":"uuid"},
  "skill_artifact_id":"uuid",
  "platform_key":"example-prod",
  "target": {
    "type":"PLATFORM_SERVICE",
    "service":"customer-service-mgr",
    "operation":"get_customer"
  }
}
```

响应：

```json
{
  "decision":"ALLOW",
  "platform": {
    "id":"uuid",
    "key":"example-prod",
    "resolver_type":"BASE_URL",
    "resolver_config":{"base_url":"https://platform.internal"},
    "adapter_key":"generic-http",
    "adapter_config":{
      "login_endpoint":"/gateway/login_agent",
      "health_endpoint":"/v1/rtt"
    },
    "adapter_schema_version":"1",
    "credential_mode":"USER_THEN_SHARED"
  },
  "credential": {
    "ref_id":"uuid",
    "credential_json":{"username":"…","password":"…"},
    "credential_schema_version":"1"
  }
}
```

Runtime/Worker 随后在本地共享 `platform-sdk` 中：

```text
AdapterRegistry.get(adapter_key)
 -> CredentialRepository.get(ref_id) 读取明文 credential_json
 -> PlatformSessionManager
 -> adapter.authenticate/validate/prepare_request
```

### 4.3 `GET /internal/platform-adapters/{adapter_key}`

Runtime/Worker 通常通过本地 `platform-sdk` Registry 获取 Adapter；该接口主要用于跨版本诊断和 Console 元数据一致性检查。

响应示例：

## 5. Agent Runtime -> Agent Worker

这些 Internal API 只在内网开放，并且**与 `/internal/admin/*` 同一服务身份门控**（2026-10-06 评审 #1）：
每个请求都必须带 `X-Internal-Service: $INTERNAL_SERVICE_TOKEN`，缺失或错误一律 `FORBIDDEN`。
租户与 actor 都取自请求头，只有确认调用方是受信服务（Runtime / Console）之后，这些头才谈得上
「可信上下文」；`INTERNAL_SERVICE_TOKEN` 未配置时同样一律拒绝（不做「未配置即放行」）。

✅ Runtime 的 `WorkerTaskClient` 构造时传 `service_token=settings.internal_service_token`，每个请求都带上它。
❌ 只带 `X-Tenant-Id` 就调用 `/internal/tasks` —— 任何能连上 Worker 端口、知道目标租户/任务 id 的调用方都能读、建、取消别人的任务，也能改别人的定时任务。

### 5.1 `POST /internal/tasks`

创建即时 Background Task。通常由 Runtime 的 `execute_skill -> ExecutionRouter` 调用，而不是让 LLM 自己构造后台 Task。

请求：

```json
{
  "tenant_id":"t1",
  "agent_id":"uuid",
  "actor_user_id":"uuid",
  "source_run_id":"uuid",
  "intent_key":"policy_check",
  "skill_id":"uuid",
  "skill_artifact_id":"uuid",
  "input": {"customers":["A","B","C"]},
  "execution_snapshot": {},
  "snapshot_hash":"sha256:...",
  "idempotency_key":"run:tool-or-router-key",
  "delivery_route": {
    "channel":"WECOM",
    "bot_id":"bot_xxx",
    "external_user_id":"wotv...",
    "external_conversation_id":"xxx"
  },
  "delivery_mode":"FINAL_ONLY"
}
```

响应：

```json
{"task_id":"uuid","status":"QUEUED"}
```

### 5.2 `POST /internal/schedules`

创建定时任务。调用方必须已经由 Agent 理解并规范化业务意图。

```json
{
  "name":"每周策略检查",
  "agent_id":"uuid",
  "actor_user_id":"uuid",
  "intent_key":"policy_check",
  "skill_id":"uuid",
  "input_template":{"customer":"A"},
  "schedule":{"type":"CRON","cron":"0 9 * * 1","timezone":"Asia/Shanghai"},
  "delivery_route": {
    "channel":"WECOM",
    "bot_id":"bot_xxx",
    "external_user_id":"wotv..."
  }
}
```

Schedule 保存稳定 `skill_id`，不保存 Skill Artifact checksum。每次触发时按 `skill_id` 校验当前 Skill/Agent Binding/user_scope，再读取 current_artifact_id 生成新 Task Snapshot；不得按 skill_key 重新匹配资源。V1 错过触发按 SKIP 处理（不补发），无 misfire 配置。

### 5.3 Task 查询与取消

```text
GET  /internal/tasks/{task_id}
GET  /internal/tasks?schedule_id=&agent_id=&actor_user_id=&status=&trigger_type=&start_time=&end_time=&page=&page_size=
POST /internal/tasks/{task_id}/cancel

GET    /internal/schedules?actor_user_id=
PUT    /internal/schedules/{schedule_id}
DELETE /internal/schedules/{schedule_id}
```

更新 Schedule 仅影响未来触发。通过 Agent 调用时，Worker 必须校验 `actor_user_id` 是 Schedule owner；Console 管理接口按 Admin/Builder 权限控制。

## 7. Agent Worker -> IM Gateway

### 7.1 `POST /internal/deliveries`

```json
{
  "task_id":"uuid",
  "delivery_key":"task:uuid:final",
  "route":{
    "channel":"WECOM",
    "bot_id":"bot_xxx",
    "external_user_id":"wotv...",
    "external_conversation_id":"xxx"
  },
  "message":{
    "type":"text",
    "text":"任务已完成：成功 18，失败 2。"
  },
  "artifact_ids":["uuid"]
}
```

该 API 只做渠道发送，不重新做 Agent reasoning。IM Gateway 以 `delivery_key` 去重（Redis `delivery:dedupe:{delivery_key}`：先占位、发送成功后 CAS 升级为送达标记，TTL 7d），重复请求直接返回 200；Redis 不可用时按 at-least-once 发送。

请求头与归属校验（2026-10-06 起）：端点要求服务身份 `X-Internal-Service`；`tenant_id` 必须等于网关部署的租户；产物形态投递必须带 `artifact_id`，网关经 Runtime 的 `GET /internal/artifacts/{id}` 在本租户内解析出权威引用，请求体里的 `storage_key` 仅用于比对。响应体在产物形态下附带 `outcome`（`DELIVERED`/`DEGRADED`）与降级的 `fallback_url`；**去重重放回放首次的这两个字段**。

### 9.3 Memory（受保护管理命令）

Runtime 是记忆唯一写入者；Console 管理写全部转发到这里（TASK-023 契约）：

```text
POST   /internal/admin/users/{user_id}/memory/commands
GET    /internal/admin/users/{user_id}/memory
GET    /internal/admin/users/{user_id}/memory/{memory_key}/history
DELETE /internal/admin/users/{user_id}/memory
```

- Header：`X-Tenant-Id`（租户）、`X-Internal-Service`（服务身份，伪造/缺失 403）、`Idempotency-Key`
  （命令号；回执永久、同号异指纹 `IDEMPOTENCY_MISMATCH`）；清空另需 `X-Actor-Id`。
- `POST …/commands` 请求体只有 `{actor_id, mutation}`：`mutation.action ∈
  {UPSERT,DELETE,CLEAR,ENABLE,DISABLE,RESTORE}`，`UPSERT` 带 `memory_key/category/value`
  （可选 `expected_version/expires_at/enable/restore`），`DELETE` 按 `memory_key` 或 `memory_id`
  二者之一，其余动作必须带 `expected_version`。调用方不能传 `author`（来源只由服务身份派生为
  `ADMIN`）。响应 `{command_id, scope_revision, forget_epoch, changed_count, status, items[]}`。
- `GET` 列表按 `category/author/status` 过滤并分页（`status` 由 enabled+expires_at 派生，
  已删除不出现）；`GET …/{memory_key}/history` 返回 append-only 版本历史（按 version 倒序）。
- `DELETE`（清空）是一命令原子操作：逐项写历史、递增 `forget_epoch` 撤销未消费候选。

### 10.12 Overview

```text
GET /api/v1/overview?days=7
```

单一只读聚合返回资源摘要、六项核心指标、趋势、状态、Agent Top5 和待处理摘要。登录会话决定 `tenant_id`；`days` 为 1–30，默认 7，页面提供今日/近7天/近30天。

响应 `data` 契约：

- `days`、`timezone`（平台 IANA 时区）、`generated_at`（该时区 `YYYY-MM-DD HH:mm:ss+00:00` 形式，必须带 offset）。
- `resources`：`enabled_agents`、`enabled_skills`、`enabled_mcps`、`enabled_models`、`users`、`active_schedules`，均为整数。
- `kpis`：`run_count`、`active_users`、`model_request_count`、`token_reported_request_count` 为整数；`run_success_rate`、`average_run_duration_ms`、`input_tokens`、`output_tokens`、`total_tokens`、`token_coverage` 可为 null。
- `activity`：`active_runs`、`waiting_input_runs`、`waiting_tool_runs`、`queued_tasks`、`running_tasks`、`waiting_tasks`、`overdue_tasks`，均为整数。
- `attention`：`failed_runs`、`failed_tasks`、`failed_deliveries`，均为整数。
- `trend.runs[]` / `trend.tasks[]`：`date`、`total`、`failed`；`trend.tokens[]`：`date`、`input_tokens`、`output_tokens`、`model_request_count`、`token_reported_request_count`。日期为连续 days 个平台自然日，升序排列；无请求日补零，有请求但用量未知时保留 null。
- `status.runs` / `status.tasks`：状态到整数数量的映射，只返回实际存在的状态。
- `agent_ranking[]`：`agent_id`、`agent_name`（可为 null）、`run_count`；最多 5 项，运行数降序、ID 升序。

统计口径：

- 一次捕获 now；窗口从平台时区 days-1 天前午夜至 now，排除未来记录。
- Run 数、状态、活跃用户、排行、失败摘要按期间创建的 Run 的当前结果。成功率为 `COMPLETED / (COMPLETED + FAILED) * 100`；取消和未结束运行不进入分母，无样本时返回 null。
- 平均耗时仅取期间创建的终态 Run（COMPLETED/FAILED/CANCELLED）且 start/end 有效的样本，包含运行中的等待，单位毫秒；无有效样本时返回 null。
- 趋势 total 按创建日计，failed 按实际结束日计；失败线可包含窗口之前创建、窗口内失败的记录。
- 后台业务任务统一限定 `parent_id IS NULL`，子任务不重复计数；状态与失败/投递失败摘要按期间创建的业务任务当前结果。投递失败排除 `delivery_mode='NONE'`。
- `activity` 和 `resources` 为当前存量，独立于 days；超期是未结束业务任务的 deadline_at 小于等于 now。启用定时任务不要求 next_fire_at 非空。
- 模型请求按审计发生时间计入窗口，包含重试和摘要请求，并关联同租户未删除 Run。输入/输出用量各自汇总已知值；有请求但该侧全部缺失时为 null，无请求时为 0。`total_tokens` 为已知两侧之和；`token_coverage` 是双侧均有记录的请求占比（0–100），没有请求时为 null。
- 全部查询按 tenant_id 隔离且排除软删除；先聚合再关联名称，缺失 Agent 名称不丢历史运行。读取 Owner 表，不写数据库、不建快照、不依赖 Redis；平台设置查询与单条聚合 SQL 的数量不随实体行数增长。
- 不展示运营列表、中间件/Pod 健康和费用；旧 `/overview/metrics` 不再提供。

错误码：`UNAUTHORIZED` / `COMMON_VALIDATION_ERROR` / `COMMON_INTERNAL_ERROR`。

Console 不提供图形化 Task/Workflow 编排器。
