### 2.1.2 现状问题

1.  Skill 自己管理 Chromium 启动、关闭、路径和依赖。
2.  Playwright/Chromium 版本和运行参数缺少统一治理。
3.  多个 Skill 间接依赖同一个 `generate.js`，公共渲染引擎成为单点。
4.  浏览器任务缺少统一排队、并发配额和资源监控。
5.  缺少 Tenant/User/Thread 级 Context 隔离与 Session 路由。
6.  浏览器任务没有统一关联 Fluxion Execution。
7.  缺少浏览器操作副作用等级和审计。
8.  单次任务与多轮对话浏览器操作需要不同生命周期。
9.  现有 Skill 直接启动浏览器，无法充分复用常驻 Chromium。

### 2.3.2 执行模式

#### Ephemeral：单任务执行

适用：HTML→PNG/PDF、MSSP auto URL、页面截图、DOM
提取、单次表单操作、单次 CDP 操作。

流程：

1.  Skill/Agent 提交完整任务。
2.  Browser API 校验身份、授权、配额、副作用策略。
3.  服务端根据 SDK 业务方法映射任务类型和资源池。
4.  PostgreSQL 创建 Job + Outbox。
5.  Outbox 投递到资源池 Redis Stream。
6.  Executor 有空闲槽位时领取。
7.  在常驻 Chromium 上创建独立 BrowserContext。
8.  注入当前用户的目标平台认证信息。
9.  在 Context 内创建 Page 并完成完整步骤。
10. 上传制品、保存结构化结果。
11. PostgreSQL 更新终态。
12. Redis ACK。
13. 关闭 Context，释放槽位。

规则： - 每个 Job 独立 Context。 - Job 内可有多个 Page，但不得与其他 Job
共享 Context。 - 终态后必须关闭 Context。 - 不允许跨用户/Thread 共享
Cookie、Storage。 - 一个 Job 的完整步骤尽量在 Executor
内完成，避免每个动作都经过 Browser API。

#### Persistent：对话式持续会话

适用：用户多轮探索网页、连续点击/筛选/查看详情、要求保留页面状态。

流程： 1. Agent 调用 `browser_open_session`。 2. Browser API
校验四维身份和 Agent 授权。 3. 创建 Session 记录。 4. 从 General Pool
选择健康 Executor。 5. Executor 创建独立 Context。 6. 保存
`session_id → executor_id/context_id`。 7. 后续通过
`browser_session_action` 固定路由到原 Executor。 8. 同一 Session
的命令串行执行。 9. Thread 结束、主动关闭或空闲超时后释放 Context。

边界： - Persistent 表示 Context 在对话期间持续存在，不表示跨 Pod
持久化。 - Pod 故障后内存状态不可迁移；Session 标记 INTERRUPTED。 -
可重新获取 SessionManager 凭证创建新 Context，但不承诺恢复 JS
内存、未提交表单等页面现场。 - 无法恢复时必须明确返回，不得伪装成功。

### 2.3.3 逻辑任务类型与物理资源池

  逻辑类型     典型场景                           默认模式                    物理池
  ------------ ---------------------------------- --------------------------- ---------
  Render       HTML→PNG/PDF、卡片/海报/报告渲染   Ephemeral                   Render
  Automation   导航、JS、DOM、表单、auto URL      Ephemeral                   General
  Capture      CDP 区域截图、动画帧               Ephemeral，必要时 Session   General
  Session      对话式持续页面操作                 Persistent                  General

严格隔离： - Render Pool 与 General Pool 是两个独立 Deployment。 -
两个池使用不同 Redis Stream。 - Render Executor 只能消费 Render
Stream。 - General Executor 只能消费 General Stream 和自己的 Session
定向命令。 - 不允许跨池借用、抢占或自动迁移。 - 两个 Deployment 使用相同
Executor 代码/镜像，通过 `pool_type` 配置区分。 - General
内部用并发配额控制 Automation、Capture、Session，不再拆成三个
Deployment。 - 生产副本比例根据线上任务占比和压测结果人工确定。

### 2.3.4 Agent、Skill 与 Browser 的职责

  ------------------------------------------------------------------------------------------------------
  组件                    负责                                            不负责
  ----------------------- ----------------------------------------------- ------------------------------
  Agent                   理解意图，选择一次性任务或持续会话工具          选择资源池/Pod/Chromium/配额

  Skill                   通过 SDK 完成业务流程，提供业务参数和步骤       启动/关闭 Chromium，选择 Pod

  Browser SDK             封装业务语义接口和调用协议                      最终资源调度和授权

  Browser API             身份授权、任务分类、资源池路由、排队、Session   页面执行
                          路由和配额                                      

  Executor                Chromium、Context、Page、Playwright、结果上传   Agent 意图识别和用户授权


Skill 不指定 `pool_type` 或 `executor_id`。Skill
通过业务语义方法调用： - `browser.render(...)` -
`browser.execute(...)` - `browser.capture(...)`

服务端固定映射到任务类型和资源池。

Agent 对话工具： - `browser_run`：一次性 Ephemeral。 -
`browser_open_session`：创建 Persistent。 -
`browser_session_action`：继续已有 Session。

意图识别规则： 1. 一次性读取、截图、单次页面操作默认 Ephemeral。 2.
明确要求持续探索、保留页面状态或多轮继续时使用 Persistent。 3. 当前
Thread 已有有效 Session，用户要求继续时复用原 Session。 4.
生命周期不明确且会影响结果时询问用户。 5. API 重新校验 Session 的
Tenant/Agent/User/Thread 归属；LLM 提供的 ID 不是授权凭证。 6. Agent
不得指定资源池、Pod 或 Chromium。

### 2.3.5 浏览器操作副作用等级

  ----------------------------------------------------------------------------------------------------------------------------
  等级              名称               示例                                       默认策略
  ----------------- ------------------ ------------------------------------------ --------------------------------------------
  L0                READ_ONLY          打开只读页、读取 DOM、截图、查询列表       已授权域名内允许

  L1                REVERSIBLE_WRITE   修改筛选、草稿、可撤销配置                 需要 Capability 授权

  L2                BUSINESS_WRITE     创建报告、提交业务任务、创建记录           明确业务意图、动作授权、幂等键；必要时确认

  L3                HIGH_IMPACT        删除、批量操作、发布、审批、外部消息发送   默认拒绝；显式授权和审批/确认后执行


规则： - 副作用等级由服务端 Capability Policy、Skill
注册信息、目标域名和已登记动作确定，不接受 Agent
自报等级作为唯一依据。 - 未知 URL/动作按高风险处理。 - MSSP `/auto`
即使通过 GET 导航触发报告，也按 L2 业务写入处理。 - 不能仅根据 HTTP
GET/POST 判断副作用。 - L2/L3
记录调用主体、目标、动作、授权/确认、幂等键和结果。 -
副作用等级与资源类型是独立维度。

### 2.3.6 任务排队与 20 QPS

20 QPS 的定义： - 集群持续接收并持久化 20 Job/s。 - 对应 Executor
集群持续领取/消费 20 Job/s，不出现长期增长的未消费积压。 - Completed
QPS、Successful QPS、执行时间、失败率单独统计。 - 20 QPS
是集群目标，不是单 Pod 目标，也不是已实测承诺。 - 具体副本数和每 Pod
并发由真实任务混合压测确定。

  指标                  定义
  --------------------- -----------------------------------------
  Accepted QPS          每秒成功创建并持久化的 Job 数
  Dispatched QPS        每秒成功写入 Redis Stream 的 Job 数
  Claimed/Started QPS   每秒被 Executor 领取并开始执行的 Job 数
  Completed QPS         每秒进入成功/失败终态的 Job 数
  Successful QPS        每秒成功完成的 Job 数
  Queue Wait            Job 创建到 Executor 开始执行的时间
  Execution Duration    Executor 开始执行到任务终态的时间

长期稳定要求消费能力不低于持续到达速率。队列吸收突发，不替代容量。

### 2.3.7 幂等与重试

-   只读导航、DOM 读取、截图可按错误类型安全重试。
-   认证失效、超时等条件重试需分类。
-   可能已经产生外部副作用但结果不确定的任务不得自动重试。
-   每个 Job 有 `idempotency_key` 和请求摘要。
-   相同幂等键、相同请求返回已有 Job；相同键、不同请求返回冲突。
-   MSSP auto URL 触发后尽可能捕获网络响应并保存 `task_id`。
-   触发请求发出但响应丢失时标记
    UNKNOWN，先查询任务列表/业务接口确认，不直接再次访问 auto URL。
-   MSSP 不支持幂等键时，依靠业务可查询条件核实，并记录重复触发风险。

### 3.2.2 Browser API 职责

-   统一接收 Skill/Agent/Worker 请求。
-   校验服务身份、用户身份、Tenant、Agent 授权、Thread。
-   依据 SDK 业务语义确定任务类型和 Pool。
-   创建 Job/Session/Outbox。
-   查询、取消 Job。
-   创建、操作、关闭 Persistent Session。
-   维护 Session 固定路由。
-   执行全局/Tenant/User/Thread 配额。
-   不持有 Chromium、Page、Context。
-   无状态，可多副本部署；状态在 PostgreSQL/Redis。

### 3.2.3 Browser Executor 职责

-   启动一个 Chromium Browser 进程。
-   注册 Executor ID、Pool Type、健康和资源指标。
-   只消费所属 Pool 队列。
-   只有存在本地执行槽位时才领取任务。
-   创建/关闭 Context 和 Page。
-   注入 SessionManager 认证信息。
-   执行 Playwright 操作。
-   上传制品。
-   更新 Job 状态并 ACK。
-   心跳和上报 CPU/内存/Context/Page 数。

Executor 不保存业务持久事实。Chromium、Context、Page
是运行态。Persistent Context 只在 Pod 存活期间保留；Pod 故障时标记
Session 中断，不承诺内存态迁移。

### 3.2.4 两个严格隔离物理资源池

``` mermaid

    end
```

  逻辑类型     物理池    规则
  ------------ --------- -------------------------------
  Render       Render    只允许 Render
  Automation   General   普通自动化
  Capture      General   独立并发配额
  Session      General   固定 Executor、Session 内串行

两个池独立 Deployment、独立
Stream、独立副本数。禁止跨池借用、抢占和迁移。General
内部通过并发配额控制三种任务，不再增加 Deployment。

### 3.2.5 一个 Pod 一个 Chromium


-   Pod 启动时启动一个 Chromium。
-   Browser 健康后才注册 READY。
-   Browser 崩溃期间停止领取任务。
-   可执行受控重启；连续崩溃由 Kubernetes 重建 Pod。
-   不在一个 Pod 内再维护多个 Chromium。
-   Context 上限通过配置控制，压测确定。
-   不同 Job 不共享 Context。

### 3.2.7 Persistent 时序

``` mermaid
sequenceDiagram
  participant A as Agent
  participant API as Browser API
  participant DB as PostgreSQL
  participant E as General Executor
  participant C as Chromium
  A->>API: browser_open_session

  API->>E: 创建 Context
  E->>C: new_context

  E-->>API: 操作结果
  API-->>A: 返回
```

Persistent Session： - 创建后绑定 Executor。 - API 重启后可从 DB/Redis
恢复路由。 - 每个 Session 命令串行。 - Executor 不健康时标记
INTERRUPTED。 - 不将命令随机路由到其他 Pod。 -
可重新认证和重新导航，但不保证恢复页面内存态。

### 3.2.8 Redis Streams 队列

  ---------------------------------------------------------------------------------
  Stream                            消息                    Consumer
  --------------------------------- ----------------------- -----------------------
  `browser:jobs:render`             Render Job              Render Executor Group

  `browser:jobs:general`            Automation/Capture Job  General Executor Group

  `browser:session:{executor_id}`   指定 Executor 的        指定 Executor
                                    Session 命令            

  `browser:dlq:{pool}`              超过恢复策略的消息      运维/补偿
  ---------------------------------------------------------------------------------

消费规则： 1. 检查健康状态。 2. 检查本地空闲槽位。 3. 有槽位才领取消息。
4. 不大量预取到本地队列。 5. 执行并持久化结果。 6. ACK。 7. 释放 Context
和槽位。 8. 继续消费。

Pending 恢复使用 `XAUTOCLAIM` 或等价机制。重复投递必须幂等。ACK
不是业务成功的事实来源，PostgreSQL 状态才是。

### 3.2.9 Job 状态机

``` mermaid
stateDiagram-v2

  QUEUED --> DISPATCHED

  RUNNING --> SUCCEEDED
  RUNNING --> FAILED
```

  状态               含义
  ------------------ ------------------------------
  QUEUED             已创建，待投递/消费
  DISPATCHED         已进入 Redis Stream
  RUNNING            Executor 已领取并开始
  SUCCEEDED          执行结果已持久化
  FAILED             确定性失败

  CANCELLED          已取消
  UNKNOWN            外部副作用可能发生但结果未知
  RECONCILING        查询业务系统核实
  MANUAL_REVIEW      需要人工核实

### 3.2.10 调度与公平性

-   API 确定性路由到物理池。
-   Pool 内由 Consumer Group 分配。
-   Executor 有槽位才领取。
-   全局、Pool、Tenant、User、Thread 均设置并发/队列配额。
-   同一 Persistent Session 串行。
-   第一阶段只实现并发配额和队列上限，不引入复杂动态公平调度算法。
-   Render/General 不跨池借用。

### 3.2.11 SessionManager

-   凭证按 User × Platform 管理，不归属 Agent。
-   用户能否调用 Agent 由 Console 授权决定。
-   API 校验 Agent 授权后，按用户和目标平台获取凭证。
-   每个 BrowserContext 独立注入 Cookie/Storage。
-   Cookie/Token 不进入日志、Trace、普通 Redis 消息或 API 响应。
-   Browser Service 不建设第二套凭证中心。

### 3.2.12 Artifact

-   PNG/PDF/截图/下载文件存入 ArtifactStore。
-   Executor 使用受限临时目录。
-   上传成功并保存元数据后 Job 才能成功。
-   任务结束清理本地临时文件。
-   Artifact 查询再次校验 Tenant/Agent/User 权限。
-   不返回 Pod 本地路径。

### 3.2.13 模块分层

Browser API： - api - auth - browser_facade - task_router - jobs -
sessions - scheduler/quota - repositories - outbox - observability

Browser Executor： - bootstrap - chromium_supervisor - consumers -
admission_controller - job_runner - session_runner -
playwright_adapter - policy_guard - artifact_adapter -
executor_registry - observability

请求头： - `Authorization`：内部服务身份凭证。 -

`X-Idempotency-Key`：创建类请求幂等键。 -
`Content-Type: application/json`。

响应：

``` json
{
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "req_xxx"
```



校验配额。 8. PostgreSQL 事务创建 Job + Outbox。 9. 返回 QUEUED。 10.

### 3.4.4 API-BR-002 查询任务

`GET /api/v1/browser/jobs/{job_id}`

返回：job_id、status、task_kind、pool_type、queued_time、started_time、finished_time、duration_ms、result、artifacts、error。必须校验
Tenant/Agent/User/Thread 或管理员管理范围。

### 3.4.5 API-BR-003 取消任务

`POST /api/v1/browser/jobs/{job_id}/cancel`

-   QUEUED/DISPATCHED：标记取消，Executor 消费时跳过并 ACK。
-   RUNNING：CANCEL_REQUESTED，通知 Executor 在安全边界关闭 Context。
-   已产生的外部副作用不能因取消而自动撤销。
-   UNKNOWN 必须先核实，不能直接改为 CANCELLED。

### 3.4.6 API-BR-005 创建 Session

请求：

### 3.4.7 API-BR-006 Session 操作

请求：

``` json
{

    "action": "click",
```

-   必须校验 Session 四维归属和 ACTIVE 状态。
-   固定路由到原 Executor。

### 3.4.8 API-BR-008 关闭 Session

标记 CLOSING，拒绝新命令，等待当前命令完成或超时，关闭
Page/Context，更新 CLOSED，清理路由和 Lease，释放配额。

## 3.5 质量实现方案

### 3.5.1 性能设计

  -----------------------------------------------------------------------
  热点                    实现                    放弃方案
  ----------------------- ----------------------- -----------------------
  Chromium 启动           每 Pod 一个常驻 Browser 每 Job 启动 Chromium

  Context                 Ephemeral 单 Job        所有 Thread 永久保留
                          独立创建/释放           

  API 往返                一个 Job 在 Executor    每个 click/navigate
                          内完整执行              单独调用 API

  队列                    有槽位才领取            大量预取后本地排队

  状态                    PostgreSQL 持久化       DB 高频轮询作为主队列

  隔离                    Render/General 两池     所有任务混跑

  Session                 固定 Executor、命令串行 每次动作随机路由

  制品                    ArtifactStore           长期保存在 Pod 磁盘

  认证                    每 Context 独立注入     多用户共享 Context
  -----------------------------------------------------------------------

容量模型：

-   `λ`：任务到达速率，目标 20 Job/s。
-   `T`：平均 Context 占用时间。
-   `C_active ≈ λ × T`。
-   集群持续消费能力 `S` 必须不低于长期到达速率 `λ`。

例如平均占用 3 秒，20 Job/s 约对应 60 个活动任务；仅为 Little's Law
示例，不是实测容量。

Render、General 分开压测： 1. 固定 Pod CPU/内存。 2. 一个 Chromium
进程。 3. 逐步增加 Context 并发。 4. 记录
QPS、P95、CPU、RSS/PSS、崩溃率。 5. 找稳定拐点并留安全余量。 6. 形成每
Pod 稳定吞吐。 7. 按线上任务占比人工确定两个池的副本数。

### 3.5.2 可靠性设计

  ---------------------------------------------------------------------------
  风险                    影响                    应对
  ----------------------- ----------------------- ---------------------------
  PostgreSQL 成功、Redis  Job 不消费              Outbox 重试
  投递失败                                        

  Executor 领取后崩溃     Job 卡住                Pending
                                                  Recovery、Lease、Attempt
                                                  核对

  消息重复                重复执行                幂等键、状态检查

  auto URL 响应丢失       重复报告                UNKNOWN，先查业务任务

  Chromium 崩溃           Pod 任务失败            标记不健康、受控重启/Pod
                                                  重建

  Context 泄漏            内存增长                finally 清理、超时回收

  Persistent Pod 故障     页面现场丢失            Session
                                                  INTERRUPTED，明确恢复边界

  Session 并发            页面状态错乱            命令串行

  Tenant 突发             其他租户饥饿            并发/队列配额

  Render 影响 Automation  延迟升高                两池严格隔离

  Artifact 上传失败       结果不完整              上传成功后再标成功

  Executor 心跳丢失       路由失效                Lease 过期剔除
  ---------------------------------------------------------------------------

ACK 顺序：领取 → 创建 Attempt → RUNNING → 执行 → 上传制品 → PostgreSQL
保存终态 → ACK → 关闭 Context。若 DB 终态成功但 ACK 失败，重投后通过 Job
状态检查跳过重复执行并 ACK。

### 3.5.3 安全性

身份： - Browser API 仅接受可信内部服务身份。 - 用户身份从 Agent
Runtime/Worker 可信上下文获取。 - 校验用户 Agent 授权。 - 每次 Session
操作校验四维归属。 - Executor 只执行已授权任务。

凭证： - User × Platform 管理。 - 不归属 Agent。 - 每个 Context 独立
Cookie/Storage。 - Cookie/Token 不写日志、Trace、普通队列或 API 响应。 -
不建设第二套凭证中心。

Prompt Injection： - 页面 DOM、文本、脚本、下载文件均视为不可信输入。 -
页面内容不得覆盖系统指令或扩大工具权限。 -
页面不能获得平台服务身份凭证。 - 下载/上传有目录、大小和类型限制。

网络： - Browser Pod 网络与其他业务 Pod 一致，处于内网。 -
仍遵守平台统一容器安全基线，防止访问 Service Account
Token、云元数据和内部管理端口。 - 内网不等于页面内容可信。

副作用： - L0 只读。 - L1 可逆写，需 Capability 授权。 - L2
业务写，需明确动作授权、幂等和审计，必要时确认。 - L3
高影响操作默认拒绝，显式审批/确认后允许。 - 未登记动作不得通过任意 JS
绕过策略。 - 页面自动触发业务写操作也必须纳入策略。

多轮操作。 13. Context 回收。 14. Chromium 崩溃和 Pod 重启。

容量： - Render 独立压测。 - General 独立压测。 - 真实任务混合压测。 -
持续 20 Job/s 接收/消费。 - 突发流量。 - Redis Pending Recovery。 -
Context 并发阶梯。 - 长时间运行泄漏。 - Persistent 占用。

每次压测记录：Pod
规格、版本、Fixture、任务占比、并发、持续时间、Accepted/Claimed/Completed/Successful
QPS、P50/P95/P99、CPU、RSS/PSS、失败率、队列趋势。

### 4.1.3 镜像

-   固定 Linux 基础镜像、Python、Playwright、Chromium 版本。
-   安装截图/PDF 所需字体。
-   安装必要图片/PDF 依赖。
-   非 root 运行。
-   临时目录独立可写。
-   `/dev/shm` 容量按压测确定。
-   构建时执行 Chromium 启动和截图 Smoke Test。
-   不在容器启动时动态下载 Chromium。
-   两个 Pool 使用同一镜像，通过 `pool_type` 配置区分。

### 4.1.4 资源配置

不在未压测前给出虚假 CPU/内存规格。确定步骤： 1.
固定节点规格和镜像版本。 2. 分别测试 Render、General 任务。 3. 逐步增加
Context 并发。 4. 观察 CPU、RSS/PSS、P95、失败率和崩溃。 5.
找稳定拐点并保留安全余量。 6. 得到每 Pod 稳定 QPS。 7.
根据生产任务占比确定两池副本比例。 8. 运维根据告警人工调整副本。

### 4.1.5 网络与安全

-   API/Executor 只在内网。
-   普通用户不直接访问 Browser API/Executor。
-   对外仍通过 IM/WebChat。
-   Executor 网络与其他业务 Pod 一致。
-   内部 API 使用服务身份认证。
-   不将服务凭证暴露给网页 JS。
-   Context 使用独立临时目录并清理。

## 4.2 发布与回滚

发布： 1. 构建固定 Chromium/Playwright 镜像。 2. CI
执行启动、Render、Automation、Capture Smoke Test。 3. 部署 Browser API。
4. 部署少量 Render/General Executor。 5. 执行内网测试平台验证。 6.
验证队列、状态、Artifact、隔离和恢复。 7. 按资源池逐步增加副本。 8.
稳定后扩大 Skill 接入。

回滚： - API 回滚到兼容版本。 - Executor 镜像回滚到上一固定版本。 -
Chromium/Playwright 作为验证过的组合回滚。 -
消息格式兼容滚动发布；不兼容变更版本化。 - 回滚期间核对 Job
和副作用状态，不重复执行。 - Persistent Session 可能中断，必须明确通知。

## 4.3 监控告警

看板： 1. Render Pool：副本、Ready、队列深度、最老等待、各类 QPS。 2.
General Pool：同上，另显示 Automation/Capture/Session 数。 3.
Executor：CPU、内存、Chromium、Context、Page、空闲槽位。 4.
Job：状态、失败码、执行时间、UNKNOWN。 5.
Session：ACTIVE/IDLE/INTERRUPTED、超时回收。 6.
Outbox/Redis：待投递、Pending、重领、DLQ。 7. Tenant：配额使用和拒绝。

运维原则： - Render 积压只扩 Render。 - General 积压只扩 General。 -
UNKNOWN 先核实，不通过重试清空。 - CPU 低不代表没有瓶颈，需同时观察
Context 上限、队列和网络等待。

## 4.4 数据迁移与 Skill 迁移

本模块为新增能力，无浏览器运行态数据迁移。

Skill 迁移顺序： 1. 将
`security-incident-followup-card/scripts/generate.js` 公共渲染能力迁移到
Browser SDK。 2. 迁移依赖该引擎的 mssp/mssw
病毒监控、事件推送、仿冒站卡片链路。 3. 迁移 fake-website-alert。 4.
迁移 security-risk-analysis 的 CDP 区域截图/动画帧。 5. 迁移
health-checkup-report HTML/Word/PDF 分支。 6. 评估 ti-redirect-analyze
的 OpenClaw Browser 依赖，改为统一 Session/Automation。 7. 迁移 MSSP
auto URL：触发完成后释放 Context，后续由业务接口/Worker 轮询任务状态。
8. 移除 Skill 自行 `chromium.launch()`、浏览器路径探测和隐式
`NODE_PATH`。

迁移期可使用 Feature Flag，但同一业务 Job
不得同时触发新旧两套实现，避免重复产生副作用。

### B.1 容量压测输出

两个资源池分别输出： - Accepted QPS - Claimed/Started QPS - Completed
QPS - Successful QPS - Queue Wait P50/P95/P99 - Execution P50/P95/P99 -
CPU 平均/峰值 - RSS/PSS 平均/峰值 - Active Context 稳定并发上限 -
Chromium Crash Rate - Context Cleanup Failure - 每 CPU Core Successful
QPS - 每 GiB Successful QPS

Render 和 General 严格隔离，两个池容量不能互相抵扣。

生产副本数按各自任务到达速率、单 Pod
稳定吞吐和安全余量分别计算，再由运维人工配置。
