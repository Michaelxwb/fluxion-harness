# 01 问题与目标

## 1. 产品定位

Fluxion 是业务无关、可开源复用、面向生产环境的 Agent Harness/Platform。核心不是"做一个 Agent Studio"，而是让逻辑 Agent 在生产环境中具备稳定运行、用户能力治理、状态外置、安全执行、可靠流程接入和可观测治理能力。

## 2. 六个长期问题域

### A. Runtime 与事实状态耦合

历史 P01/P02/P04/P05/P07 的本质是：配置、Session、Memory、用户资源或逻辑 Agent 生命周期曾依赖进程/Pod。

目标：RuntimeInstance 只承担可替换计算；配置与 durable state 外置；同一执行视图跨实例等价。

### B. 用户能力与 Agent 耦合

历史 P03/P16/P17 的本质是：Skill/MCP/Tool、Credential、Profile 等用户事实容易形成 Agent 私有副本；"用户拥有"与"Agent 允许"混淆。

目标：Definition、User/Tenant Binding、Agent Allowlist、Tenant Policy 分离；AgentDefinition 不是用户资源 Owner。

### C. Agent Core 持续膨胀

历史 P08/P09/P10/P12/P20 的本质是：每新增 Model/Tool/MCP/Hook/Channel/A2A 都可能修改 Core，并扩大信任边界。

目标：Microkernel + 稳定 Contract；可信基础设施与不可信业务扩展分层。

### D. Agent Tool Chain 不等于可靠业务流程

历史 P11/P21 的本质是：LLM 推理链不能承担 durable retry、补偿、长等待、人工节点和 crash recovery。

目标：Agent 负责推理，Durable Workflow 负责可靠流程；Runtime 只持有 Adapter/Contract。

### E. 生产安全与治理不足

历史 P14/P15/P19/P23 的本质是：Schema 合法不等于业务合法；审批过度会损害体验；策略模型和运行时消费可能漂移。

目标：typed spec 单一真相源；授权、语义校验、风险、审批、执行分层；有明确延迟预算。

### F. 用户、渠道与运营割裂

历史 P06/P13/P18 的本质是：渠道身份、平台用户、配置入口、Trace/Eval 等缺乏统一产品闭环。

目标：统一 PlatformUser；Console 是控制面但不是 Runtime 在线依赖；Eval/Trace 可持续。

## 3. 不再继承的历史方案

以下不是不可变需求：

- "Agent"这个词必须指 Pod；
- RuntimeProfile 等价于逻辑 Agent；
- 每个逻辑 Agent 创建独立 Deployment；
- Workflow Engine 必须自研；
- 所有 Capability 必须使用完全相同的授权算法；
- SQLite/PostgreSQL/DBOS 等具体技术等于产品需求。

## 4. 当前统一术语

- `AgentDefinition`：逻辑/产品 Agent。
- `RuntimeInstance`：Runtime Pod/Process。
- `RuntimePool`：共享无状态计算池。
- `RuntimeProfile`：执行机制配置。
- `Execution`：一次运行。
- `ExecutionSnapshot`：一次运行解析出的不可变视图。
- `CapabilityDefinition`：能力是什么。
- `CapabilityBinding/Grant`：主体如何拥有/使用能力（用户级差异，不写入 AgentDefinition）。
- `AgentCapabilityReference`（Allowlist/Reference）：AgentDefinition 上声明的能力引用（capability_ref + type + version pin）。

> 产品文案映射：Console / 渠道 UI 使用「Agent / 智能体」作为 `AgentDefinition` 的产品展示名；架构与代码必须使用 `AgentDefinition`，禁止复用裸 `Agent` 或新增 `ResourceKind.AGENT`（避免重新引入「Agent = Pod」歧义，并与 Workflow 的 agent node 区分）。

### 4.1 能力授权语义（Skill / Tool / MCP / Workflow 统一）

所有能力类型（skill / tool / mcp / workflow）**统一**支持「按用户授权」：

| 维度 | 语义 |
|------|------|
| `visibility` | public / tenant：全租户用户可用，无需 grant；private：仅被管理员 grant 的用户可用 |
| 管理员 per-user grant | `grant()`（capability_grants）给不同用户配置任意类型能力 |
| Agent allowlist（Tool/MCP） | Agent 必须声明该 Tool/MCP，否则 fail-closed（安全上界） |
| Tenant policy（Tool/MCP） | 租户策略可拒绝（deny 优先） |

> Tool/MCP 是「动作」有副作用，额外保留 `AgentAllowlist ∩ TenantPolicy` 双重硬约束；Skill 是「内容/提示词」、Workflow 是「粗粒度流程」，均按 visibility + grant 授权。四者「按用户授权」语义一致，差异只在 Tool/MCP 多了安全层。Workflow 内部 step 沿用发起用户授权（frozen effective 图进 durable 上下文，流程中途不随授权变更漂移）。

## 5. 成功标准

生产环境至少证明：Pod 可任意替换；无 sticky session 依赖；同一用户跨 Pod 等价；不同用户使用同一 Agent 可得到不同且隔离的 Capability/Credential；配置发布不重启 Runtime；执行中不漂移；durable workflow 不依赖 Runtime 本地状态；高风险写操作不能仅凭 LLM 参数合法直接执行。
