# 02 核心需求

## Runtime

- **REQ-RUN-001** RuntimeInstance 必须可替换，durable fact 不得只存本地。
- **REQ-RUN-002** AgentDefinition 不绑定固定 RuntimeInstance，默认共享 RuntimePool。
- **REQ-RUN-003** 同一 tenant/user/agent/session/config 在不同实例上应解析出等价运行态。
- **REQ-RUN-004** Session、持久 Memory、Credential、Binding、Profile、Approval、Scheduled Task、Workflow State、发布配置必须外置。
- **REQ-RUN-005** Execution 临时状态、L0、连接池、有界 Cache、Plugin implementation 可以本地存在，但必须可丢弃。

## Execution 与配置

- **REQ-EXE-001** 可配置对象采用 typed、versioned Resource。
- **REQ-EXE-002** 每次 Execution 在开始阶段 Resolve Once，形成不可变 Snapshot。
- **REQ-EXE-003** 配置更新只影响新 Execution。
- **REQ-EXE-004** Published Resource 不原地修改。
- **REQ-EXE-005** 发布配置不要求重启 Runtime。

## AgentDefinition

- **REQ-AGT-001** AgentDefinition 是产品逻辑实体，至少可表达 persona/instructions、model ref/policy、runtime profile ref、capability allowlist、workflow/memory/personalization policy ref。
- **REQ-AGT-002** AgentDefinition 不保存用户 Credential、用户私有 config、用户 capability ownership。
- **REQ-AGT-003** Console 的 Agent Studio 操作逻辑 Agent，不管理普通 Runtime Pod 生命周期。

## Capability

- **REQ-CAP-001** Definition 与 Binding 分离。
- **REQ-CAP-002** Tool/MCP 的有效权限必须满足 `UserGrant ∩ AgentAllowlist ∩ TenantPolicy`。
- **REQ-CAP-003** Tool/MCP 缺任一授权维度时 fail-closed。
- **REQ-CAP-004** 同一 AgentDefinition 下，不同用户可以拥有不同版本、参数、enable 状态和 CredentialRef。
- **REQ-CAP-005** Skill 可采用"Agent baseline + User Binding 扩展"语义，但必须单独显式定义并受 Tenant Policy 约束。
- **REQ-CAP-006** EffectiveCapability 由单一 Resolver 产生，执行链不能自行拼第二套授权逻辑。
- **REQ-CAP-007** Tool 是 Agent-facing invocation contract；Plugin 是实现/扩展载体，二者不能永久建模成同一概念。

## User / Channel

- **REQ-USR-001** 所有渠道身份映射到统一 PlatformUser。
- **REQ-USR-002** Profile、Preference、Memory、Capability、Policy、Credential 是用户事实，不创建 Agent 私有副本。
- **REQ-USR-003** tenant/user scope 强制存在，跨 scope 默认拒绝。
- **REQ-CH-001** Channel 通过统一 Adapter Contract 接入，新增通道不修改 AgentLoop。

## Memory

- **REQ-MEM-001** L0 只属于当前 Execution。
- **REQ-MEM-002** Session Context/L1 必须共享持久化。
- **REQ-MEM-003** SessionContextSummary 只属于 Session，不得泄漏到 User Personal Memory。
- **REQ-MEM-004** Personal Memory 区分 Episodic/Semantic，写入必须经过 candidate→policy→consent→learning_enabled。
- **REQ-MEM-005** 用户可查看、纠正、删除 Personal Memory，并可关闭学习。
- **REQ-MEM-006** Context Compaction 与长期 Memory Learning 是两条不同链路。

## Workflow / Scheduler

- **REQ-WF-001** durable retry/compensation/wait/signal/human step/crash recovery 由 Workflow Engine 负责。
- **REQ-WF-002** Runtime 通过 WorkflowEngine Contract/Adapter 调用，不保存 durable workflow state。
- **REQ-WF-003** 当前 DBOS 是可替换实现选择，不进入 Kernel Contract。
- **REQ-SCH-001** Scheduled Task Definition/next-run/lease/claim 等 durable facts 必须外置；Runtime 本地 scheduler 只能作为测试/开发实现。

## 安全

- **REQ-SEC-001** typed Spec Model 是校验、Runtime、Console Schema 的单一真相源。
- **REQ-SEC-002** Secret 明文不进入 Resource Spec/Binding。
- **REQ-SEC-003** Tool 执行顺序至少保证：存在性/授权 → 语义/风险策略 → 必要审批 → Hook/执行。
- **REQ-SEC-004** Schema valid 不代表 semantic valid。
- **REQ-SEC-005** 不可信扩展默认隔离，不获得 Runtime 进程级信任。
- **REQ-SEC-006** 审批状态必须 durable、跨 RuntimeInstance 可见。

## Observability / Eval / DFX

- **REQ-OBS-001** 每个 Execution 有 execution_id、trace_id，并关联 Snapshot/Tool/MCP/Workflow。
- **REQ-OBS-002** 生产 Trace/Audit/Eval 不能依赖 Runtime 进程内唯一存储。
- **REQ-EVAL-001** Eval 与 Agent/Resource/Snapshot 版本关联。
- **REQ-PERF-001** Runtime framework overhead、Resolver、Snapshot、Hook、Console/Chat 等有量化预算。
- **REQ-DEV-001** SQLite dev / PostgreSQL prod 共享领域模型、migration 和 Store Contract。
- **REQ-DEV-002** 核心架构原则必须有真实 integration/deployment Gate。
