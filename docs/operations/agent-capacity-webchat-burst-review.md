## 已确认的功能问题

### 探针触发重启与断连

原 800 用户报告的 77 次 Gateway→Runtime 传输错误有完整时间线：

- `10:04:24Z` 至 `10:04:44Z`：一个 Runtime 的 `/healthz` 连续 3 次超过 1s 超时。
- `10:04:44Z`：Kubernetes 事件明确记录 `Container app failed liveness probe, will be restarted`。
- `10:04:44.607Z` 至 `10:04:45.915Z`：全部 77 次传输错误集中出现，其中 74 次 `ReadError`、
  3 次 `ConnectError`；随后容器在终止宽限结束时以 137 退出。
- Gateway 同期记录 65 次 SSE 打开失败、33 次已打开流失败。因而该轮不能仅归因为请求背压
  或连接池不足；探针重启直接中断了上游连接。

四个正式 Deployment 都未显式声明探针预算，实际使用 1s 超时、10s 周期、连续失败 3 次。
现在均显式使用 **5s / 10s / 3 次**；`/healthz` 与 `/readyz` 的路径和职责保持原有口径。
发布预检拒绝缺失、非整数或低于这些预算的配置，避免下次发布退回默认值。
Kubernetes 对默认值和重启条件的定义见[官方探针文档](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)。

### 领取异常和取消被吞掉

`5f651e2b` 把 claim 移出执行槽锁后，在 `finally` 内返回 `False`，会覆盖 claim 的异常与
`CancelledError`。现在清理预留槽后让原异常/取消传播；登记成功的布尔结果在 `finally` 外返回。
`free_slots` 同时扣除正在领取的槽，避免调度器把这些槽当成可用容量。

3 条新增回归覆盖原异常对象传播、真实任务取消、并发领取不持全局锁且不超发槽位。
旧实现为 **3 failed**，修复后通过。锁内不引入数据库操作。

### 指标架构守卫漂移

SSE 入口 `open()` 已委托 `_open()`，旧 AST 守卫仍只检查外层入口，整套架构检查与单跑都失败。
守卫现在同时核对委托关系与实际实现中的 `opened/resumed` 打点；分别在内存 AST 中移除两种
打点都能使守卫失败，恢复后通过。产品指标行为未调整。

## 测量条件与统计口径

- 四个 Runtime、四个 Console、四个 Gateway、三个 Worker；真实 HTTP、PG、Redis、Skill
  执行与公开 SSE，800 个独立用户各提交一轮，零 ramp，8 个驱动进程。
- 使用已有专用 `muad_acc_*` 验收库追加数据，未清理开发库、未重建本轮验收库。
- Runtime 的 PG 池为每进程 400、overflow 0；Console 为 20+5，Worker 为 20+10。
  上界总和为 `4×400 + 4×25 + 3×30 = 1790`，本轮没有增加连接预算。
- 模型为受控 HTTP 探针，首块延迟 500ms；调用真实 JOIN Skill，Skill 内睡眠 50ms。
- `ADMISSION_REJECTED: 8` 是 8 个驱动进程各自故意提交非法会话的边界拒绝，正常 800 轮的
  `failures` 单独核对，不把预期边界拒绝藏掉。
- `/healthz` 每 Pod 每秒采样一次，客户端最大等待 15s；这是独立诊断采样，不替代 kubelet
  自身的探针结果。记录重启数、传输错误与终帧完整性，不只看数据库中的完成状态。
